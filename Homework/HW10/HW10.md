## **1. Entity & Table Mapping**

| **Annotation**        | **Purpose**                                                  | **Typical Placement**        | **Key Details / Boundary Conditions**                        |
| --------------------- | ------------------------------------------------------------ | ---------------------------- | ------------------------------------------------------------ |
| **@Entity**           | Marks a class as a **JPA entity** (i.e., a row-mapped domain object). | On a **class**               | • Class must have a no-arg constructor.• Name defaults to class name; override with @Entity(name="…"). |
| **@Table**            | Overrides the DB **table name** and optional constraints.    | On the same class as @Entity | java @Table(name="posts", uniqueConstraints=@UniqueConstraint(columnNames="slug")) |
| **@Id**               | Declares the **primary key** field.                          | On a **field** or **getter** | One per entity; type must be serializable.                   |
| **@GeneratedValue**   | Configures primary-key **generation strategy**.              | Next to @Id                  | IDENTITY (auto-increment), SEQUENCE, TABLE, AUTO.            |
| **@Column**           | Overrides column name & DDL attributes.                      | On a field/getter            | nullable, length, updatable, insertable, etc.                |
| **@UniqueConstraint** | Declares a multi-column **unique key**.                      | Inside @Table                | DB must support the constraint; else DDL will fail.          |

## **2 .Relationship Mapping**

| **Annotation**  | **Cardinality**                                              | **Used On**               | **Extras / Edge Cases**                                 |
| --------------- | ------------------------------------------------------------ | ------------------------- | ------------------------------------------------------- |
| **@ManyToOne**  | Many → One                                                   | Child entity field        | Default FetchType.EAGER; consider LAZY for performance. |
| **@OneToMany**  | One → Many                                                   | Parent collection         | Must set mappedBy or own a join table.                  |
| **@ManyToMany** | Many ↔ Many                                                  | Collection on either side | Requires a **join table** (automatic or explicit).      |
| **@JoinColumn** | Defines the **FK column** for @ManyToOne/@OneToOne.          | Field or property         | Use nullable=false for non-null FK at DDL level.        |
| **@JoinTable**  | Customizes the **join table** for @ManyToMany or bidirectional @OneToMany. | Collection field          | Allows naming, indexes, composite PK.                   |

## **3. Data-Access Components**

| **Annotation**          | **Purpose**                                                  | **Where to Use**                      | **Notes**                                                    |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------- | ------------------------------------------------------------ |
| **@Repository**         | Marks a **DAO** (Data Access Object) and enables automatic **exception translation** to DataAccessException. | On a class that interacts with the DB | Enables component scanning.                                  |
| **@PersistenceContext** | Injects a managed **EntityManager**.                         | Field, setter, or constructor param   | type=EXTENDED keeps the persistence context across transactions (rare). |

| **@Param**              | Binds a method parameter to a named placeholder inside @Query. | Repository method parameters          | :#{#exp} allows SpEL expressions.                            |

**3. Write Custom JPA Methods and Validate Syntax**

Based on the codebase from **Task 2**:

Write custom **JPA methods** using **Spring Data JPA naming conventions**.

Demonstrate how **JPA** performs **compile-time syntax checks** on method names.

Ans:

**Core idea first →** Spring Data JPA ships an *annotation processor* (a compile-time tool) that **parses every repository method name while your project is being compiled**.

If the processor cannot match the property path you wrote (findByFooBar…) against the fields in the corresponding entity class, **the Java compiler fails with an error, before the application even starts**.

Below is a minimal, end-to-end demonstration.

------

## **1 . Enable the compile-time checker**

```xml
<!-- pom.xml -->
<dependencies>
    <!-- your normal Spring-Data dependency -->
    <dependency>
        <groupId>org.springframework.data</groupId>
        <artifactId>spring-data-jpa</artifactId>
    </dependency>
</dependencies>

<!-- add the processor on the compile class-path -->
<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.11.0</version>
      <configuration>
        <annotationProcessorPaths>
          <!-- The processor lives in spring-data-commons -->
          <path>
            <groupId>org.springframework.data</groupId>
            <artifactId>spring-data-commons</artifactId>
            <version>${spring-data.version}</version>
          </path>
        </annotationProcessorPaths>
      </configuration>
    </plugin>
  </plugins>
</build>
```

> **What happens?**

> During compilation the **Spring Data Repository Annotation Processor** scans every interface that extends Repository/JpaRepository, tokenises each method name, and tries to walk the property path on the *entity metamodel*.

------

## **2 . A valid repository method (compiles ✅)**

```java
@Entity                      // simple entity
public class Post {
    @Id Long id;
    String title;
    String author;
}

@Repository                  // repository with a valid derived query
public interface PostRepository
        extends JpaRepository<Post, Long> {

    // ‘title’ exists on Post, so the processor is happy
    List<Post> findByTitleContainingIgnoreCase(String keyword);
}
```

**Compilation result**

```shell
[INFO] BUILD SUCCESS
```

------

## **3 . An invalid method (compile-time failure ❌)**

```java
@Repository
public interface PostRepository
        extends JpaRepository<Post, Long> {

    // Typo: ‘titel’ does NOT exist on Post
    List<Post> findByTitelContainingIgnoreCase(String keyword); // ← error
}
```

**Compiler output**

```shell
org.springframework.data.repository.query.parser.InvalidPropertyException:
No property 'titel' found on Post!
  at PostRepository.findByTitelContainingIgnoreCase(PostRepository.java:8)
```

*The build stops here; we will catch the mistake before runtime.*

------

## **4 . Boundary conditions & edge cases**

| **Scenario**                             | **Processor behaviour**                                      |
| ---------------------------------------- | ------------------------------------------------------------ |
| **Nested path** (findByAuthor_FirstName) | Walks relationship graph; fails if any segment is missing.   |
| **Ambiguous path** (findByOrder)         | Fails if both a property *and* a relationship named order exist. |
| **Kotlin/JPA records (no getters)**      | Requires Kotlin annotation-processing plugin or Lombok accessors. |
| **Disabled processor** (IDE only)        | If you rely on IDE build (Gradle/Maven not invoked), enable *annotation processing* in IDE settings. |

------

## 5 . Why this matters

- **Fail fast** – avoids hidden runtime errors that would only surface when the repository method is first called.
- **Refactoring safety** – renaming an entity field in your IDE will instantly flag all affected repository methods.
- **IDE completion** – IntelliJ/VS Code use the same metadata, providing autocomplete and quick-fixes.

------

### **Take-away**:

Spring Data JPA’s annotation processor performs a compile-time syntax and semantic check on repository method names.Typos or invalid property paths cause a compiler error, guaranteeing your derived-query methods are correct before the application is ever run.

### 5. Technology Comparison  

**Q:** Explain the differences and relationships among *Spring Data JPA*, *Hibernate*, *HikariCP*, and *JDBC*.

**A:**  

| Layer                                 | Purpose                                                      | Key Points                                                   | Relationship                                                 |
| ------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **JDBC** (Java Database Connectivity) | Low‑level Java API that lets you send SQL to any relational database with a compatible driver. | • Manual SQL, connection handling.  <br>• Returns `ResultSet` objects. | Foundation that all higher‑level ORMs ultimately call.       |
| **Hibernate**                         | Object–Relational Mapping (ORM) implementation of the JPA spec plus many extras. | • Maps Java classes ↔︎ database tables. <br>• Generates SQL, handles caching, transactions, dirty checking, lazy loading. | Uses JDBC under the hood.                                    |
| **Spring Data JPA**                   | Spring module that sits on top of JPA providers (e.g., Hibernate) to remove boilerplate. | • Repository interfaces with derived‑query methods. <br>• Transparent pagination, auditing. | Delegates to a JPA provider such as Hibernate, which in turn uses JDBC. |
| **HikariCP**                          | High‑performance JDBC connection pool.                       | • Manages a pool of DB connections for reuse. <br>• Fast acquire/release, low GC. | Configured by Spring Boot ⇢ provides JDBC `Connection` objects to Hibernate/Spring Data. |

### 6. JPA Relationships  

**Q:** Explain the following annotations with examples, and their properties `mappedBy`, `cascade`, and `fetch`.

```java
// OneToMany & ManyToOne
@Entity
class Author {
    @Id Long id;
    String name;

    @OneToMany(mappedBy = "author",
               cascade = CascadeType.ALL,
               fetch = FetchType.LAZY)
    private List<Book> books = new ArrayList<>();
}

@Entity
class Book {
    @Id Long id;
    String title;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id")   // FK
    private Author author;
}

// ManyToMany
@Entity
class Student {
    @Id Long id;
    String name;

    @ManyToMany(fetch = FetchType.LAZY)
    @JoinTable(name = "student_course",
        joinColumns        = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id"))
    Set<Course> courses = new HashSet<>();
}

@Entity
class Course { ... }
```

* **`mappedBy`** (only on the *inverse* side) tells JPA which field owns the FK; avoids join table duplication.  
* **`cascade`** controls which entity‑manager operations propagate (e.g., `PERSIST`, `REMOVE`).  
* **`fetch`** chooses how association data is loaded. (`LAZY` = on demand proxy; `EAGER` = join fetch now).

| Annotation    | Cardinality          | Owning Side                                 | Default `fetch` |
| ------------- | -------------------- | ------------------------------------------- | --------------- |
| `@OneToMany`  | 1 → N                | *Many* side (Book) unless `mappedBy` is set | `LAZY`          |
| `@ManyToOne`  | N → 1                | always the *Many* side                      | `EAGER`         |
| `@ManyToMany` | N ↔︎ N via join table | Side without `mappedBy`                     | `LAZY`          |

### 7. Cascade Options in JPA  

**Q:** Explain `cascade = CascadeType.ALL` and `orphanRemoval = true`. List all other `CascadeType` values.

* `CascadeType.ALL` – shorthand for persisting, merging, removing, detaching, and refreshing the child when the parent is acted on.  
* `orphanRemoval = true` – when a child entity is removed from the collection reference, it will be **deleted** in DB on flush.

| CascadeType | Purpose                                                |
| ----------- | ------------------------------------------------------ |
| `PERSIST`   | Propagate `persist()` (insert).                        |
| `MERGE`     | Propagate `merge()` (update/attach).                   |
| `REMOVE`    | Propagate `remove()` (delete).                         |
| `DETACH`    | Propagate `detach()` (clear from persistence context). |
| `REFRESH`   | Propagate `refresh()` (reload from DB).                |
| `ALL`       | Shortcut for the above five.                           |

---

### 8. Fetch Types in JPA  

**Q:** Explain `FetchType.LAZY` vs `FetchType.EAGER` and when to use each.

| FetchType | Behaviour                                                    | Pros                                                         | Cons                                                         | Typical Use                                                  |
| --------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `LAZY`    | Creates proxy; executes query only when field first accessed. | • Saves bandwidth on unneeded data.<br>• Avoids N+1 when tuned. | • May cause *LazyInitializationException* outside transaction.<br>• Extra queries if not optimized. | Default for collections; use almost everywhere unless you *always* need the data. |
| `EAGER`   | Uses `JOIN` (or second query) immediately when parent is loaded. | • Ready to use even outside persistence context.             | • Unpredictable big joins, slower queries, memory overhead.  | For truly mandatory, small single‑valued associations (e.g., `@ManyToOne` lookup tables). |

## Part 4: Querying and Data Access

### 9. JPQL Overview  

**Q:** What is JPQL and how does it differ from SQL? Provide examples.

* *JPQL* (Java Persistence Query Language) is an **object‑oriented** query language defined by JPA.  
* Targets entity names & fields, not table/column names.  
* Translated to vendor‑specific SQL by the JPA provider.

| Aspect  | JPQL                                               | SQL                                                          |
| ------- | -------------------------------------------------- | ------------------------------------------------------------ |
| Domain  | Entities (`Book`)                                  | Tables (`books`)                                             |
| Select  | `SELECT b FROM Book b WHERE b.author.name = :name` | `SELECT b.* FROM books b JOIN authors a ON ... WHERE a.name = ?` |
| Updates | `UPDATE Book b SET b.price = :p WHERE b.id = :id`  | `UPDATE books SET price=? WHERE id=?`                        |

### 10. Using the `@Query` Annotation  

**Q:** What does `@Query` do and how to use it for JPQL vs native SQL?

```java
// JPQL
@Query("SELECT p FROM Post p WHERE p.title LIKE %:keyword%")
List<Post> search(@Param("keyword") String keyword);

// Native
@Query(value = "SELECT * FROM posts WHERE title ILIKE %:keyword%",
       nativeQuery = true)
List<Post> searchNative(@Param("keyword") String keyword);
```

* Placed on repository methods.  
* Replaces derived query with explicit JPQL or native SQL string.  
* Supports pagination (`Pageable`), projections, SpEL, and `@Modifying` for DML.

## Part 5: Hibernate and Entity Management

### 11. EntityManager vs SessionFactory  

**Q:** Compare `EntityManager` and `SessionFactory` and illustrate their relationship.

| Item         | JPA API                | Hibernate API    |
| ------------ | ---------------------- | ---------------- |
| Factory      | `EntityManagerFactory` | `SessionFactory` |
| Unit‑of‑work | `EntityManager`        | `Session`        |

```java
// Screenshot-esque snippet
@Autowired
private EntityManager em;   // Spring Boot injects a proxy

public void demo() {
    Session session = em.unwrap(Session.class); // Hibernate core
    // both APIs now reference the same persistence context
}
```

* Spring Boot auto‑configures a `SessionFactory` internally when Hibernate is the provider.  
* `EntityManagerFactory` delegates to `SessionFactory`; each `EntityManager` wraps a Hibernate `Session`.

### 12. SessionFactory vs Session  

* **SessionFactory** – heavyweight singleton; created at startup; caches entity metadata; opens `Session`s.  
* **Session** – lightweight, short‑lived **unit‑of‑work**, tied to transaction; holds first‑level cache and dirty checking; interacts with DB.

## Part 6: Database Fundamentals

### 13. SQL Transactions  

**Q:** What is a transaction and how do Spring/Hibernate manage them?

* A **transaction** = atomic, consistent, isolated, durable (ACID) sequence of DB operations.  
* In Spring you annotate service methods with `@Transactional`; a proxy opens a JDBC connection, sets auto‑commit off, delegates to Hibernate; on success commits, on unchecked exception rolls back.

```java
@Service
class AccountService {
  @Transactional
  public void transfer(...) { ... }
}
```

### 14. Hibernate Caching  

**Q:** Explain Hibernate’s caching mechanisms.

| Level        | Scope                                    | Provider                             | What is cached                        |
| ------------ | ---------------------------------------- | ------------------------------------ | ------------------------------------- |
| First‑Level  | Per‑`Session`                            | Built‑in                             | Entities & identifiers; mandatory.    |
| Second‑Level | Across sessions in same `SessionFactory` | Optional (EHCache, Caffeine, Redis…) | Entities, collections, query results. |

* First‑level prevents duplicate selects within one transaction.  
* Second‑level reduces round‑trips for read‑mostly data across requests; must be configured entity‑by‑entity.
