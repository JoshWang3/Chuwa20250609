3. ## Explain why do we need model mappers in Spring, and in what scanrios we need it.

   **Core Idea:**

   Model mappers automate and centralize the conversion between different object types (e.g. Entities, DTOs, ViewModels), cutting boilerplate and keeping your layers clean.

   ------

   **Why Use Model Mappers?**

   - **Boilerplate Reduction:** Eliminate repetitive set/get code.
   - **Separation of Concerns:** Keep mapping logic out of services/controllers.
   - **Consistency:** Apply global rules for naming, type conversion, nested objects.
   - **Complex Mappings:** Handle renaming, enums, dates, collections with minimal code.

   ------

   **When to Use:**

   - **Entity → DTO:** Hide internal fields and avoid lazy-loading issues in API responses.
   - **DTO → Entity/Domain:** Convert incoming payloads into business models.
   - **Microservices Integration:** Map external models to your internal schema.
   - **ViewModel Construction:** Build front-end–friendly objects from domain data.
   - **Batch Processing & Tests:** Quickly map large collections or create test fixtures.

   ------

   **Quick MapStruct Example:**

   ```java
   @Mapper(componentModel = "spring")
   public interface UserMapper {
     UserDTO toDto(UserEntity e);
     UserEntity toEntity(UserDTO d);
   }
   
   @Service
   public class UserService {
     private final UserMapper mapper;
     public UserService(UserMapper mapper) { this.mapper = mapper; }
     public UserDTO get(Long id) {
       return mapper.toDto(repo.findById(id).orElseThrow());
     }
   }
   ```

4. ## Provide 3 examples in which model mapper will NOT map succesfully, explain why.

   --**Different Field Names without Configuration**

   ```
   class UserEntity { String firstName; /*…*/ }
   class UserDTO    { String givenName;  /*…*/ }
   ```

   *Why it fails:* The mapper looks for properties with identical names by default. Since firstName ≠ givenName, no automatic mapping occurs unless you add a custom property mapping or rename strategy.

   --**Incompatible Types without Converter**

   ```
   class OrderEntity { BigDecimal total; /*…*/ }
   class OrderDTO    { String total;     /*…*/ }
   ```

   *Why it fails:* Converting BigDecimal → String (or vice versa) requires a type converter. Without registering a converter or custom mapping, the mapper can’t translate those types and will throw an error or leave the field null.

   --**No Accessible Constructor or Setter**

   ```java
   class ProductEntity {
     private final String id;
     public ProductEntity(String id) { this.id = id; }
     public String getId() { return id; }
   }
   class ProductDTO {
     private String id;
     // no setter: public void setId(String id) {…}
   }
   ```

   *Why it fails:* The mapper needs either a no-arg constructor + setters or a matching all-args constructor (for MapStruct). Here, ProductDTO has no setter and no matching constructor, so it can’t instantiate and populate the id field.

5. ## Explain how model mapper cast different data types between source object and target class.

   **Core Idea:**

   Model mappers handle type mismatches by leveraging built-in converters (for common types) and by allowing you to register custom converters for anything else.

   ------

   ### **1. Built-in Converters**

   Most mapper libraries (e.g. ModelMapper, MapStruct) include out-of-the-box support for simple conversions:

   - **Primitives & Wrappers:** int ↔ Integer, long ↔ Long
   - **Numbers ↔ String:** Integer ↔ "123"
   - **Enums ↔ String:** Status.ACTIVE ↔ "ACTIVE"
   - **Dates ↔ java.time:** java.util.Date ↔ LocalDateTime

   Under the hood, they either:

   - **ModelMapper**: use a **Converter** registry (mapper.getConverterRegistry()) with priority-ordered converters.
   - **MapStruct**: generate code calling String.valueOf(), Enum.valueOf(), or DateTimeFormatter.

   ------

   ### **2. Custom Converters**

   When you hit a gap, you register your own:

   #### **ModelMapper Example**

   ```java
   Converter<String, UUID> toUuid = ctx -> 
       ctx.getSource() == null ? null : UUID.fromString(ctx.getSource());
   mapper.addConverter(toUuid);
   ```

   #### **MapStruct Example**

   ```java
   @Mapper
   public interface OrderMapper {
     @Mapping(target="id", source="id", qualifiedByName="toUuid")
     OrderDTO toDto(OrderEntity e);
   
     @Named("toUuid")
     static UUID toUuid(String s) {
       return s == null ? null : UUID.fromString(s);
     }
   }
   ```

   ------

   ### **3. Conversion Process**

   1. **Match Source → Target Type:** mapper checks if a converter exists for <S, T>.
   2. **Apply Converter:** if found, it transforms the value.
   3. **Fallback:** if no converter, and types are assignable, it copies directly; otherwise throws or leaves null.

   ------

   **In Summary:**

   Mappers use a registry of converters (built-in + your custom ones) to transform mismatched types at mapping time, keeping your mapping declarations clean and centralized.

7. ## Explain how Controller Advices work, is there any other approach to do same/similar global API exception handling?

   **Core Idea:**

   @ControllerAdvice centralizes exception handling (and other cross-cutting concerns) across all your @Controller-annotated beans. It lets you define @ExceptionHandler, @InitBinder, and @ModelAttribute methods once, rather than repeating them in every controller.

   ------

   ### **How** **@ControllerAdvice** **Works**

   1. **Component Scanning:** Spring detects your @ControllerAdvice bean at startup.
   2. **Target Matching:** You can scope it to all controllers or subsets via annotations (basePackages, assignableTypes, annotations).
   3. **Exception Resolution:** When a controller method throws, Spring’s DispatcherServlet delegates to any @ExceptionHandler methods in matching @ControllerAdvice (or in the controller itself).
   4. **Response Formation:** Your handler method returns a value (e.g. ResponseEntity<ErrorDTO>) that Spring writes out as the HTTP response.

   

   ```java
   @ControllerAdvice
   public class GlobalExceptionHandler {
     @ExceptionHandler(EntityNotFoundException.class)
     public ResponseEntity<ErrorDTO> handleNotFound(EntityNotFoundException ex) {
       ErrorDTO err = new ErrorDTO("NOT_FOUND", ex.getMessage());
       return ResponseEntity.status(HttpStatus.NOT_FOUND).body(err);
     }
   }
   ```

   ------

   ### **Alternative Global Exception-Handling Approaches**

   1. **Extend ResponseEntityExceptionHandler**

      Subclass and override its protected methods for Spring MVC–specific exceptions (e.g. handleMethodArgumentNotValid)—still packaged in a @ControllerAdvice.

   2. **Custom HandlerExceptionResolver**

      Implement the HandlerExceptionResolver interface and register it in your WebMvcConfigurer. Gives full control over exception-to-response mapping.

   3. **Error Controller (ErrorController)**

      For Spring Boot apps, implement ErrorController (override error()), or customize BasicErrorController to handle all “whitelisted” errors (404, 500, etc.) at the /error endpoint.

   4. **Servlet Filter or Spring OncePerRequestFilter**

      Wrap your entire request chain in a filter to catch uncaught exceptions, then write directly to the HttpServletResponse.

   5. **AOP Aspect**

      Define an @Aspect that wraps all controller methods with an @Around advice, catches exceptions, and transforms them into a unified response.

   ------

   **Summary:**

   While @ControllerAdvice is the idiomatic, declarative way to handle global API errors in Spring MVC, you can also use custom exception resolvers, error controllers, servlet filters, or AOP aspects depending on your needs for flexibility, ordering, or integration with Spring Boot’s error page mechanism.

8. ## What's the difference between throwing a regular exception and a customized API exception that will be eventually thrown to Controller Advice codes? Please provide screenshots to explain your findings.

   **Core Idea:**

   A plain exception is a catch-all error with no built-in semantics for your API layer, whereas a custom API exception carries explicit metadata (status code, error key, user-friendly message) so your @ControllerAdvice can map it cleanly to an HTTP response.

   ------

   

   | **Aspect**                                               | **Regular Exception**                                        | **Custom API Exception** |
   | -------------------------------------------------------- | ------------------------------------------------------------ | ------------------------ |
   | **Type & Semantics**                                     | RuntimeException, IllegalArgumentException, etc.—generic categories. |                          |
   |                                                          | No contract about how it’s used or what HTTP status it implies. |                          |
   | **Error Payload**                                        | You get a stack trace and a message string only.             |                          |
   |                                                          | Your advice usually turns it into a 500 with a generic body. |                          |
   | **HTTP Mapping**                                         | ControllerAdvice has to inspect exception type or message to choose a status—often defaults to 500. |                          |
   |                                                          | Custom exception holds a dedicated HttpStatus, error code, or payload DTO, so advice method can simply read fields. |                          |
   | **Handler Granularity**                                  | Hard to differentiate validation vs. authorization vs. business errors without custom branching logic. |                          |
   |                                                          | You can catch each custom subclass in its own @ExceptionHandler, giving precise responses. |                          |
   | **Clarity & Maintenance**                                | Over time, many code paths throw the same exceptions—harder to trace root causes. |                          |
   |                                                          | Custom exceptions document intended failure modes (e.g. ResourceNotFoundException, InvalidOrderStateException). |                          |
   | **Example**                                              | ```java                                                      |                          |
   | // Generic                                               |                                                              |                          |
   | if (obj==null) throw new NullPointerException(“no obj”); |                                                              |                          |

   ```java
   |                          | ```java  
   // Custom  
   public class ApiException extends RuntimeException {  
     private final HttpStatus status;  
     private final String errorCode;  
     public ApiException(HttpStatus s, String code, String msg){…}  
   }  
   // usage  
   if (order==null) throw new ApiException(NOT_FOUND, "ORDER_404", "Order not found");  
   ```

   ------

   **In practice:**

   - **Regular exceptions** → all fall into a catch-all handler → HTTP 500 + generic error.
   - **Custom API exceptions** → each type carries its status/code → @ControllerAdvice returns rich, accurate HTTP responses without extra if/instanceof logic.

10. ## Explain Spring framework fundamental principles. And how can they help build business applications?

    **Core Idea:**

    Spring’s core principles—Inversion of Control (IoC)/Dependency Injection (DI), Aspect-Oriented Programming (AOP), modular architecture, “convention over configuration,” and rich infrastructure support—bring loose coupling, testability, and declarative services to business applications.

    ------

    ## **1. Inversion of Control / Dependency Injection**

    - **What:** Objects receive (“are injected with”) their collaborators rather than creating them.
    - **How it helps:**
      - **Decoupling:** Business classes depend on interfaces, not concrete implementations.
      - **Testability:** Swap real components for mocks in unit tests with no code changes.
      - **Configuration Flexibility:** Wire different implementations (e.g. dev vs prod) via profiles or configuration files.

    ------

    ## **2. Aspect-Oriented Programming**

    - **What:** Encapsulate cross-cutting concerns (logging, security, transactions) into reusable aspects.
    - **How it helps:**
      - **Separation of Concerns:** Business code remains clean of plumbing logic.
      - **Consistency:** Apply policies (e.g. audit trails, error handling) uniformly across services.
      - **Maintainability:** Change an aspect (e.g. logging level) in one place, not everywhere.

    ------

    ## **3. Modular, Layered Architecture & “Convention over Configuration”**

    - **What:**
      - Spring Boot auto-configuration picks sensible defaults; modules (Data, MVC, Security, Batch, Cloud) plug in as needed.
      - Standard layer separation: Controllers → Services → Repositories.
    - **How it helps:**
      - **Rapid Development:** Minimal XML or boilerplate; start from opinionated defaults.
      - **Scalability:** Swap modules (e.g. replace JDBC with JPA) by changing a dependency.
      - **Team Alignment:** Everybody follows the same project structure and patterns.

    ------

    ## **4. Declarative Transaction Management**

    - **What:** Annotate methods/classes with @Transactional to demarcate transaction boundaries.
    - **How it helps:**
      - **Data Integrity:** Automatic commit/rollback ensures consistency.
      - **Simplicity:** No manual begin/commit calls; reduces error risk.
      - **Isolation Control:** Configure propagation and isolation levels per method.

    ------

    ## **5. Rich Infrastructure & Integration**

    - **What:** Out-of-the-box support for REST MVC, data access (JDBC, JPA), messaging, scheduling, caching, security.
    - **How it helps:**
      - **Reusability:** Leverage battle-tested modules instead of reinventing wheels.
      - **Interoperability:** Integrate with cloud services (Spring Cloud), enterprise systems (JMS, Kafka) with minimal glue code.
      - **Production Readiness:** Health checks, metrics, externalized config, and graceful shutdown via Actuator.

    ------

    **In Summary:**

    By embracing IoC/DI, AOP, modular conventions, declarative transactions, and a comprehensive ecosystem, Spring lets you build business applications that are **loosely coupled**, **easy to test**, **configurable**, and **ready to scale**.

11. ## Explain different types of dependency injection, explain their suitable use cases, and why fielde injection is not recommended in general. Please provide necessary code snippets and screenshots if possible.

    **Core Idea:**

    Spring supports three DI styles—constructor, setter, and field injection—each suited to different needs. Constructor and setter injection make dependencies explicit and testable; field injection hides them and is generally discouraged.

    ------

    ## **1. Constructor Injection**

    ```java
    @Component
    public class OrderService {
        private final PaymentGateway gateway;
    
        // Mandatory dependency → injected here
        public OrderService(PaymentGateway gateway) {
            this.gateway = gateway;
        }
    
        public void place(Order o) {
            gateway.charge(o.getAmount());
        }
    }
    ```

    - **Use cases:**
      - **Required** dependencies that a bean cannot function without.
      - Enables **final** fields → immutable, thread-safe.
      - Simplest to unit-test (no Spring context needed).

    ------

    ## **2. Setter Injection**

    ```java
    @Component
    public class ReportGenerator {
        private DataSource dataSource;
    
        // Optional or replaceable dependency
        @Autowired
        public void setDataSource(DataSource ds) {
            this.dataSource = ds;
        }
    
        public Report create() {
            return dataSource.query("..."); 
        }
    }
    ```

    - **Use cases:**
      - **Optional** or **mutable** dependencies.
      - Backwards compatible when adding new collaborators.
      - Allows re-wiring at runtime (e.g. in tests or management UIs).

    ------

    ## **3. Field Injection**

    ```java
    @Component
    public class UserController {
        @Autowired
        private UserService service;  // hidden dependency
    
        @GetMapping("/users")
        public List<User> list() {
            return service.findAll();
        }
    }
    ```

    - **Why it works:** Spring uses reflection to set private fields.
    - **Why it’s discouraged:**
      1. **Hidden Contract:** Dependencies aren’t visible in constructors or setters.
      2. **No final Fields:** You lose immutability guarantees.
      3. **Hard to Unit-Test:** Requires Spring test support or reflection hacks to inject mocks.
      4. **Violates Encapsulation:** Other code can’t see or override them easily.

    ------

    ## **Summary of When to Use Which**

    | **Style**       | **Best for**                      | **Testability** | **Immutability** |
    | --------------- | --------------------------------- | --------------- | ---------------- |
    | **Constructor** | Required, core dependencies       | Excellent       | Yes              |
    | **Setter**      | Optional or late-set dependencies | Good            | No               |
    | **Field**       | Quick demos or legacy constraints | Poor            | No               |

    **Recommendation:**

    Default to **constructor injection** for everything required, use **setter injection** sparingly for optional beans, and avoid **field injection** except in quick prototypes or when you cannot refactor existing code.

12. ## Explain different types of application context in Spring framework, with screenshots. You may take https://github.com/CTYue/springIOC for reference.

    **Core Idea:**

    Spring’s ApplicationContext is the central interface for accessing beans, resources, and application events. There are several concrete implementations—standalone vs. web—each suited to different configuration styles and environments.

    ------

    ## **1. Standalone Contexts**

    | **Context class**                      | **Description**                                              |
    | -------------------------------------- | ------------------------------------------------------------ |
    | **AnnotationConfigApplicationContext** | Java-based, annotation-driven configuration. Scan @Configuration classes and register beans. |
    | **ClassPathXmlApplicationContext**     | XML-based, loads one or more config files from the classpath (classpath:/appContext.xml). |
    | **FileSystemXmlApplicationContext**    | XML-based, loads config files from the file system (e.g. file:///config/appContext.xml). |
    | **GenericApplicationContext**          | “Blank” programmatic context. Combine with XmlBeanDefinitionReader, AnnotatedBeanDefinitionReader, or manual bean registration. |
    | **GenericGroovyApplicationContext**    | Load Groovy scripts as bean definitions.                     |

    ------

    ## **2. Web Contexts**

    All implement **WebApplicationContext** (extends ApplicationContext) and integrate with the ServletContext.

    | **Context class**                         | **Description**                                              |
    | ----------------------------------------- | ------------------------------------------------------------ |
    | **XmlWebApplicationContext**              | XML-based config for web apps. Typically initialized by ContextLoaderListener in web.xml. |
    | **AnnotationConfigWebApplicationContext** | Java-config for web apps. Scan @Configuration for controllers, services, etc., and register DispatcherServlet beans. |
    | **GenericWebApplicationContext**          | Programmatic web context. Register readers or call registerBean(); can share parent context with a standalone root context. |

    ------

    ## **3. How They Fit Together**

    1. **Root vs. Dispatcher Context:**
       - A **root** WebApplicationContext (loaded by ContextLoaderListener) holds middle-/lower-level beans (services, repositories).
       - Each **DispatcherServlet** gets its own child WebApplicationContext for web-layer beans (controllers, view resolvers), inheriting from the root.
    2. **Bean Inheritance:**
       - Child contexts see parent beans, but not vice-versa.
       - Allows separation of concerns (web vs. business layers).

    ------

    ## **4. Choosing the Right One**

    - **Java Config (Standalone):** AnnotationConfigApplicationContext or AnnotationConfigWebApplicationContext
    - **XML Config (Legacy):** ClassPathXmlApplicationContext or XmlWebApplicationContext
    - **Programmatic / Testing:** GenericApplicationContext / GenericWebApplicationContext
    - **Scripting:** GenericGroovyApplicationContext

    

    By picking the context that matches your configuration style and environment (standalone app vs. web app), you get consistent bean management, resource loading, and lifecycle support across your Spring application.

    

13. ## Compare @Component and @Bean and in which scenario they should be used.

    **Core Idea:**

    - @Component is a class-level stereotype scanned and registered automatically.
    - @Bean is a method-level declaration inside a @Configuration class, giving you full control over instantiation.

    | **Aspect**                | @Component                                                   | @Bean                                                        |
    | ------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **Declaration**           | Placed on your own classes (or use @Service, @Repository, @Controller) and picked up via classpath scanning. | Placed on factory methods within a @Configuration class.     |
    | **Scanning vs Manual**    | **Auto-discovered** by component scanning (@ComponentScan).  | **Explicitly** registered—no scanning needed.                |
    | **Use Cases**             | • Your own POJOs and services with simple constructors.• When you’re happy with default lifecycle and no extra setup logic. | • Third-party or legacy classes you can’t annotate.• Beans requiring complex construction logic (parameters, conditionals, initialization).• When you need fine-grained control (custom init/destroy methods, dynamic parameters). |
    | **Dependency Resolution** | Only default constructor or @Autowired setters/fields.       | Method parameters are automatically injected—you can pull in other beans or config values. |
    | **Proxy Semantics**       | Standard singleton or scoped bean.                           | In a full @Configuration class, Spring uses CGLIB to ensure @Bean methods respect scoping and proxies. |

    ------

    ### **Examples**

    #### **Using** **@Component**

    ```java
    @Service  // a specialized @Component
    public class InvoiceService {
      private final PaymentGateway gateway;
      @Autowired
      public InvoiceService(PaymentGateway gateway) {
        this.gateway = gateway;
      }
      // ...
    }
    ```

    #### **Using** **@Bean**

    ```java
    @Configuration
    public class AppConfig {
      @Bean
      public PaymentGateway paymentGateway(@Value("${pay.url}") String url) {
        // complex setup, perhaps reading properties or conditional logic
        return new RestPaymentGateway(url, /* other dependencies */);
      }
    }
    ```

    ------

    **When to choose which:**

    - **Default:** annotate your own simple components with @Component (or its stereotypes).
    - **Explicit control or non-modifiable classes:** use @Bean methods to register and configure them in a @Configuration class.

14. ## Explain Spring bean scopes and how to pick the correct bean scope.

    **Core Idea:**

    Spring bean scopes define *when* and *how long* a bean instance lives. Choose the narrowest scope that still meets your requirements: prefer singleton for stateless services and use narrower scopes only when you need per-use or per-request state.

    ------

    ## **Built-in Scopes**

    | **Scope**               | **Definition**                                               | **Use Case**                                                 |
    | ----------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **singleton** (default) | One shared instance per Spring ApplicationContext.           | Stateless services, data repositories, configuration beans.  |
    | **prototype**           | A new instance each time it’s injected or retrieved.         | Stateful helpers, per-operation data holders (e.g. a builder). |
    | **request**             | One instance per HTTP request (only in a web-aware context). | Beans that hold request-specific data, like security context or request metadata. |
    | **session**             | One instance per HTTP session (only in a web-aware context). | Shopping cart, user preferences, or other session-scoped state. |
    | **application**         | One instance per ServletContext (shared across all requests and sessions). | Shared, application-wide resources in a web app (e.g. a cache manager). |
    | **websocket**           | One instance per WebSocket session.                          | Beans that maintain state over a WebSocket connection.       |

    ------

    ## **How to Pick the Right Scope**

    1. **Stateless vs. Stateful**
       - If your bean holds *no* per-user or per-operation state, use **singleton** for maximum performance and simplicity.
       - If it *does* hold state that must not be shared, consider **prototype** (per-use) or a web scope.
    2. **Web Context Needs**
       - For data tied to a single HTTP request—use **request**.
       - For data tied to a user’s session—use **session**.
       - For data shared across the entire web app lifecycle—use **application**.
    3. **Resource Management**
       - Prototype beans aren’t managed past creation: Spring doesn’t call lifecycle callbacks after injection, so you handle cleanup yourself.
       - Web scopes require a Spring MVC or WebFlux environment.
    4. **Testing & Complexity**
       - More scopes → more complexity in lifecycle and testing. Default to **singleton** unless you have a clear, scope-specific need.

    ------

    ## **Example**

    ```java
    @Component
    @Scope("prototype")        // a new instance each time
    public class ReportBuilder {
        // stateful, so each report gets its own builder
    }
    
    @Configuration
    public class WebConfig {
        @Bean
        @Scope(value = WebApplicationContext.SCOPE_REQUEST,
               proxyMode = ScopedProxyMode.TARGET_CLASS)
        public UserContext userContext() {
            return new UserContext();  // holds info for a single HTTP request
        }
    }
    ```

    **Summary:**

    - **Default** to singleton for stateless beans.
    - Use **prototype** only for stateful, per-operation objects.
    - In web apps, pick **request**, **session**, or **application** when bean state must align with those lifecycles.

15. ## Explain the difference between bean id and bean class.

    **Core Idea:**

    - **Bean ID** is the unique name (or alias) by which Spring registers and looks up a bean in its container.
    - **Bean Class** is the actual Java type that Spring will instantiate when creating that bean.

    ------

    ### **Bean ID**

    - **Definition**: The identifier you assign to a bean definition.
    - **Usage**:
      - Used in XML:

    ```xml
    <bean id="orderService" class="com.example.OrderServiceImpl"/>
    ```

    - Used in annotations: the default name of a @Component is the class name with a lowercase first letter (e.g. orderController for OrderController), or you can override it:

    

    ```java
    @Service("paymentService")
    public class PaymentServiceImpl { … }
    ```

    - **Role**:
      - Reference other beans via @Autowired @Qualifier("beanId") or <ref bean="beanId"/>.
      - Support multiple beans of the same type by unique names or aliases.

    ### **Bean Class**

    - **Definition**: The fully qualified Java class or interface that Spring will instantiate (and possibly proxy) to create the bean.
    - **Usage**:
      - Declared in XML via the class attribute.
      - With annotations, it’s simply the annotated class itself.
    - **Role**:
      - Determines the bean’s API (its methods, fields, and implemented interfaces).
      - Used by type-based injection (@Autowired by type) when there’s a single candidate.

    ------

    ### **Why the Distinction Matters**

    1. **Lookup Flexibility**
       - By **ID**: context.getBean("orderService")
       - By **Type**: context.getBean(OrderService.class)
    2. **Multiple Implementations**
       - Two beans of the same class need different IDs (emailSender, smsSender) so you can pick which one to inject.
    3. **Aliasing & Profiles**
       - You can define multiple IDs or aliases for the same class (e.g. "legacyDao" and "newDao") and control which one is active via profiles or conditions.

    ------

    **In short:**

    - The **bean ID** is the container’s lookup key.

    - The **bean class** is the code Spring instantiates.

      They work together so you can register, find, and inject beans by name and/or by type.

16. ## Explain that when a bean has multiple alternative implementations, how will Spring decide which bean implementation to inject/autowire?

    **Core Idea:**

    When multiple beans match an autowired type, Spring applies a resolution order: type → @Primary → @Qualifier → by-name matching → fail fast.

    1. **Type Matching**

    ```java
    interface Payment { … }
    @Component class CreditCardPayment implements Payment { … }
    @Component class PaypalPayment     implements Payment { … }
    @Autowired Payment payment;  // two candidates!
    ```

    1. Spring sees two Payment beans → move to next steps.
    2. **@Primary Annotation**

    ```java
    @Component @Primary
    class CreditCardPayment implements Payment { … }
    ```

    1. Mark one bean as primary → used by default when type alone is ambiguous.
    2. **@Qualifier Annotation**

    ```java
    @Component("paypal")
    class PaypalPayment implements Payment { … }
    
    @Autowired
    @Qualifier("paypal")
    private Payment payment;
    ```

    1. Explicitly name which bean to inject, overriding @Primary.
    2. **By-Name Matching**

    ```java
    @Component("creditCardPayment")
    class CreditCardPayment implements Payment { … }
    
    @Autowired
    private Payment creditCardPayment;  // field name == bean name
    ```

    1. If no @Primary or @Qualifier, Spring tries matching the **parameter/field name** to a bean name.
    2. **Collection and Map Injection**
       - @Autowired List<Payment> payments; injects **all** Payment beans in declaration order (or sorted by @Order).
       - @Autowired Map<String,Payment> payments; injects a map keyed by bean name.
    3. **Failure Case**
       - If after all steps more than one candidate remains, you get:

    ```java
    NoUniqueBeanDefinitionException: expected single matching bean but found 2: [paypal,creditCardPayment]
    ```

    ------

    **Summary:**

    Spring’s autowiring picks by type, then prefers a bean marked @Primary, then honors an explicit @Qualifier, then falls back to matching the injection point’s name to a bean name—finally failing if ambiguity persists.
