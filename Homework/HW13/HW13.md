2. ## Explain **TLS**, **PKI**, **certificate**, **public key**, **private key**, and **signature**.

   **Core idea :**

   *TLS* secures data in transit by first using *public-key cryptography*—distributed and trusted through a *PKI* (Public Key Infrastructure)—to authenticate the other party via a *certificate* and *digital signatures*. Once trust is established (the other side proves it controls the matching *private key* for the certificate’s *public key*), both sides agree on shared *symmetric* keys to encrypt and integrity-protect all further traffic.

   ------

   ## Term-by-term explanations

   ### **1.** **TLS (Transport Layer Security)**

   A security protocol that sits “above” TCP (and other transports) to provide:

   - **Confidentiality** (encryption so eavesdroppers can’t read data),
   - **Integrity** (detection of tampering),
   - **Authentication** (verifying who you’re talking to—most commonly the server; optionally the client),
   - **Forward secrecy** (if using ephemeral Diffie-Hellman/ECDHE: past traffic stays safe even if long-term keys are later compromised).

   TLS is what turns http:// into secure https://, and also protects email, messaging, and many other application protocols.

   ------

   ### 2. **PKI (Public Key Infrastructure)**

   Not a single technology but an **ecosystem + ruleset** that makes large-scale trust in public keys practical. A PKI typically includes:

   - **Certificate Authorities (CAs)** that issue and sign certificates binding an identity (domain name, org, person) to a public key.
   - **Root CAs** (pre-trusted in operating systems/browsers) and **intermediate CAs** forming *trust chains*.
   - **Registration / validation processes** to confirm the requester actually controls the claimed identity (e.g., domain ownership checks).
   - **Revocation mechanisms** (CRL—Certificate Revocation List, OCSP—Online Certificate Status Protocol).
   - **Policies & procedures** defining how keys are generated, stored, rotated, and validated.

   PKI answers: *“Whose public key is this, and why should I trust it?”*

   ------

   ### 3. **Certificate**(commonly an X.509 certificate)

   A structured, signed data object that **binds an identity to a public key**. Key fields include:

   - **Subject** (who the certificate is for—e.g., www.example.com).
   - **Subject Public Key Info** (the actual public key + algorithm).
   - **Validity Period** (Not Before / Not After dates).
   - **Extensions** (usage constraints, subject alternative names, key usage, etc.).
   - **Issuer** (who signed it—a CA).
   - **Digital Signature from the Issuer** (proves the CA vouches for the binding).

   When a browser connects to a website, the site sends its certificate (and usually intermediate certificates). The browser checks the chain back to a trusted root CA and verifies the signature(s) to ensure authenticity.

   ------

   ### **4.** **Public Key**

   The *shareable* half of an **asymmetric key pair**. Depending on the algorithm and usage:

   - Used by others to **verify a signature** created with the matching private key.

   - Or used by others to **encrypt data** that only the holder of the private key can decrypt.

     (Modern TLS most often uses it for authentication/signature verification, while key *agreement* is done via Diffie-Hellman / ECDHE.)

   Public keys are safe to distribute widely—but they’re only useful if you can trust that the key truly belongs to the claimed identity. That’s where certificates/PKI come in.

   ------

   ### **5.** **Private Key**

   The *secret* half of the asymmetric key pair. Must be tightly protected (file permissions, hardware security module (HSM), TPM, cloud KMS, etc.). Uses:

   - **Create digital signatures** that can be verified with the public key.

   - **Decrypt** data encrypted to the public key (when that mode is used).

     If a private key is stolen, an attacker can impersonate the owner (issue valid signatures, possibly decrypt past traffic—depending on protocol and ciphers).

   ------

   ### 6. **Digital Signature**

   A cryptographic value computed over some data using a **private key**. Verification uses the corresponding **public key**. A valid signature provides:

   - **Authentication**: The signer held the private key.
   - **Integrity**: The signed data wasn’t altered (verification fails if it changes).
   - **Non-repudiation** (in some legal/operational contexts): The signer can’t easily deny having signed, assuming strong key custody controls.

   Most modern signature schemes hash the data first, then sign the hash (because it’s shorter and more secure).

   ------

   ### How they work together in a **TLS handshake** **(high-level flow)**

   Below is the *typical* (TLS 1.2/1.3-ish) server-authenticated handshake pattern. Exact message names vary by version, but the trust steps are conceptually similar.

   ```bash
   Client → Server: ClientHello (supported TLS versions, cipher suites, etc.)
   Server → Client: ServerHello, Certificate (server cert chain), [CertificateVerify signature], ServerKeyShare, etc.
   Client:
     1. Validates the server's certificate chain (PKI trust path to a known root).
     2. Checks hostname matches subject/SAN.
     3. Checks cert validity dates & revocation status.
     4. Uses the public key from the server certificate to verify the server's digital signature
        over handshake data (proves server controls the private key).
   Both sides: Perform (E)CDHE key agreement → derive symmetric session keys.
   All further app data: Encrypted & integrity-protected using symmetric crypto.
   ```

   **Optional client certificate:** If the server requests client authentication, the client sends its own certificate and proves possession of its private key via a signature, allowing mutual TLS (mTLS).

   ------

   ### **Quick mental mapping**

   | **Concept**       | **What it is**      | **Who owns it**               | **Shared?**        | **Used for**                            | **Where seen in TLS**                    |
   | ----------------- | ------------------- | ----------------------------- | ------------------ | --------------------------------------- | ---------------------------------------- |
   | TLS               | Protocol            | N/A                           | N/A                | Secure transport                        | Handshake + record encryption            |
   | PKI               | Trust system        | Ecosystem (OS, browsers, CAs) | N/A                | Bind identity ↔ key                     | Validating cert chains                   |
   | Certificate       | Data structure      | Issued to subject             | Public             | Publish subject’s public key + identity | Sent by server (and maybe client)        |
   | Public Key        | Math object         | Belongs to key pair owner     | Public             | Verify sigs / encrypt to owner          | Inside cert; used to verify server proof |
   | Private Key       | Secret              | Must be guarded by owner      | Private            | Create sigs / decrypt                   | Stays on server (or client in mTLS)      |
   | Digital Signature | Cryptographic proof | Generated w/ private key      | Publicly checkable | Prove control + data integrity          | Server proves identity during handshake  |

   ------

   ### **Common edge cases & pitfalls (边界条件 / 常见坑)**

   1. **Expired certificate** – Validity dates passed; clients should reject or warn.
   2. **Hostname mismatch** – Certificate subject/SAN doesn’t match the domain you connected to; indicates possible misconfig or attack.
   3. **Untrusted issuer** – CA not in client trust store (self-signed or private CA); needs manual trust import.
   4. **Revoked certificate** – Private key compromised or cert mis-issued; clients *should* check CRL/OCSP (behavior varies).
   5. **Weak algorithms** – Obsolete signature algorithms (e.g., SHA-1) or key sizes too small; modern clients may refuse.
   6. **Key reuse across services** – Increases blast radius if key leaks; prefer separate certs/keys per domain/service.
   7. **Lack of forward secrecy** (old RSA key exchange) – If private key is later stolen, past captured traffic can be decrypted. Prefer ECDHE/DHE suites (TLS 1.3 defaults to forward secrecy).

   ------

   ### **Everyday analogy (quick memory aid)**

   - **Public key** = Your publicly listed *PO box number*.
   - **Private key** = The *key to open the box*; only you have it.
   - **Certificate** = A government-issued *ID card* saying “This PO box really belongs to Alice” and signed by a trusted authority.
   - **PKI** = The whole government system that issues, verifies, and can revoke IDs.
   - **Digital signature** = Your tamper-proof *seal* you stamp on letters—anyone can confirm it’s yours.
   - **TLS** = The *secure envelope delivery service* that checks IDs, seals envelopes, and delivers mail securely.

   ------

   ### **Minimal “If you remember nothing else” summary**

   > TLS relies on PKI-issued certificates to distribute trusted public keys. The party proves ownership of the certificate by signing handshake data with the matching private key. Once verified, both sides derive symmetric keys and communicate securely.

5. ## Compare **authentication** and **authorization**? Name and explain important components in Spring security that undertake **authentication** and **authorization**

   **Memory Hook:**

   **AuthN = Name (Who are you?) → create Authentication.**

   **AuthZ = PermiZsions (What can you do?) → allow/deny access.**

   ------

   ##  Quick Compare

   |           | **Authentication**                                      | **Authorization**                                 |
   | --------- | ------------------------------------------------------- | ------------------------------------------------- |
   | Core Q    | Who are you?                                            | What are you allowed to do?                       |
   | Output    | Authenticated Authentication (principal + authorities). | Permit or deny (403) for a given action/resource. |
   | Fail Code | **401** need/invalid creds.                             | **403** creds ok but no rights.                   |

   ------

   ## Spring Security “AuthN Pipeline” (Who?)

   **Extract creds → Validate → Build Identity → Store**

   1. **Filters** (entry points):
      - UsernamePasswordAuthenticationFilter (form)
      - BasicAuthenticationFilter
      - BearerTokenAuthenticationFilter / OAuth2 Resource Server
      - RememberMeAuthenticationFilter, AnonymousAuthenticationFilter (fallback)
   2. **AuthenticationManager** (usually ProviderManager) – routes to…
   3. **AuthenticationProvider** (mechanism-specific) – e.g., DaoAuthenticationProvider, JWT, LDAP.
   4. **UserDetailsService+PasswordEncoder`** – load user + verify password hash.
   5. **SecurityContextHolder** – stores successful Authentication for the request/thread.

   ------

   ## Spring Security “AuthZ Pipeline” (What?)

   **Check request → Compare required vs. granted → Allow/deny**

   1. **FilterSecurityInterceptor** (URL/web)
      - Looks up needed attributes (roles/expressions).
      - Calls AccessDecisionManager.
   2. **AccessDecisionManager** + voters:
      - RoleVoter (ROLE_*)
      - AuthenticatedVoter (anonymous vs. user)
      - ExpressionVoter (SpEL: hasRole('ADMIN'), etc.)
      - Your custom voters.
   3. **Method Security** (service-level defense in depth):
      - @PreAuthorize, @PostAuthorize, @Secured, @RolesAllowed.
      - Enforced by MethodSecurityInterceptor.

   ## Failure Translators (Important for APIs)

   | **Situation**  | **Component**            | **Typical Response** |
   | -------------- | ------------------------ | -------------------- |
   | No / bad creds | AuthenticationEntryPoint | 401                  |
   | Not allowed    | AccessDeniedHandler      | 403                  |

   ------

   ## Mini Mental Flow Diagram

   ```bash
   Request
     ↓
   [Auth Filters] → AuthenticationManager → AuthenticationProvider → UserDetailsService/PasswordEncoder
     → SecurityContextHolder(Authentication)
     ↓
   FilterSecurityInterceptor → AccessDecisionManager (voters)
     ↓
   Controller / @PreAuthorize ...
   ```

   ### **Fast Interview Soundbite**

   > *Authentication proves identity (AuthN = Name). Filters extract credentials and delegate to an AuthenticationManager/Provider to create an* *Authentication* *stored in the SecurityContext. Authorization checks permissions (AuthZ = PermiZsions) using FilterSecurityInterceptor + AccessDecisionManager (voters) and method-level annotations. 401 = need creds; 403 = not allowed.*

6. ## Explain HTTP Session?

   **Memory Hook:** *Session = server-side “memory bucket” keyed by a cookie ID so stateless HTTP can feel stateful.*

   ------

   ### **6.1. What**

   A server-created data store (key–value) tied to a **session ID** (e.g., JSESSIONID) that the client sends on every request.

   ------

   ### 6.**2. Why**

   Remember user across requests: logged-in state, cart, CSRF token, prefs, cached user data.

   ------

   ### **6.3. How It Flows**

   1. Server creates session → sends Set-Cookie: JSESSIONID=....
   2. Client sends cookie back.
   3. Server looks up session → retrieves attributes → continues.

   ------

   ### **6.4. Lifecycle Checklist**

   - **Create** on login or getSession(true).
   - **Use** while requests arrive with the ID.
   - **Timeout** after inactivity.
   - **Invalidate** on logout.
   - **Rotate ID** after login (stop fixation).

   ------

   ### 6.**5. Security Must-Dos**

   Secure + HttpOnly + SameSite cookie; HTTPS; short idle timeout; regenerate ID on privilege change; clear on logout.

   ------

   ### **6.6. Scaling Options (remember “I-S-D-J”)**

   **I**n-memory (single node) → dev.

   **S**ticky LB → small clusters.

   **D**istributed store (Redis/DB) → prod scale.

   **J**WT (stateless) → no server session, but revocation harder.

   ------

   ### **6.7. Spring Security Quick Map**

   - Auth result (SecurityContext) stored in **HttpSession** by default.
   - Control behavior: sessionCreationPolicy(...).
   - Protect vs fixation: .sessionFixation().migrateSession().
   - Limit concurrent logins: .maximumSessions(n).
   - Use **Spring Session** to externalize storage (e.g., Redis) for clusters.

7. ## Explain Cookie? 

   - **Definition**: Small data stored in browser, sent with each HTTP request to the same domain.
   - **Purpose**: Session management, personalization, tracking.
   - **Set by Server**: Via Set-Cookie header.
   - **Sent by Browser**: Via Cookie header.
   - **Attributes**:
     - HttpOnly: not JS-accessible
     - Secure: HTTPS only
     - Max-Age/Expires: lifespan
     - Path: scope
     - SameSite: controls cross-site sending

   Used to maintain state in stateless HTTP.

8. ## Compare Session and Cookie?

   ### **Cookie vs Session (Concise Comparison)**

   | **Feature**    | **Cookie**                          | **Session**                       |
   | -------------- | ----------------------------------- | --------------------------------- |
   | **Storage**    | Client-side (browser)               | Server-side                       |
   | **Security**   | Less secure (can be modified)       | More secure (stored on server)    |
   | **Size Limit** | ~4KB                                | Larger (limited by server memory) |
   | **Lifespan**   | Can persist (via Expires)           | Ends with browser/session timeout |
   | **Usage**      | Track user prefs, login info        | Store user state securely         |
   | **Access**     | Accessible via JS (unless HttpOnly) | Not accessible from client-side   |

    Typically: **Session ID stored in cookie**, then server retrieves session data.

11. ## What is the **spring security filter**?

    ### **Spring Security Filter (Concise)**

    The **Spring Security Filter** is a **chain of servlet filters** that intercepts HTTP requests and applies security logic.

    ------

    ### **Purpose:**

    - Authenticate users
    - Authorize access
    - Protect against attacks (e.g., CSRF)

    ------

    ### ** Core Filters (in order):**

    1. **SecurityContextPersistenceFilter** – Loads security context
    2. **UsernamePasswordAuthenticationFilter** – Handles login (form-based)
    3. **BasicAuthenticationFilter** – Handles HTTP Basic Auth
    4. **BearerTokenAuthenticationFilter** – Handles JWT bearer tokens
    5. **ExceptionTranslationFilter** – Handles security exceptions
    6. **FilterSecurityInterceptor** – Authorizes access to resources

    ------

    ### **Notes:**

    - Configured via FilterChainProxy
    - Order matters
    - Custom filters can be added before/after standard ones

12. ## Explain **bearer token** and how **JWT** works.

    ### **Bearer Token (Concise)**

    A **Bearer Token** is a type of access token used in HTTP Authorization headers to authenticate users.

    **Format:**

    ```java
    Authorization: Bearer <token>
    ```

    - The word **“Bearer”** indicates the token is a credential.
    - Whoever has the token is “authorized”—no further proof needed.

    ------

    ### How JWT (JSON Web Token) Works

    A **JWT** is a self-contained token that encodes authentication and claims data.

    **Structure (3 parts):**

    ```
    <Header>.<Payload>.<Signature>
    ```

    #### **1. Header**

    Specifies the token type and signing algorithm:

    ```
    { "alg": "HS256", "typ": "JWT" }
    ```

    #### **2. Payload**

    Contains claims (e.g., user info, expiration):

    ```
    { "sub": "123456", "role": "admin", "exp": 1710000000 }
    ```

    #### **3. Signature**

    Ensures token integrity:

    ```
    HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
    ```

    ------

    ### **JWT Flow**

    1. **Login** → Server verifies credentials, issues JWT.
    2. **Client stores JWT** (usually in localStorage or cookie).
    3. **Client sends JWT** with each request in the Authorization header.
    4. **Server verifies JWT** signature and extracts user info.

13. ## Explain how do we store sensitive user information such as password and credit card number in DB? 

    #### **1.** **Passwords → Hash (Not Encrypt!)**

    - **Use strong hashing algorithm**: BCrypt, Argon2, or PBKDF2
    - Add **salt**: random value to prevent rainbow table attacks
    - Example (BCrypt in Spring Security):

    ```
    new BCryptPasswordEncoder().encode("plainPassword");
    ```

    - ✅ Cannot be reversed (one-way)

    ------

    #### **2.** **Credit Card Numbers → Encrypt**

    - Use **symmetric encryption** (e.g., AES)
    - Store **encryption key securely** (e.g., hardware security module or vault)
    - Example libraries: JCE (Java Cryptography Extension), Jasypt
    - Can be decrypted when needed (e.g., for payments)

    ------

    ### **Best Practices**

    - Enable **TLS/HTTPS** for data in transit
    - Apply **access control** to restrict who can read sensitive fields
    - Use **database field-level encryption** if supported
    - Regularly **rotate encryption keys** and monitor access

14. ## Compare UserDetailService, AuthenticationProvider, AuthenticationManager, AuthenticationFilter?

    ### ** Spring Security Core Interfaces (Concise Comparison)**

    | **Component**              | **Responsibility**                                           | **Key Role**                                                 |
    | -------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **UserDetailsService**     | Loads user info (username, password, roles) from DB or service | Used during authentication to fetch user details             |
    | **AuthenticationProvider** | Validates Authentication (e.g., username & password) using UserDetailsService | Core logic for verifying credentials                         |
    | **AuthenticationManager**  | Orchestrates authentication by delegating to AuthenticationProvider(s) | Central entry point for authentication process               |
    | **AuthenticationFilter**   | Intercepts HTTP requests, extracts credentials, and triggers authentication | Typically UsernamePasswordAuthenticationFilter or custom filters |

    ------

    ### **Flow Overview:**

    1. **Filter** captures login request → builds Authentication object.
    2. Passes it to **AuthenticationManager**
    3. Which delegates to **AuthenticationProvider**
    4. Which calls **UserDetailsService** to load user info
    5. Verifies credentials → returns authenticated Authentication object

15. ## What is the disadvantage of Session? how to overcome the disadvantage?

    ### ** Disadvantages of Session (and Solutions)**

    | **Disadvantage**                    | **Explanation**                                              | **Solution**                                                 |
    | ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
    | **Not scalable**                    | Sessions are stored in server memory—doesn’t scale well in distributed systems | Use **distributed session storage** (e.g., Redis, DB)        |
    | **Tied to server**                  | Session data is lost if request hits another server          | Use **sticky sessions** or **shared session store**          |
    | **Memory consumption**              | Many users = high memory usage                               | Use **stateless auth** (e.g., JWT) for less critical session data |
    | **Requires session management**     | Sessions expire, must be cleaned up                          | Implement **session timeout** and **cleanup policies**       |
    | **Vulnerable to session hijacking** | If session ID is stolen, attacker gains access               | Use **HTTPS**, regenerate session ID after login, enable **HttpOnly** cookie |

    **Modern Alternative**: Use **JWT (JSON Web Token)** for **stateless** authentication where suitable.

17. ## What is the role of configure(HttpSecurity http) and configure(AuthenticationManagerBuilder auth)?

    ### --**Role of** **configure(HttpSecurity http)**  **vs**  **configure(AuthenticationManagerBuilder auth)**

    | **Method**                                       | **Role**                                                     |
    | ------------------------------------------------ | ------------------------------------------------------------ |
    | **configure(HttpSecurity http)**                 | Defines **authorization rules** and **HTTP security config** |
    | **configure(AuthenticationManagerBuilder auth)** | Defines **authentication logic** (e.g., how to load and verify users) |

    ------

    ### **configure(HttpSecurity http)**

    **Used for:**

    - Route protection (.antMatchers("/admin").hasRole("ADMIN"))
    - Login/logout config
    - CSRF, CORS, HTTPS, session, etc.

    ```java
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
          .authorizeRequests()
            .antMatchers("/admin").hasRole("ADMIN")
            .anyRequest().authenticated()
          .and()
            .formLogin();
    }
    ```

    ------

    ### **configure(AuthenticationManagerBuilder auth)**

    **Used for:**

    - UserDetailsService and password encoder
    - In-memory or JDBC auth config

    ```java
    @Override
    protected void configure(AuthenticationManagerBuilder auth) throws Exception {
        auth
          .userDetailsService(myUserDetailsService)
          .passwordEncoder(new BCryptPasswordEncoder());
    }
    ```

    ------

    **In Spring Boot 3+**, these are replaced by defining SecurityFilterChain and injecting beans like AuthenticationManager.

19. ## Explain best practices to securely store secrets in applications.

    ### **Best Practices for Securely Storing Secrets in Applications**

    | **Practice**                                    | **Explanation**                                              |
    | ----------------------------------------------- | ------------------------------------------------------------ |
    | **1. Don’t hardcode secrets**                   | Never store passwords, API keys, or tokens directly in source code. |
    | **2. Use environment variables**                | Load secrets at runtime via System.getenv() or Spring @Value. |
    | **3. Use a secrets manager**                    | Tools like **AWS Secrets Manager**, **HashiCorp Vault**, **Azure Key Vault**. |
    | **4. Encrypt secrets at rest**                  | Encrypt config files or DB fields that store sensitive info. |
    | **5. Restrict access**                          | Use role-based access to limit who/what can read secrets.    |
    | **6. Rotate secrets regularly**                 | Automate key/token rotation to reduce risk of long-term exposure. |
    | **7. Use secure config servers**                | In microservices, use tools like **Spring Cloud Config + Vault**. |
    | **8. Avoid storing secrets in version control** | Use .gitignore, secret scanners, and audit tools.            |
    | **9. Audit and monitor**                        | Log access to secrets and alert on unusual patterns.         |
    | **10. Secure secrets in memory**                | Minimize lifetime of secrets in memory, clear when done.     |

    ------

     In **Spring Boot**, use:

    - application.properties ➝ for non-sensitive config
    - **Externalized configuration** with env vars or cloud vault
    - @Value("${secret}") or @ConfigurationProperties
