**Core idea**

Quality assurance follows two parallel tracks:

1. **Testing depth — from microscopic Unit Tests to business-facing User-Acceptance Tests (UAT).**
2. **Environment maturity — from flexible Development to locked-down Production.**

Understanding where a test sits on these two tracks tells you **what it guards, when to run it, and how costly failure is.**

------

## **1 · Testing-type cheat sheet**

| **Type**                          | **Scope & Goal**                                             | **Concrete example**                                         | **Common edge cases / “gotchas”**                   |
| --------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | --------------------------------------------------- |
| **Unit Testing**                  | Single function or class behaves correctly.                  | divide(a,b) returns 2 for (6,3).                             | Zero-division, null input, overflow.                |
| **Functional Testing**            | One public feature meets its spec (“black-box”).             | “Create-order” REST endpoint returns an order-id and 201 status. | Missing token, invalid JSON, timezone mismatch.     |
| **Integration Testing**           | Multiple components collaborate as expected.                 | Order service calls Inventory and Payment services and rolls back if either fails. | Network timeout, partial failure, schema drift.     |
| **Regression Testing**            | Prove new code didn’t break old behaviour.                   | After coupon bug-fix, legacy checkout flows still price correctly. | Feature flag flipped off, DB migration rolled back. |
| **Smoke Testing**                 | Quick sanity check that the build “starts & lights up”.      | After deploy: homepage 200 OK, login succeeds once.          | Mis-set ENV var, secrets missing.                   |
| **Performance Testing**           | Meets latency / throughput under *expected* load.            | 200 QPS login API stays < 100 ms P95.                        | Cold cache, GC pause, DB connection pool limits.    |
| **Stress Testing**                | Observe behaviour at *extreme* load and recovery.            | Hammer API with 1 000 QPS for 30 min: expect graceful degradation, auto-scale, clean recovery. | CPU = 100 %, message queue back-pressure.           |
| **A/B Testing**                   | Compare two versions on user-level metrics.                  | New button colour vs old; click-through rate over 5 % lift?  | Sample bias, user bucketing leaks, cookie loss.     |
| **End-to-End (E2E) Testing**      | Full user journey across UI → back-end → DB.                 | Selenium script: add to cart, pay in sandbox, receive email. | Third-party sandbox down, flaky UI selector.        |
| **User Acceptance Testing (UAT)** | Real business owner signs off that the system solves the problem. | Finance team runs monthly-closing workflow in UAT and approves. | Regulatory rules, anonymised data hides edge case.  |

**Testing pyramid rule-of-thumb:**

Unit tests » Service-level tests » Integration/E2E tests in *count*; inverse in *run time & maintenance cost*.

## **2 · Environment-type cheat sheet**

| **Environment**        | **Purpose & Traits**                                         | **Example quirks**                                           |
| ---------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Development (Dev)**  | Rapid coding; mocks allowed; breaking things inexpensive.    | Local docker-compose spins all micro-services.               |
| **QA / Test**          | Reproduce bugs and run automated suites; data reset often.   | CI pipeline auto-deploys every merge, then fires full regression pack. |
| **Pre-prod / Staging** | Production-like config for final dress rehearsal, low real traffic. | Canary 5 % traffic to new recommendation model; DB masked copy. |
| **Production (Prod)**  | Real users, strict SLA, auditing & monitoring.               | Kubernetes prod-us-west-2 cluster serving 1 M DAU; blue-green deploys. |

### **Typical promotion flow**

1. **Dev**: developer commits, runs Unit + Functional tests locally.
2. Merge → **QA**: CI deploys, executes Regression, Performance, Integration packs.
3. Tag release → **Staging**: Smoke, End-to-End, UAT, optional A/B seed cohort.
4. Sign-off → **Prod**: gradual rollout, live monitoring; Stress tests may run off-hours on a clone.

------

### **Key comparisons & edge-case reminders**

- **Granularity vs cost**: The later a defect escapes the pyramid (e.g., discovered only in Prod), the more expensive it is to fix.
- **Environment parity**: Staging must mirror Prod in config/hardware; otherwise performance numbers lie.
- **Data isolation**: Never use live customer data in lower tiers unless fully masked.
- **Rollback strategy**: Blue-green or feature flags make Regression failures in Prod reversible within minutes.
