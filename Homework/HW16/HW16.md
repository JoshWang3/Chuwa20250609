# Explain following concepts, and how they coordinate with each other: 

## **Concepts**

**Topic (主题, topic)**

- A named stream of records (messages).
- Has a **replication factor** and a **retention policy** (time or size; optionally **log compaction**).
- Is split into **partitions** for scale and parallelism.

**Partition (分区, partition)**

- An ordered, append-only log within a topic. Ordering is guaranteed **only within a single partition**.
- One broker acts as **leader** for a partition; others (if replicated) are **followers** in the **ISR** (in-sync replicas).
- Records are routed to a partition by a **partitioner** (e.g., hash of key) or round-robin.

**Broker (代理/节点, broker)**

- A Kafka server process; a **cluster** comprises multiple brokers.
- Stores partition data; leaders handle reads/writes, followers replicate.
- One broker acts as the **controller** (cluster metadata, leader elections).

**Producer (生产者, producer)**

- Client that sends records to a topic.
- Chooses partition (by key/partitioner).
- Reliability knobs: acks (0/1/all), **idempotent producer** (deduplicate retries), **transactions** (exactly-once across partitions within a transaction).

**Consumer Group (消费者组, consumer group)**

- A set of consumers that **share the work** of reading a topic.
- Each partition is owned by **at most one** consumer in the group at a time (parallelism = partitions).
- The group’s progress is tracked by **offsets** stored in Kafka.

**Offset (位移, offset)**

- The position (logical index) of a record within a partition.
- Maintained **per (topic, partition, consumer-group)**.
- Stored in the internal topic __consumer_offsets when **committed** (auto or manual).
- Reading is “pull”: consumers fetch from their last committed (or in-memory) offset.

**ZooKeeper (ZK, ZooKeeper)**

- Historically used by Kafka for cluster metadata, controller election, and configs.
- **Modern note:** Newer Kafka deployments use **KRaft** (Kafka Raft) to replace ZooKeeper; concepts here still apply, but the controller and metadata are managed internally, not via ZK.



Answer following questions:

1. ## Given N (number of partitions) and M (number of consumers,) what will happen when N>=M and N<M respectively?

   **1) N partitions vs. M consumers (same group)**

   - **N ≥ M:** Every consumer gets ≥1 partition; if **N > M**, some consumers read multiple partitions; if **N = M**, it’s 1:1.
   - **N < M:** At most **N** consumers are active (one per partition); the extra **M−N** consumers are **idle**.
   - **Rule:** A partition is owned by **at most one** consumer in a group at a time.

2. ## Explain how brokers work with topics?

   **2) How brokers work with topics**

   - A **topic** is split into **partitions** that are spread across **brokers**.
   - For each partition, one broker is **leader** (handles produce/fetch); others are **followers** (replicate, form ISR).
   - A **controller** assigns leaders and coordinates failover/rebalances (via ZooKeeper in legacy, **KRaft** now).

3. ## Are messages pushed to consumers or consumers pull messages from topics?

   **3) Push or pull?**

   - **Producers push** to broker leaders.
   - **Consumers pull** (long-poll **Fetch** requests) from brokers.

4. ## How to avoid duplicate consumption of messages?

   **4) Avoiding duplicate consumption**

   - **Process → then commit** offsets (disable auto-commit or use sync commits).
   - Use **idempotent producer** (enable.idempotence=true, acks=all, retries) and, when needed, **transactions** (commit output + offsets atomically; consumers use isolation.level=read_committed).
   - Make the sink **idempotent** (e.g., UPSERT by key, de-dupe by message ID).

5. ## What will happen if some consumers are down in a consumer group? Will data loss occur? Why?

   **5) Some consumers in the group go down**

   - Group **rebalances**; remaining consumers take over those partitions.
   - **No Kafka data loss**; lag may grow.
   - **Caveat:** If the outage lasts beyond topic **retention**, that group can **miss** expired data.

6. ## What will happen if an entire consumer group is down? Will data loss occur? Why?

   **6) Entire consumer group goes down**

   - No reading; data stays in Kafka until **retention**.
   - On restart, consumers resume from **last committed offsets** (or auto.offset_reset if none).
   - **No broker data loss**, but the group can miss data if it expires before they’re back.

7. ## Explain consumer lag and how to resolve it?

   - **What:** Difference between the log end offset and the group’s **processed/committed** offset.
   - **Causes:** Slow processing, not enough consumers, hot partitions, small fetch/batch sizes, I/O/GC pauses, frequent rebalances.
   - **Fixes:** Scale consumers (up to **N partitions**), **increase partitions** (mind per-key ordering), optimize processing/I/O, increase fetch/batch sizes, tune backpressure, reduce rebalances (sticky assign, session/heartbeat tuning).

8. ## Explain how Kafka tracks message delivery?

   **8) How Kafka tracks delivery**

   - Via **offsets per (topic, partition, group)** committed to __consumer_offsets.
   - Broker **group coordinator** stores/serves these; consumers resume from committed offsets.
   - With **transactions**, Kafka also uses producer IDs/sequence numbers and **transaction markers** for exactly-once semantics.

9. ## Compare Kafka vs RabbitMQ, compare messageing frameworks vs MySql (Why Kafka)?

   - **Kafka:** Partitioned log, very high throughput, durable retention & replay, pull model, ordering **per partition**, great for streaming/event sourcing.
   - **RabbitMQ:** AMQP, push model with per-message acks, flexible routing (exchanges/bindings), great for low-latency work queues/RPC—**not** optimized for large-scale replay.
   - **Why not MySQL as a queue:** DB tables as queues suffer from locks/scans, poor throughput/backpressure, no partitioned log or cheap replay.
   - **Why Kafka:** Decouples producers/consumers, horizontal scale, durable **replay**, backpressure via pull, and strong delivery semantics (at-least/at-most/exactly-once with transactions).
