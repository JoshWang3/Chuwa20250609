# HW14 - Kafka Concepts and Questions

## Kafka Concepts and How They Coordinate

### Topic
A topic is a category or feed name where messages are published. It's like a channel that producers write to and consumers read from. Topics are divided into partitions for scalability and parallel processing.

### Partition
A partition is a subset of a topic. Each partition is an ordered, immutable sequence of messages. Messages within a partition are ordered by their offset. Partitions allow topics to scale beyond what a single server can handle and enable parallel consumption.

### Broker
A broker is a Kafka server that stores and serves messages. Multiple brokers form a Kafka cluster. Each broker can handle thousands of reads and writes per second from producers and consumers. Brokers coordinate with each other to replicate data and ensure fault tolerance.

### Consumer Group
A consumer group is a set of consumers that work together to consume messages from topics. Each message in a topic is delivered to only one consumer within each consumer group. This enables load balancing and fault tolerance among consumers.

### Producer
A producer is a client application that publishes messages to Kafka topics. Producers decide which partition to send messages to, either through custom partitioning logic or using Kafka's default round-robin approach.

### Offset
An offset is a unique identifier for each message within a partition. It's a sequential number that increases with each new message. Consumers track their progress by maintaining their current offset position.

### Zookeeper
Zookeeper is a centralized service used by Kafka for configuration management, leader election, and maintaining metadata about brokers, topics, and partitions. It helps coordinate the Kafka cluster operations.

## Questions and Answers

### 1. Given N (partitions) and M (consumers), what happens when N>=M and N<M?

**When N >= M (partitions >= consumers):**
- Each consumer can be assigned one or more partitions
- Some consumers may handle multiple partitions if N > M
- All partitions are consumed, optimal parallelism within the consumer group

**When N < M (partitions < consumers):**
- Some consumers will be idle (no partitions assigned)
- Only N consumers will be active (one per partition)
- Remaining M-N consumers will sit idle until rebalancing occurs

### 2. How do brokers work with topics?

Brokers store topic data across multiple partitions. Each broker can host multiple partitions from different topics. For fault tolerance, partitions are replicated across multiple brokers with one broker acting as the leader for each partition. The leader handles all reads and writes while followers replicate the data.

### 3. Are messages pushed to consumers or do consumers pull messages?

Consumers **pull** messages from topics. Kafka uses a pull-based model where consumers request messages from brokers at their own pace. This allows consumers to control their consumption rate and handle backpressure effectively.

### 4. How to avoid duplicate consumption of messages?

- Enable idempotent producers to prevent duplicate writes
- Use manual offset commits after successful message processing
- Implement exactly-once semantics with transactional producers
- Use unique message IDs for deduplication at the application level
- Configure proper consumer settings like `enable.auto.commit=false`

### 5. What happens if some consumers are down in a consumer group? Will data loss occur?

When consumers go down, Kafka triggers a **rebalancing** process. The remaining active consumers will be reassigned the partitions from the failed consumers. **No data loss occurs** because:
- Messages remain stored in Kafka brokers
- Offsets are tracked per partition
- Remaining consumers will continue from the last committed offset

### 6. What happens if an entire consumer group is down? Will data loss occur?

If an entire consumer group goes down, **no data loss occurs**. Messages remain stored in Kafka brokers according to the retention policy. When the consumer group comes back online, consumers will resume from their last committed offsets. However, if messages exceed the retention period while consumers are down, those messages will be deleted.

### 7. Explain consumer lag and how to resolve it?

**Consumer lag** is the difference between the latest message offset in a partition and the consumer's current offset. It indicates how far behind the consumer is.

**Resolution strategies:**
- Scale up consumers (add more consumers to the group)
- Optimize consumer processing logic
- Increase consumer fetch size and batch processing
- Monitor and alert on lag metrics
- Consider increasing partition count for better parallelism

### 8. How does Kafka track message delivery?

Kafka tracks message delivery through **offsets**:
- Each message gets a unique offset within its partition
- Consumers commit their current offset after processing messages
- Brokers maintain offset information in an internal topic `__consumer_offsets`
- Different commit strategies: auto-commit, manual commit, or transactional commits

### 9. Compare Kafka vs RabbitMQ, and messaging frameworks vs MySQL

**Kafka vs RabbitMQ:**
- Kafka: High throughput, log-based, pull model, better for streaming
- RabbitMQ: Lower latency, queue-based, push model, better for traditional messaging

**Messaging vs MySQL:**
- **Messaging frameworks** are designed for real-time data streaming, event-driven architectures, and decoupling systems
- **MySQL** is designed for transactional data storage with ACID properties
- Kafka excels at handling high-volume, real-time data streams that would overwhelm traditional databases
- Better scalability and fault tolerance for streaming scenarios
