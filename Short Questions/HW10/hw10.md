## Part 1

Core Stereotype Annotations

1. `@Component` marks a class as a Spring-managed bean
2. `@Service` specialized version of `@Component` for service layer
3. `@Repository` specialized version of `@Component` for data access layer
4. `@Controller` marks a class as a web controller in Spring MVC
5. `@RestController` combines `@Controller` and `@RespsonseBody` for REST APIs

Dependency Injection

1. `@Autowired` automatically injects dependencies
2. `@Value` injects values from properties file

Configuration & Bean Management

1. `@Configuration` declares a class that defines Spring beans
2. `@Bean` declares a method that returns a Spring bean
3. `@PropertySource` loads properties file into the Spring Environment
4. `@ComponentScan` enables component scanning for Spring-managed beans

Spring Boot

1. `@EnableJpaRepositories` enables JPA repositories
2. `@EnableAutoConfiguration` tells Spring Boot to auto-configure the application 
3. `@SpringBootApplication` combines `@Configuration`, `@EnableAutoConfiguration`, and `@ComponentScan`

Persistence (Spring Data JPA)

1. `@Entity` marks a class as a JPA entity
2. `@Id` specifies the primary key
3. `@GeneratedValue` configures auto-generation of primary key
4. `@Table` maps an entity to a specific DB table
5. `@Column` maps a field to a specific DB column
6. `@Query` defines a custom JPQL or native SQL query
7. `@Transcational` defines transaction boundaries
8. `@OneToMany`, `@ManyToOne`, `@ManyToMany`, `@OneToOne` defines relationships between entities.

Web MVC & REST

1. `@RequestMapping` maps HTTP requests to handler methods or classes
2. `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` shorthand for `@RequestMapping` with method
3. `@PathVariable` binds URI template variable to method parameter
4. `@RequestParam` binds query parameter to method parameter
5. `@RequestBody` binds HTTP request body to a method parameter
6. `@ResponseBody` writes return value directly to the HTTP response body

Validation (Spring Validation / Bean Validation)

1. `@Valid`, `@Validated` triggers validation on method or parameter
2. `@NotNull`, `@NotEmpty`, `@Email`, `@Pattern`, `@Size` field-level constraints
3. `@Min`, `@Max` numeric field constraints

Testing

1. `@SpringBootTest` loads full application context for integration tests
2. `@WebMvcTest` loads controller-related beans only
3. `@DataJpaTest` tests repository layer with in-memory DB

## Part 3

1. Spring Data JPA, Hibernate, JDBC, HikariCP
    1. Spring Data JPA simplifies JPA by generating repository code and queries. It’s high-level abstraction that sits on top of JPA (usually backed by Hibernate). (The high-level API means less control, easier and faster development). It can auto-generates repository interfaces using method naming conventions. It supports custom queries through `@Query` and makes CRUD and query logic extremely concise. It also supports ORM (object-relational mapping) via JPA. 
    2. Hibernate is a JPA implementation (ORM = Object-Relational Mapping). It’s mid API level. It maps Java classes to DB tables (using `@Entity`, `@Id`, etc). It can handle dirty checking, lazy loading, caching, and SQL generation. It uses JDBC under the hood to interact with the database. 
    3. JDBC is low-level API with `Connection`, `Statement`, `ResultSet`, etc. It’s more control and more work. It requires manual SQL, error handling, and resource management. We need to work with raw SQL and data types - no object-relational mapping. 
    4. HikariCP is a high-performance JDBC connection pool. It’s used by spring boot as the default connection pool. It manages a pool of database connection for reuse which improves performance. It integrates under the hood with hibernate/JDBC. 
2. Entity relationships define how classes (tables) are connected.
    1. `@OneToMany` means one entity has many related entities.
        
        Configuration:
        
        - `mappedBy` refers to the field in the child entity that owns the relationship
        - `cascade` defines what operations should cascade.
        - `fetch` there are two types - lazy (default): fetch when accessed; eager: fetch immediately.
    2. `@ManyToOne` means many entities belong to one parent.
        
        Configuration:
        
        - `fetch` there are two types - lazy: fetch when accessed; eager (default): fetch immediately.
        - `@JoinColumn` specifies the foreign key column name in DB
    3. `@ManyToMany` means many entities of type A are related to many entities of type B
        
        Configuration:
        
        - `@JoinTable` specifies the join table name and foreign key columns
        - `mappedBy` is used on the inverse side to refer to the owning side’s field.
        - `cascade` defines what operations should cascade.
        - `fetch` lazy by default
    
    7. The `cascade` attribute in JPA defines which operations performed on a parent entity should be automatically applied to its related entities. 
    
    `orphanRemoval = true` automatically deletes child entities removed from the collection. Without it, removing from the list will only remove it from memory - not from the database. It will be used when the child should be deleted if it’s no longer part of the parent. 
    
    CascadeType Options:
    
    - Persist - when you save the parent (entityManager.persist()), the child is saved too
    - Merge - when you merge (update) the parent, the child is also merged
    - Remove - deleting the parent will delete the child as well
    - Detach - detaching the parent from the persistence context also detaches the child
    - Refresh - refreshing the parent from DB will also refresh the child
    - All - shortcut for applying all of the above
    1. `fetch` there are two types - lazy (default): fetch when accessed; eager: fetch immediately.

## Part 4

1. JPQL vs SQL
    1. JPQL (Java Persistence Query Language) is an object-oriented query language to query entities, not tables. It’s used in JPA and uses entity relationships.
        1. It looks similar to SQL but operates on Java classes and properties rather than database tables and columns.
        2. JPQL is interpreted by the JPA provider (e.g., Hibernate) and then translated into native SQL
        
        ```java
        @Entity
        public class Post {
            @Id
            private Long id;
        
            private String title;
        
            @ManyToOne
            private User author;
        }
        ```
        
        ```java
        @Query("SELECT p FROM Post p WHERE p.title LIKE %:keyword%")
        List<Post> searchPosts(@Param("keyword") String keyword);
        ```
        
        Also, it can be used with `EntityManager.createQuery()`:
        
        ```java
        public List<Post> getAllPostWithJPQL() {
                TypedQuery<Post> posts = entityManager.createNamedQuery("Post.getAll", Post.class);
                return posts.getResultList();
            }
        ```
        
    2. SQL is used in DB tools, JDBC, native queries. It must use JOINs on foreign keys. 
2. The `@Query` allows us to write custom queries (either JPQL or native SQL) instead of relying on method name conventions. It’s used in repository layer to define custom JPQL queries and native SQL queries. 
    1. JPQL with `@Query`: JPQL works with entity names and field names (not table/column names).
        
        ```java
            @Query("select p from Post p where p.id = :key and LOWER(p.content) LIKE LOWER(CONCAT('%', :content, '%'))")
            Post getPostByIDAndContentWithJPQLNamedParameters(@Param("key") Long id,
                                                              @Param("content") String content);
        ```
        
    2. Native SQL with `@Query (nativeQuery = true)`: It’s good for SQL functions specific to a database. It’s raw control over the query. It can direct access to table/column names.
        
        ```java
            @Query(value = "select * from posts p where p.id = ?1 and LOWER(p.content) LIKE LOWER(CONCAT('%', ?2, '%'))", nativeQuery = true)
            Post getPostByIDAndContentWithSQLIndexParameters(Long id, String content);
        ```
        

## Part 5

1. `EntityManager` is part of JPA while `SessionFactory` is part of Hibernate. `EntityManager` abstracts provider details while `SessionFactory` is hibernate-specific operations exposed. `EntityManager` is not thread-safe while `SessionFactory` is thread-safe. `EntitiyManager` is portable while `SessionFactory` is hibernate-specific and not portable.
    
    `EntityManager`
    
    ```java
        @PersistenceContext
        EntityManager entityManager;
    
        @Override
        public List<Post> getAllPostWithJPQL() {
            TypedQuery<Post> posts = entityManager.createNamedQuery("Post.getAll", Post.class);
            return posts.getResultList();
        }
    ```
    
    `SessionFactory`
    
    ```java
    Session session = sessionFactory.openSession();
    Post post = session.get(Post.class, 1L);
    session.save(post);
    ```
    
2. Session is the main interface for performing CRUD operations on the DB. Session is lightweight, per-transaction object used to do all actual DB operations (not thread-safe). SessionFactory is a factory for creating Session instances. It’s a heavy, app-wide object used to create sessions (thread-safe).

## Part 6

1. In relational DB, a transaction is a sequence of one or more SQL operations that are treated as a single logical unit of work. 
    1. **A**tomicity - All operations in a transaction succeed or all fail. No partial changes.
    2. **C**onsistency - Transaction must leave the database in a valid state.
    3. **I**solation - Concurrent transactions should not interfere with each other.
    4. **D**urability - Once committed, changes persist even after system failure.
    
    Spring provides declarative transaction management using the `@Transactional` annotation.
    
    ```java
    @Service
    public class BankService {
    
        @Transactional
        public void transfer(Long fromId, Long toId, double amount) {
            Account from = accountRepository.findById(fromId).orElseThrow();
            Account to = accountRepository.findById(toId).orElseThrow();
    
            from.setBalance(from.getBalance() - amount);
            to.setBalance(to.getBalance() + amount);
        }
    }
     
    ```
    
2. Hibernate uses caching to improve performance by reducing the number of direct database hits during entity retrieval and manipulation. 
    1. First-level cache (session scope)
        1. It’s built-in and enabled by default
        2. it’s tied to the hibernate Session object
        3. Each session has its own cache (not shared across sessions)
        4. It stores entities that have been retrieved or saved during that session.
        
        ```java
        Session session = sessionFactory.openSession();
        Post post1 = session.get(Post.class, 1L); // Hits DB
        Post post2 = session.get(Post.class, 1L); // Retrieved from cache, no DB hit
        ```
        
    2. Second-level cache (sessionFactory scope)
        1. It’s optional. It must be explicitly configured.
        2. It is shared across multiple sessions using the same SessionFactory
        3. It caches entities or collections beyond the lifespan of a single session.
