3. In Spring, we use model mappers to convert between different object models, typically between entity and DTO (Data Transfer Object).
    
    Why do we need:
    
    1. Separation of concerns
        - Entities represent your database schema.
        - DTOs represent how data is sent over the network (API).
        - Mixing the two creates tight coupling between persistence and web layers.
        
        Use mappers to decouple layers and keep the app maintainable. 
        
    2. Avoid exposing sensitive/internal fields
        - Entities may contain sensitive data (like passwords. internal IDs).
        - The information we don’t want to expose in an API response.
        
        Use mappers to filter or reshape data before sending it to clients. 
        
    3. Control API payloads
        - APIs may require different structures from what the database has.
        - For example, we may combine multiple entities into one DTO for response.
        
        Mappers help customize the shape of the API response or request payload. 
        
    4. Avoid boilerplate code
        - Manual mapping is repetitive and error-prone.
        
        ModelMapper or MapStruct can do this automatically.
        
    
    Common Use Cases (based on above reasons)
    
    1. Convert among controller, service, entity
    2. Use DTO filters
    3. Custom response/request structures
    4. Reuse across app layers
4. Examples:
    1. Field names don’t match.
        
        DTO and entity have different field names.
        
        ```java
        public class User {
            private String firstName;
            private String lastName;
        }
        ```
        
        ```java
        public class UserDto {
            private String givenName;
            private String familyName;
        }
        ```
        
        ModelMapper uses reflection and naming conventions to auto-map fields. Since `firstName` ≠ `givenName`, it won’t map anything unless explicitly configured. 
        
        ```java
        modelMapper.typeMap(User.class, UserDto.class).addMappings(mapper -> {
            mapper.map(User::getFirstName, UserDto::setGivenName);
            mapper.map(User::getLastName, UserDto::setFamilyName);
        });
        
        ```
        
    2. Nested objects aren’t mapped automatically.
        
        Entity has a nested object; DTO flattens the structure.
        
        ```java
        public class User {
            private Address address;
        }
        public class Address {
            private String city;
        }
        ```
        
        ```java
        public class UserDto {
            private String city;
        }
        ```
        
        ModelMapper doesn’t flatten nested objects by default - it can’t infer that [`user.address.city`](http://user.address.city) maps to `userDto.city`.
        
        ```java
        modelMapper.typeMap(User.class, UserDto.class).addMappings(mapper -> {
            mapper.map(src -> src.getAddress().getCity(), UserDto::setCity);
        });
        ```
        
    3. Complex collections or custom conversions.
        
        Entity contains a list of complex objects; DTO expects transformed data.
        
        ```java
        public class User {
            private List<Role> roles;
        }
        public class Role {
            private String name;
        }
        ```
        
        ```java
        public class UserDto {
            private List<String> roleNames;
        }
        ```
        
        ModelMapper can’t infer how to convert `List<Role>` → `List<String>`.
        
        ```java
        Converter<List<Role>, List<String>> roleConverter = ctx -> 
            ctx.getSource().stream().map(Role::getName).collect(Collectors.toList());
        
        modelMapper.typeMap(User.class, UserDto.class).addMappings(mapper -> {
            mapper.using(roleConverter).map(User::getRoles, UserDto::setRoleNames);
        });
        ```
        
5. ModelMapper can handle some type conversions, but not all - and it depends on whether the types are compatible or need custom converters. 
    
    ModelMapper uses Java reflection and has built-in type converters for basic types. Types that can automatically cast are int → Integer, Integer → String, String → Integer, Date → String. As for String → Date, it can cast only if parsable by default format. 
    
    Use a custom converter
    
    ```java
    Converter<BigDecimal, Double> bigDecimalToDouble = ctx -> 
        ctx.getSource() == null ? null : ctx.getSource().doubleValue();
    
    modelMapper.addConverter(bigDecimalToDouble);
    ```
    
    Use TypeMap to register it for a specific mapping
    
    ```java
    modelMapper.typeMap(Source.class, Target.class).addMappings(mapper -> {
        mapper.using(bigDecimalToDouble).map(Source::getAmount, Target::setAmount);
    });
    ```
    
    Fails when types are complex or not directly convertible. For example, BigDecimal → Double, Enum → String, String → UUID, LocalDate, etc.

7. `@ControllerAdvices` is a specialized component used for global exception handling, binding enhancements, and global model attributes - especially for REST APIs. It can be regarded as `catch{}` block for the Spring controller. 
    
    Use Case: Global Exception Handling
    
    It works together with `@ExceptionHandler` to catch and process exceptions throw from any `@RestController` or `@Controller`.
    
    Alternative approaches: 
    
    1. Pre-controller exception handling.
        
        ```java
        @RestController
        public class PostController {
        
            @ExceptionHandler(ResourceNotFoundException.class)
            public ResponseEntity<ErrorResponse> handleLocal(ResourceNotFoundException ex) {
                return new ResponseEntity<>(..., HttpStatus.NOT_FOUND);
            }
        }
        
        ```
        
    2. Custom HandlerInterceptor
        
        ```java
        public class GlobalInterceptor extends HandlerInterceptorAdapter {
            @Override
            public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
                // Custom logic
            }
        }
        
        ```
        
    3. `@RepsonseStatus` on Custom Exception.
    
    `@ControllerAdvice` can be reusable, centralized, custom response body, and good for REST APIs, but other options not. It separates error-handling logic from business logic.

10. Principles:
    1. Dependency Injection (DI) / Inversion of Control (IoC)
        
        Objects don’t create their dependencies, instead, dependencies are injected by the framework at runtime. It’s good for loosing coupling and testabilities and maintainability. 
        
        Business application: reuse and easily replace business logic, like switch from PayPal to Stripe.
        
    2. Aspect - oriented Programming (AOP)
        
        Separates cross-cutting concerns (logging, security, transactions) from business logic using aspect. It’s good for clean and focused business code. It’s reusable infrastructure logic. 
        
        Apply logging security and audit trails consistently across services.
        
    3. Modularity and Component-based design
        
        Spring allows to break the application into reusable modules (controllers, services, repositories, etc). It enhances separation of concerns (SoC) and encourages a layered architecture.
        
    4. Convention over Configuration
        
        Spring boot provides sensible defaults to minimize boilerplate configuration. It makes it faster development and less configuration needed. 
        
    5. Declarative programming via Annotations
        
        Spring uses annotation to declare behavior. It’s good for clean and readable code and reducing XML configuration. 
        
    6. Testability and mocking
        
        Spring components are loosely coupled and injected, making them easy to mock in unit tests. It facilitates unit testing and integration testing. It works well with JUnit and Mockito. 
        
    7. Support for multiple architectures
        
        Spring is not tied to a specific architecture. It supports microservices (via Spring boot + spring cloud), event-driven apps, serverless function. 
        
11. 3 types:
    1. Constructor injection with `@Autowired` with 1 constructor (required)
        
        ```java
        @Component
        public class OrderService {
            private final PaymentService paymentService;
        
            @Autowired  // Optional if there's only one constructor
            public OrderService(PaymentService paymentService) {
                this.paymentService = paymentService;
            }
        }
        
        ```
        
    2. Setter Injection `@Autowired` on setters (optional)
        
        ```java
        @Component
        public class OrderService {
        
            private PaymentService paymentService;
        
            @Autowired
            public void setPaymentService(PaymentService paymentService) {
                this.paymentService = paymentService;
            }
        }
        
        ```
        
    3. Field injection `@Autowired` on the field (not recommended).
        
        ```java
            @Autowired
            private PostService postService;
        ```

13. Component is used on a class while bean is used on a method inside `@Configuration` class. Component is annotation-based scanning while bean is explicit declaration. 
    
    Component - write the class and want Spring to manage it. keep everything auto-wired and annotation-based
    
    Bean - need to register a 3rd-party class (e.g., `ObjectMapper`, `RestTemplate`, `PasswordEncoder`), **custom logic** or parameters when constructing the bean, configuring external libraries or setting up manual wiring.
    
14. scope: singleton - Only **one instance** of the bean is created for the Spring container; prototype - A **new instance** is created **each time** the bean is requested; request - One bean instance **per HTTP request** (web only); session - One bean instance **per HTTP session** (web only); application - One instance **per ServletContext** (web only); websocket - One instance per WebSocket session (web only)
15. Bean id is a unique name or id used for reference a bean inside the Spring container. We can retrieve a specific bean instance via name. Bean class - the actual type of the object being instantiated. Spring needs to know which class to instantiate to create the bean. Id is String while class is fully qualified class name. Class is required while id is optional (auto-generated if missing).
