TLS (Transport Layer Security): TLS is a cryptographic protocol that secures communication over networks by encrypting data between a client and server. It ensures confidentiality, integrity, and authentication.

PKI (Public Key Infrastructure): PKI is a system that manages digital certificates and public-private key pairs. It enables secure data exchange and user authentication using trusted certificate authorities (CAs).

Certificate: A certificate is a digital document issued by a CA that binds a public key to an entity's identity. It includes the public key, entity info, and the CA’s signature.

Public Key: The public key is used to encrypt data or verify digital signatures. It is shared openly and works in tandem with the private key.

Private Key: The private key is kept secret and is used to decrypt data or create digital signatures. It must be securely stored by the owner.

Signature: A digital signature is a cryptographic value generated using a private key to prove authenticity and integrity. It can be verified using the corresponding public key.

10. To maintain user information across multiple HTTP requests in a stateless HTTP protocol, web applications commonly use sessions and cookies together.

When a user successfully logs in, the server creates a session, which stores user-related data (such as user ID or roles) on the server-side. It then generates a unique session ID and sends it to the client in a Set-Cookie header. This session ID is stored in the browser as a cookie.

For every subsequent request, the browser automatically includes the session ID in the Cookie header. The server uses this session ID to retrieve the associated user data from the session storage, thereby preserving the user's state across requests.

This mechanism allows the application to recognize the user without requiring re-authentication on each request. The session is typically invalidated on logout or after a timeout period. In summary, cookies store the session ID on the client-side, and the server uses it to manage session data securely.

12. Bearer Token:
    A bearer token is an access token sent in the Authorization header of HTTP requests using the format:
    Authorization: Bearer <token>.
    Whoever holds the token ("bearer") is granted access, without re-authentication.

How JWT Works:

Structure: JWT = Header + Payload + Signature (encoded in Base64).

Process:

After successful login, the server issues a JWT signed with a secret/private key.

Client stores the token (typically in localStorage or cookies).

On each request, the client includes the token in the Authorization header.

The server verifies the signature and extracts user identity and claims from the payload.

Stateless: No session stored on server; verification is done purely through signature.

Key Benefit: Lightweight, stateless, and scalable for REST APIs.

13. Passwords: Use strong hashing (e.g., BCrypt) with salt; never store plain text.

Retrievable Data (e.g., credit cards): Encrypt using AES; protect keys securely.

Minimize Exposure: Store only necessary data; mask when possible.

Access Control: Enforce strict read/write permissions.

Transmission: Always use HTTPS.

14. UserDetailsService:
Loads user-specific data by username (e.g., from DB).
Returns a UserDetails object.
Used by AuthenticationProvider.

AuthenticationProvider:
Performs actual authentication logic (e.g., password check).
Uses UserDetailsService to fetch user data.
Returns an Authentication object if successful.

AuthenticationManager:
Entry point for authentication.
Delegates to one or more AuthenticationProviders.
Returns authenticated Authentication object.

AuthenticationFilter:
Intercepts HTTP requests before reaching controllers.
Extracts credentials (e.g., username/password or token).
Calls AuthenticationManager to authenticate.

15. Scalability Issue: Session data is stored in server memory, making it hard to scale across multiple servers (e.g., in load-balanced environments).

Solution: Use stateless authentication methods like JWT (JSON Web Tokens) or store session data in a distributed cache (e.g., Redis) for shared access.
