**1. Explain monolithic architecture, service oriented architecture and Micro service architecture.**

- **Monolithic Architecture** 
  - Put everything (code) together, as a whole
  - Single codebase: UI, logic, DB access all in one
  - One deployment unit

- **Service Oriented Architecture**
  - Modular components connected via API (mostly SOAP + XML)
  - Commonly uses **Enterprise Service Bus(ESB)**
  - Services are **loosely coupled** but often share databases
  - More suitable for **enterprise system** and **legacy integration**

- **Microservice Architecture**
  - Multi-services: Each function (e.g., auth, product, payment) is its own service
  - Independently deployable: Each service can be updated or restarted on its own
  - Single responsibility: Each service handles a focused business function
  - Language/tech-stack freedom: One service can be in Java, another in Python
  - Own database per service: Avoids tight coupling
  - Communicate via lightweight protocols: REST, gRPC, message queues (e.g., Kafka)
  - Scalable: Scale services independently based on load
  - Fault isolation: Failure in one service doesn’t bring down the whole system
  - DevOps required: Needs strong CI/CD, monitoring, and orchestration (e.g., Docker, Kubernetes)

**2. Document the microservice architeture and core components**

Microservice Architecture is a design pattern where an application is structured as a collection of small, loosely coupled, independently deployable services, each focused on a single business capability.

- Each microservice:
  - Has its own codebase
  - Owns its own database
  - Is independently deployable
  - Communicates via lightweight protocols

- Core component:
  - **API Gateway** – Central entry point; routes client requests to services
  - **Service Discovery** – Keeps track of available services (e.g., Consul, Eureka)
  - **Microservices** – Independent, single-responsibility services
  - **Database per Service** – Each service manages its own data
  - **Inter-Service Communication** – REST, gRPC, or message queues (Kafka, RabbitMQ)
  - **CI/CD Pipeline** – Automates build, test, deploy
  - **Monitoring & Logging** – Tools like Prometheus, ELK, Grafana
  - **Containerization & Orchestration** – Docker + Kubernetes for scaling and deployment
  - **Security & Resilience** – JWT/OAuth, circuit breakers, retries

**3. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.**

- Resilience pattern
  - Retry: Re-attempt failed calls
  - Circuit Breaker: Stop calling a failing service temporarily
  - Fallback: Return default response on failure
  - Bulkhead: Isolate failures to prevent system-wide crash
  - Timeout: Limit wait time for responses
  - Rate Limiter: Control request flow

- A Circuit Breaker prevents a service from making calls to another service that is likely to fail.
- If too many failures happen, the circuit "opens" — future calls fail fast or go to a fallback.
- After a timeout, it half-opens to test if the service has recovered.
- If successful, the circuit closes again.
- This protects systems from cascading failures.

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-netflix-hystrix</artifactId>
</dependency>
```
```java
@Service
public class UserService {
    private final RestTemplate restTemplate = new RestTemplate();

    @HystrixCommand(fallbackMethod = "getUserFallback")
    public String getUserById(String id) {
        return restTemplate.getForObject("http://external/api/users/" + id, String.class);
    }

    public String getUserFallback(String id) {
        return "Fallback: Service unavailable";
    }
}
```

**4. Explain load balancing algorithms.**

Load balancing algorithms determine how traffic is distributed across multiple servers to ensure high availability, performance, and fault tolerance.

- Round Robin: Sends requests in order (A → B → C → A...)
- Least Connections: Chooses server with fewest active connections
- IP Hash: Same client IP always goes to the same server
- Weighted Round Robin: Like Round Robin, but stronger servers get more requests
- Random: Picks a server at random
- Consistent Hashing: Minimizes re-routing when servers are added/removed

**5. Explain API Gateway.**
An API Gateway is the single entry point for all client requests in a microservices architecture.
- Functions:
  - Routes requests to appropriate microservices
  - Handles authentication, rate limiting, logging, and response aggregation
  - Example: Netflix Zuul, Spring Cloud Gateway, Kong

---

**6. Explain service discovery and service registry**
- Service Registry: A database of available microservice instances (name, IP, port)
  - Example: Eureka Server
- Service Discovery: The process of locating a service in the registry
  - Clients or gateways query the registry to find service locations dynamically

**7. List Spring Cloud Modules that serve as Microservice components (e.g. Euerka for Service Discovery)**

Spring Cloud provides a suite of tools to support building distributed microservices. Each module addresses a specific need:

- Eureka – Service Registry for Service Discovery
- Spring Cloud Gateway – API Gateway for routing and filtering requests
- Config Server – Centralized external configuration management
- Resilience4j – Circuit breaker and fault tolerance
- Spring Cloud LoadBalancer – Client-side load balancing
- Spring Cloud Stream – Messaging with Kafka or RabbitMQ
- Sleuth + Zipkin – Distributed tracing for monitoring service calls
