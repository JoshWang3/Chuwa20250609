### 5. Technology Comparison 

##### Explain the differences and relationships among:  
Spring Data JPA:  Spring Data JPA is a Spring Data module built on the JPA (Java Persistence API) specification; by extending interfaces like JpaRepository, it minimizes boilerplate code for common CRUD operations and query method generation.  

Hibernate: Hibernate is a widely used Java ORM (Object-Relational Mapping) framework—and a leading JPA provider—that maps Java objects to relational database tables and handles SQL generation, entity state management, caching, and transaction demarcation.     

HikariCP: HikariCP is a high-performance **JDBC connection pool implementation** focused on low latency and minimal resource usage.    

JDBC: JDBC (Java Database Connectivity) is the low-level **database access API** in the Java standard library, defining interfaces for **connecting to databases, executing SQL statements, and processing ResultSet objects**.


##### Bottom-to-Top Layer Structure
1. HikariCP (Connection Pool Layer)

Manages database connections, maintains connection pool
Provides connections to upper layers

2. JDBC (Database Access Layer)

Uses connections provided by HikariCP
Executes raw SQL statements, handles result sets

3. Hibernate (ORM Layer)

Built on top of JDBC
Maps objects to SQL, maps result sets to objects
Manages entity lifecycle, caching, transactions

4. Spring Data JPA (Repository Abstraction Layer)

Based on JPA specification (Hibernate implementation)
Provides Repository interfaces, auto-implements CRUD methods
Offers advanced features like @Query

##### Inter-Layer Collaboration Flow:  
Request Flow: Repository method → JPA implementation (Hibernate) → Generate SQL → JDBC execution → HikariCP provides connection → Database  
Response Flow: Database result → JDBC result set → Hibernate object mapping → JPA returns entity → Repository returns result  


Essence: Each layer focuses on its responsibility, upper layers depend on lower layer services.

### 6. JPA Relationships
Explain the following annotations with examples: @OneToMany, @ManyToOne, @ManyToMany   
Also describe and explain the configuration properties inside each, such as mappedBy, cascade, and fetch.  

##### @OneToMany:  One entity corresponds to multiple child entities, typically defined as a collection in the parent entity, using mappedBy to point to the foreign key field in the child entity.    
```java
@Entity
public class User {
    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    private List<Order> orders;
}
```

##### @ManyToOne:  Multiple entities correspond to one parent entity, defined as a parent entity reference in the child entity, using @JoinColumn to specify the foreign key column name.  
```java
@Entity
public class Order {
    @ManyToOne(fetch = FetchType.EAGER)
    @JoinColumn(name = "user_id")
    private User user;
}
```

##### @ManyToMany：Multiple entities correspond to each other, requires an intermediate join table, using @JoinTable to configure the join table and foreign key columns.  
One entity can be associated with multiple instances of another entity, and vice versa (M:N relationship, not multiple 1:1 relationships).


```java
@Entity
public class Student {
    @ManyToMany(cascade = CascadeType.PERSIST, fetch = FetchType.LAZY)
    @JoinTable(name = "student_course",
               joinColumns = @JoinColumn(name = "student_id"),
               inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses;
}
```

##### Configuration Properties
mappedBy: Specifies the owning side of the relationship, avoids creating extra join tables  
Used on the non-owning side of @OneToMany and @ManyToMany  

cascade: Cascade operations  

CascadeType.ALL - All operations cascade  
CascadeType.PERSIST - Cascade on save  
CascadeType.REMOVE - Cascade on delete  

fetch: Loading strategy
FetchType.LAZY - Lazy loading (default for collections)
FetchType.EAGER - Immediate loading

Key Rule: @ManyToOne defaults to EAGER, @OneToMany and @ManyToMany default to LAZY.


### 7. Cascade Options in JPA [ref](https://www.geeksforgeeks.org/advance-java/hibernate-different-cascade-types/)  
##### Explain cascade = CascadeType.ALL and orphanRemoval = true. 


##### Also describe all other CascadeType values: PERSIST MERGE REMOVE DETACH REFRESH  

CascadeType.ALL: The ALL cascade type can propagate all operations, like the PERSIST, MERGE, REMOVE, REFRESH, and DETACH to the child entities of the JPA application.
CascadeType.PERSIST: The PERSIST cascade type can propagate the persist operations when the parent entity is persisted and the operation cascades to the child entities.
CascadeType.MERGE: The MERGE cascade type can propagate the merge operation and its parent entity is merged the operation cascades to its child entities of the JPA application.
CascadeType.REMOVE: The REMOVE cascade type can propagate the remove operation when the parent entity is removed then the operation cascades to its the child entities of JPA application.
CascadeType.REFRESH: The REFRESH cascade type can propagates the refresh operation when the parent entity is refreshed when the operation cascades to its the child entities of the JPA application.
CascadeType.DETACH: The detach operation removes the entity from the persistent context. When we use CascadeType.DETACH, the child entity will also get removed from the persistent context.


### 8. Fetch Types in JPA  
Explain FetchType.LAZY and FetchType.EAGER, and describe when to use each.  

FetchType.LAZY: Associated data is fetched from the database only when you first access the property.  
When to Use: 
- For large or infrequently accessed associations to avoid loading heavy object graphs up front.  
- Common for collections and many-to-many relations.
```java
@OneToMany(fetch = FetchType.LAZY, mappedBy = "user")
private List<Order> orders;
```

FetchType.EAGER: Associated data is fetched immediately along with the parent entity.  
When to Use: for mandatory many-to-one or one-to-one relations (e.g., every Order must include its User).
```java
@ManyToOne(fetch = FetchType.EAGER)
@JoinColumn(name = "user_id")
private User user;
```


### 9. JPQL Overview   
Explain what JPQL is and how it differs from SQL. Include examples.  

- Definition of JPQL: JPQL (Java Persistence Query Language) is the object-oriented query language defined by the JPA specification. It lets you query over your entity model (classes and their fields) rather than directly on database tables and columns.

- JPQL vs SQL:  
JPQL operates on Java application **entities and their attributes**, constructing queries in an object-oriented way;   
whereas SQL operates directly on **database tables and columns**, following the relational model.
  In other words, in JPQL query conditions and projections you use the **Java object’s field (or method) names**, whereas in SQL you use the **table and column names defined in the database schema**.

```java
List<User> users = em.createQuery(
    "SELECT u FROM User u WHERE u.name = :name", User.class)
    .setParameter("name", "Alice")
    .getResultList();
```

### 10. Using the @Query Annotation    
Explain what the @Query annotation does, where it is used, and how to use it for both JPQL and native
queries.  

- Definition of @Query annotation: @Query is a Spring Data JPA annotation you place on a repository method to explicitly declare the query that will be executed **when that method is called**.   
- Work Flow: 
  - Spring Data parses the method signature and sees @Query.
  - It creates either a JPA Query (for JPQL) or NativeQuery (for SQL) under the covers.(nativeQuery: set to true to indicate the query string is native SQL rather than JPQL)   
  - It binds method parameters—by name (using :param) or position (using ?1, ?2)—to the query.
  - When the repository method is invoked, Spring Data executes the query and maps the results to the method’s return type.


- Where to use: Place @Query on methods in interfaces extending JpaRepository (or CrudRepository/PagingAndSortingRepository).  
- How to use it for JPQL:    
```java
    @Query("SELECT u FROM User u WHERE u.status = :status")
    List<User> findByStatus(@Param("status") UserStatus status);
```

- How to use it for native queries:  
```java
@Query(value = "SELECT email FROM users WHERE active = true", 
       nativeQuery = true)
List<UserProjection> findActiveEmail();
```


### 11. EntityManager vs SessionFactory  
Compare EntityManager and SessionFactory.  
Include screenshots from the codebase to illustrate their relationship.  

EntityManager: An EntityManager is the JPA-standard runtime interface tied to a single persistence context for **managing entity lifecycles** (and is not thread-safe).    

SessionFactory: SessionFactory is Hibernate’s native, application-scoped, **thread-safe factory** responsible for creating and configuring multiple **Session instances** (Hibernate’s persistence contexts).  

EntityManager VS SessionFactory:  
- Standard: EntityManager is the JPA-standard interface; SessionFactory is Hibernate’s native factory.

- Thread Safety: EntityManager is not thread-safe and lives within a single transaction or request; SessionFactory is thread-safe and an application-scoped singleton.

- Scope: EntityManager is tied to one persistence context (first-level cache); SessionFactory holds application-wide metadata, connection pooling, and second-level cache.

- Responsibilities: EntityManager manages entity lifecycle, first-level cache, and JPQL/Criteria/native queries; SessionFactory bootstraps mappings, cache configuration, and produces Session instances.

Lifecycle: EntityManager is created and closed with each transaction/request; SessionFactory is initialized at application startup and closed at shutdown.
### 12. SessionFactory vs Session    
Explain the role of Session and how it differs from SessionFactory.  
- Role of Session: A Session is Hibernate’s **unit of work**, **managing entity state and first-level cache** while performing CRUD operations within a single database conversation.

- Session vs SessionFactory:  
  SessionFactory is Hibernate’s thread-safe, application-scoped factory—bootstrapping metadata, connection pooling, and second-level cache, and producing Session instances;   
  Session is the non-thread-safe unit of work representing a single database conversation, managing entity state, first-level cache, and CRUD operations within a transaction.  
  A SessionFactory is Hibernate’s configuration and factory—loading mapping metadata, managing the connection pool and second-level cache—and it produces Session instances; each Session is created by the SessionFactory and uses its configuration and resources for a single database conversation.  


### 13. SQL Transactions    
Explain what a transaction is in the context of relational databases, and how Spring/Hibernate
manage transactions.  

- Definition of transaction(in the context of relational databases): A transaction is a series of operations in a relational database treated as a single logical unit that either all commit or all roll back, ensuring atomicity, consistency, isolation, and durability (ACID).    

- how Spring/Hibernate manage transactions:  
  Spring intercepts @Transactional methods via AOP and delegates to a PlatformTransactionManager (e.g. HibernateTransactionManager/JpaTransactionManager), which binds a Hibernate Session to the current thread, calls session.getTransaction().begin() at method entry, and commit() or rollback() on exit; Hibernate’s Transaction API then manipulates the underlying JDBC Connection’s auto-commit to enforce the actual transaction boundaries.


### 14. Hibernate Caching 

Explain Hibernate’s caching mechanisms. Compare.  


- First-Level Cache (session scope): Hibernate’s first-level cache is a mandatory, session-scoped cache. Within a given Session, it keeps a map of entity instances by their identifiers, ensuring identity guarantee (each entity is loaded only once per session) and avoiding duplicate selects. Changes to these cached entities are flushed to the database upon transaction commit or an explicit flush().    


- Second-Level Cache (shared/global scope)  
  Second-level cache is an optional, SessionFactory-scoped global cache enabled via hibernate.cache.use_second_level_cache=true and managed by a cache provider (e.g., Ehcache, Infinispan). Entities or collections annotated with @Cache(region="…", usage=…) are stored in named regions and shared across Sessions, significantly reducing database hits across multiple sessions.

First-Level Cache VS Second-Level Cache:  
The first-level cache is a **mandatory**, session-scoped cache that ensures identity within a single Session and prevents duplicate selects;
the second-level cache is an **optional**, SessionFactory-scoped cache shared across sessions to reduce database hits in read-heavy scenarios.
