## 3. Explain why do we need model mappers in Spring, and in what scenarios we need it.

**Why we need model mappers:**
- Convert between Entity objects and DTOs
- Maintain separation between database layer and API layer
- Avoid exposing internal database structure to clients

**Scenarios:**
1. **Entity to DTO** - Converting database entities to API response objects
2. **DTO to Entity** - Converting API request objects to database entities
3. **Security** - Hiding sensitive fields from API responses
4. **API versioning** - Supporting different response formats
5. **Complex transformations** - Flattening nested objects or aggregating data

## 4. Provide 3 examples in which model mapper will NOT map successfully, explain why.

### Example 1: Field name mismatch with calculations
```java
// Source
class User { String firstName; String lastName; }
// Target  
class UserDto { String fullName; } // Needs firstName + lastName
```
**Why it fails:** ModelMapper can't automatically concatenate fields.

### Example 2: Circular references
```java
// Source
class User { List<Post> posts; }
class Post { User author; }
```
**Why it fails:** Creates infinite recursion, causing StackOverflowError.

### Example 3: Collection type mismatch
```java
// Source
class Product { Map<String, Object> attributes; }
// Target
class ProductDto { List<String> attributes; }
```
**Why it fails:** Can't convert Map to List automatically, different generic types.

## 5. Explain how model mapper cast different data types between source object and target class.

**Built-in conversions:**
- **Primitives:** int ↔ long ↔ double ↔ String
- **Strings:** "123" → Integer, "true" → Boolean
- **Dates:** Date ↔ String ↔ LocalDateTime

**Conversion process:**
1. **Exact match** - No conversion needed
2. **Built-in converters** - Automatic primitive/wrapper conversions
3. **Custom converters** - User-defined conversion logic
4. **Type casting** - When compatible types exist

**Custom converter example:**
```java
ModelMapper mapper = new ModelMapper();
Converter<String, LocalDate> converter = 
    ctx -> LocalDate.parse(ctx.getSource());
mapper.addConverter(converter);
```

**Failure handling:** Throws ConversionException for incompatible types.

## 7. Explain how Controller Advices work, is there any other approach to do same/similar global API exception handling?

**How Controller Advice works:**
- `@ControllerAdvice` creates a global exception handler across all controllers
- Uses `@ExceptionHandler` methods to catch specific exception types
- Intercepts exceptions thrown from any controller method
- Returns consistent error responses with proper HTTP status codes

**Process:**
1. Controller throws exception
2. Spring searches for matching `@ExceptionHandler` method
3. Controller Advice processes the exception
4. Returns customized error response

**Alternative approaches:**
1. **HandlerExceptionResolver** - Lower-level exception handling interface
2. **@ExceptionHandler in individual controllers** - Controller-specific handling
3. **ResponseEntityExceptionHandler** - Pre-built exception handler for common Spring exceptions
4. **Custom Filter** - Handle exceptions at filter level before reaching controllers

## 8. What's the difference between throwing a regular exception and a customized API exception that will be eventually thrown to Controller Advice codes?

**Regular Exception:**
- Generic `Exception`, `RuntimeException`, etc.
- No specific HTTP status code
- Generic error message
- Hard to identify error type
- Controller Advice needs to guess appropriate response

**Customized API Exception:**
- Specific exception types (`ValidationException`, `UnauthorizedException`)
- Pre-defined HTTP status codes (`@ResponseStatus`)
- Meaningful error messages
- Clear error categorization
- Controller Advice knows exactly how to handle each type

**Example:**
```java
// Regular exception
throw new Exception("Something went wrong");  // Generic, unclear

// Customized API exception
throw new ValidationException("Email format is invalid");  // Specific, clear
```

**Benefits of customized exceptions:**
- Better error categorization
- Consistent HTTP status codes
- More informative error messages
- Easier debugging and monitoring
- Clear API contract with clients

## 10. Explain Spring framework fundamental principles. And how can they help build business applications?

**Spring Framework Fundamental Principles:**

1. **Inversion of Control (IoC)** - Framework manages object creation and dependencies
2. **Dependency Injection (DI)** - Objects receive dependencies from external sources
3. **Aspect-Oriented Programming (AOP)** - Cross-cutting concerns handled separately
4. **Convention over Configuration** - Default behaviors reduce boilerplate code
5. **Modular Architecture** - Loosely coupled components

**How they help build business applications:**

- **Testability** - DI makes unit testing easier with mock objects
- **Maintainability** - Loose coupling allows easy code changes
- **Scalability** - Modular design supports growth and complexity
- **Productivity** - Less boilerplate code, more focus on business logic
- **Enterprise features** - Built-in support for transactions, security, data access

## 11. Explain different types of dependency injection, explain their suitable use cases, and why field injection is not recommended in general.

**Types of Dependency Injection:**

### 1. Constructor Injection
```java
@Service
public class UserService {
    private final UserRepository userRepository;
    
    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}
```
**Use case:** Required dependencies, immutable objects
**Benefits:** Guarantees dependency availability, supports final fields

### 2. Setter Injection
```java
@Service
public class UserService {
    private UserRepository userRepository;
    
    @Autowired
    public void setUserRepository(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}
```
**Use case:** Optional dependencies, reconfigurable objects
**Benefits:** Allows partial injection, flexible configuration

### 3. Field Injection (Not Recommended)
```java
@Service
public class UserService {
    @Autowired
    private UserRepository userRepository;
}
```

**Why field injection is not recommended:**
- **Hard to test** - Cannot inject mocks easily
- **Violates immutability** - Cannot use final fields
- **Hidden dependencies** - Dependencies not visible in constructor
- **Framework coupling** - Tightly coupled to Spring framework
- **Reflection required** - Uses reflection, affects performance

**Best practice:** Use constructor injection for required dependencies, setter injection for optional ones.

## 12. Explain different types of application context in Spring framework, with screenshots.

**Types of Application Context:**

### 1. ClassPathXmlApplicationContext
```java
ApplicationContext context = new ClassPathXmlApplicationContext("applicationContext.xml");
```
- **Usage:** Loads context from XML file in classpath
- **Best for:** Traditional XML-based configuration

### 2. FileSystemXmlApplicationContext
```java
ApplicationContext context = new FileSystemXmlApplicationContext("/path/to/applicationContext.xml");
```
- **Usage:** Loads context from XML file in file system
- **Best for:** XML configuration outside classpath

### 3. AnnotationConfigApplicationContext
```java
ApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);
```
- **Usage:** Loads context from Java configuration classes
- **Best for:** Modern annotation-based configuration

### 4. WebApplicationContext
```java
// Automatically created in web applications
WebApplicationContext context = WebApplicationContextUtils.getWebApplicationContext(servletContext);
```
- **Usage:** Web-aware application context for web applications
- **Best for:** Spring MVC applications

### 5. GenericApplicationContext
```java
GenericApplicationContext context = new GenericApplicationContext();
```
- **Usage:** Generic context for programmatic bean registration
- **Best for:** Programmatic configuration

## 13. Compare @Component and @Bean and in which scenario they should be used.

**@Component vs @Bean:**

### @Component
```java
@Component
public class UserService {
    // Spring automatically creates instance
}
```
- **Usage:** Class-level annotation for automatic bean creation
- **Control:** Spring controls instantiation
- **Flexibility:** Limited customization options

### @Bean
```java
@Configuration
public class AppConfig {
    @Bean
    public UserService userService() {
        return new UserService(); // Manual instantiation
    }
}
```
- **Usage:** Method-level annotation in configuration classes
- **Control:** Developer controls instantiation
- **Flexibility:** Full control over bean creation

**When to use:**
- **@Component:** Simple beans, automatic scanning, standard instantiation
- **@Bean:** Third-party classes, complex initialization, conditional creation, multiple instances of same class

## 14. Explain Spring bean scopes and how to pick the correct bean scope.

**Spring Bean Scopes:**

### 1. Singleton (Default)
```java
@Component
@Scope("singleton")
public class UserService { }
```
- **Lifecycle:** One instance per Spring container
- **Use case:** Stateless services, shared resources

### 2. Prototype
```java
@Component
@Scope("prototype")
public class UserCommand { }
```
- **Lifecycle:** New instance every time requested
- **Use case:** Stateful objects, request-specific data

### 3. Request (Web only)
```java
@Component
@Scope("request")
public class UserSession { }
```
- **Lifecycle:** One instance per HTTP request
- **Use case:** Request-specific data in web applications

### 4. Session (Web only)
```java
@Component
@Scope("session")
public class ShoppingCart { }
```
- **Lifecycle:** One instance per HTTP session
- **Use case:** User session data, shopping carts

### 5. Global-Session (Web only)
```java
@Component
@Scope("globalSession")
public class GlobalUserData { }
```
- **Lifecycle:** One instance per global HTTP session
- **Use case:** Portlet applications

**How to pick the correct scope:**
- **Singleton:** Default choice for stateless services
- **Prototype:** When you need fresh instances with different state
- **Request:** For web request-specific data
- **Session:** For user session data that persists across requests

## 15. Explain the difference between bean id and bean class.

**Bean ID vs Bean Class:**

### Bean ID
```java
@Component("userService")  // ID = "userService"
public class UserService { }

@Bean("customUserService")  // ID = "customUserService"
public UserService createUserService() { }
```
- **Purpose:** Unique identifier for the bean in Spring container
- **Usage:** Used to retrieve bean from context
- **Default:** Class name with first letter lowercase

### Bean Class
```java
@Component
public class UserService { }  // Class = UserService.class
```
- **Purpose:** The actual Java class type of the bean
- **Usage:** Defines the bean's type and behavior
- **Relationship:** Multiple beans can have same class but different IDs

**Example:**
```java
// Same class, different IDs
@Bean("primaryUserService")
public UserService primaryService() { return new UserService("primary"); }

@Bean("secondaryUserService") 
public UserService secondaryService() { return new UserService("secondary"); }
```

**Key differences:**
- **ID:** Unique name for identification
- **Class:** Type definition and implementation
- **Retrieval:** Can get bean by ID or by class type
- **Multiple beans:** Same class can have multiple IDs

## 16. Explain that when a bean has multiple alternative implementations, how will Spring decide which bean implementation to inject/autowire?

**Problem:** When multiple beans of the same type exist, Spring cannot decide which one to inject.

**Default Behavior:** Spring throws `NoUniqueBeanDefinitionException`

**Solutions:**

### 1. @Primary Annotation
```java
@Component
@Primary
public class EmailNotificationService implements NotificationService { }

@Component
public class SmsNotificationService implements NotificationService { }

@Service
public class UserService {
    @Autowired
    private NotificationService notificationService; // Injects EmailNotificationService
}
```
- **Usage:** Mark preferred implementation as primary
- **Benefit:** Default choice when multiple implementations exist

### 2. @Qualifier Annotation
```java
@Component
@Qualifier("email")
public class EmailNotificationService implements NotificationService { }

@Component
@Qualifier("sms")
public class SmsNotificationService implements NotificationService { }

@Service
public class UserService {
    @Autowired
    @Qualifier("email")
    private NotificationService notificationService; // Specific injection
}
```
- **Usage:** Specify exact bean to inject by qualifier name
- **Benefit:** Explicit control over which implementation to use

### 3. @Resource Annotation
```java
@Service
public class UserService {
    @Resource(name = "emailNotificationService")
    private NotificationService notificationService; // Inject by bean name
}
```
- **Usage:** Inject by bean name instead of type
- **Benefit:** Name-based injection

### 4. Constructor Parameter Names
```java
@Service
public class UserService {
    private final NotificationService emailNotificationService;
    
    public UserService(NotificationService emailNotificationService) {
        this.emailNotificationService = emailNotificationService; // Matches bean name
    }
}
```
- **Usage:** Parameter name matches bean name
- **Benefit:** Automatic matching by name

### 5. List/Map Injection
```java
@Service
public class UserService {
    @Autowired
    private List<NotificationService> notificationServices; // All implementations
    
    @Autowired
    private Map<String, NotificationService> serviceMap; // Name -> Implementation
}
```
- **Usage:** Inject all implementations or as a map
- **Benefit:** Access to all implementations when needed

**Resolution Order:**
1. **@Primary** - Preferred implementation
2. **@Qualifier** - Explicit qualifier matching
3. **Bean name** - Parameter/field name matching
4. **Exception** - NoUniqueBeanDefinitionException if none of above work

**Best Practices:**
- Use **@Primary** for default implementation
- Use **@Qualifier** for specific use cases
- Use **@Resource** for name-based injection
- Avoid multiple @Primary annotations for same type
