## 2. TLS, PKI, Certificate, Public Key, Private Key, and Signature

**TLS (Transport Layer Security)**: A cryptographic protocol that provides secure communication over networks. It encrypts data between client and server, ensuring confidentiality and integrity.

**PKI (Public Key Infrastructure)**: A framework of technologies, policies, and procedures for managing digital certificates and public-private key pairs. It enables secure electronic transfer of information.

**Certificate**: A digital document that binds a public key to an identity (like a domain name or organization). It's issued by a trusted Certificate Authority (CA) and proves that the public key belongs to the claimed entity.

**Public Key**: Part of an asymmetric key pair that can be shared openly. Used to encrypt data that only the corresponding private key can decrypt, or to verify signatures created with the private key.

**Private Key**: The secret part of an asymmetric key pair that must be kept confidential. Used to decrypt data encrypted with the public key or to create digital signatures.

**Signature**: A cryptographic mechanism that proves data authenticity and integrity. Created using a private key and verified using the corresponding public key.

### 3.2 Testing Without Importing Certificate

When you test the HTTPS API without importing the self-signed certificate, you'll get an SSL certificate verification error. This happens because:
- Self-signed certificates aren't issued by a trusted CA
- The browser/client can't verify the certificate's authenticity
- The certificate chain doesn't lead back to a trusted root CA

### 3.3 Making HTTPS Call Work

To make HTTPS calls work properly:
1. **Import the certificate**: Add the self-signed certificate to your system's trust store
2. **Use proper client configuration**: Configure your HTTP client to trust the specific certificate
3. **Certificate chain verification**: Ensure the certificate has proper subject alternative names (SAN) for your domain

For Java clients:
```java
// Import certificate to Java cacerts
keytool -import -trustcacerts -file mycert.crt -alias myapp -keystore $JAVA_HOME/lib/security/cacerts
```

## 4. HTTP Status Codes for Authentication/Authorization Failures

- **401 Unauthorized**: Authentication required or failed
- **403 Forbidden**: Authenticated but not authorized for the resource
- **407 Proxy Authentication Required**: Must authenticate with proxy
- **511 Network Authentication Required**: Client must authenticate to gain network access

## 5. Authentication vs Authorization & Spring Security Components

**Authentication**: Verifying "who you are" - validating user credentials
**Authorization**: Determining "what you can do" - checking permissions for resources

**Key Spring Security Components**:
- **AuthenticationManager**: Coordinates authentication process
- **AuthenticationProvider**: Performs actual authentication logic
- **UserDetailsService**: Loads user-specific data
- **SecurityFilterChain**: Handles HTTP request security processing
- **AccessDecisionManager**: Makes authorization decisions

## 6. HTTP Session

An HTTP session is a way to store information about a user across multiple HTTP requests. Since HTTP is stateless, sessions provide a mechanism to maintain state. The server creates a unique session ID and stores session data server-side, while the client receives the session ID (usually in a cookie).

## 7. Cookie

A cookie is a small piece of data sent from the server to the user's browser, which stores it and sends it back with subsequent requests to the same domain. Cookies can store user preferences, authentication tokens, or tracking information.

## 8. Session vs Cookie

| Session | Cookie |
|---------|--------|
| Stored on server | Stored on client |
| More secure | Less secure |
| No size limit (server memory) | Size limited (~4KB) |
| Expires when session ends | Can have custom expiration |
| Requires session ID cookie | Standalone data storage |

## 9. Google SSO Workflow

Google SSO uses OAuth 2.0 flow:

1. **Authorization Request**: App redirects to Google authorization server
2. **User Consent**: User authenticates and grants permissions
3. **Authorization Code**: Google redirects back with authorization code
4. **Token Exchange**: App exchanges code for access token
5. **User Info**: App uses token to get user information

Key REST calls in Chrome DevTools:
- `GET https://accounts.google.com/oauth/authorize` - Authorization request
- `POST https://oauth2.googleapis.com/token` - Token exchange
- `GET https://www.googleapis.com/oauth2/v2/userinfo` - User profile

## 10. Using Session and Cookie for User Information

1. **Login**: Server validates credentials and creates session
2. **Session Storage**: Server stores user info in session
3. **Cookie Response**: Server sends session ID in cookie
4. **Subsequent Requests**: Browser includes session cookie
5. **Session Retrieval**: Server uses session ID to retrieve user data

```java
// Store in session
session.setAttribute("user", userObject);

// Retrieve from session
User user = (User) session.getAttribute("user");
```

## 11. Spring Security Filter

Spring Security uses a chain of filters to process HTTP requests. The `SecurityFilterChain` intercepts requests before they reach controllers, handling authentication, authorization, CSRF protection, and more. Key filters include:
- `UsernamePasswordAuthenticationFilter`
- `BasicAuthenticationFilter`
- `AuthorizationFilter`

## 12. Bearer Token and JWT

**Bearer Token**: An access token that grants access to resources. The client includes it in the Authorization header: `Authorization: Bearer <token>`

**JWT (JSON Web Token)**: A self-contained token format with three parts:
- **Header**: Algorithm and token type
- **Payload**: Claims about the user
- **Signature**: Verification signature

JWT benefits: stateless, self-contained, can carry user information without server lookups.

## 14. Spring Security Components Comparison

- **UserDetailsService**: Loads user data from storage (database, LDAP)
- **AuthenticationProvider**: Implements authentication logic, uses UserDetailsService
- **AuthenticationManager**: Coordinates multiple AuthenticationProviders
- **AuthenticationFilter**: Intercepts requests, triggers authentication process

Flow: Filter → Manager → Provider → UserDetailsService

## 15. Session Disadvantages and Solutions

**Disadvantages**:
- Memory consumption on server
- Not suitable for microservices
- Sticky sessions required for load balancing
- Doesn't scale horizontally well

**Solutions**:
- Use stateless JWT tokens
- Implement distributed session storage (Redis)
- Session clustering
- Database-backed sessions

## 17. configure(HttpSecurity) vs configure(AuthenticationManagerBuilder)

**configure(HttpSecurity http)**:
- Configures web-based security
- Defines URL access rules
- Sets up filters, login pages, logout
- Handles authorization policies

**configure(AuthenticationManagerBuilder auth)**:
- Configures authentication mechanisms
- Sets up authentication providers
- Defines user stores (in-memory, database, LDAP)
- Handles password encoding

## 19. Best Practices for Storing Secrets

1. **Environment Variables**: Store secrets in environment variables, not code
2. **External Secret Management**: Use services like AWS Secrets Manager, HashiCorp Vault
3. **Configuration Files**: Keep secrets in separate, encrypted configuration files
4. **Principle of Least Privilege**: Grant minimal necessary access
5. **Secret Rotation**: Regularly rotate secrets
6. **Encryption at Rest**: Encrypt stored secrets
7. **Audit Logging**: Log secret access and changes
8. **Version Control**: Never commit secrets to version control
