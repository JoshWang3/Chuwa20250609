1. Explain TLS, PKI, certificate, public key, private key, and signature.
    - TLS: Transport Layer Security is a protocol that ensures sucure communication over a network(like HTTPS).
    It provides Encryption, Integrity and Authentication.
    - PKI: Public Key Infrastructure is the framework that makes TLS and orther secure system work. It includes Digital cerificates, Certificates authorities(CAs), Public/Private key pairs and Validation rules.
    - Certificate: A digital certificate is like a passport for a website. It contains: The website's public key, the domain name, the issuer, the digital signature of the issuer. The cerificate is what the browser checks when connecting to a secure site.
    - Public Key and Private Key:
    Public Key can be shared with anyone. 
    It is used to encrypt messages or verify signatures.
    - Private Key:
    It must be kept secret.
    It is used to decrypt messages or sign data.
    It verifies a participant is who the participant claims to be.
    The public/private key pair is the backbone of asymmetric cryptography.
    - Digital Signature:
    A digital signature proves that a message(or cerificate) was created by someone who owns the private key.
    The process is listed below:
        - Data is hashed
        - The hash is encrypted with the sender's private key(signature)
        - The recipient uses the sender's public key to verify the signature
    In TLS, CAs sign cerificates and the broser verifies them using the CA's public key.

3. List all http status code that are related to authentication and authorization failures.
   | Status Code            | Name                                       | Description                                                                                                                         |
| ---------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| **401**                | **Unauthorized**                           | The user is **not authenticated** — usually means missing or invalid credentials (e.g., no token, invalid session, wrong password). |
| **403**                | **Forbidden**                              | The user is **authenticated but not authorized** — you don’t have permission to access the resource (e.g., wrong role).             |
| **407**                | **Proxy Authentication Required**          | The client must first authenticate with the proxy — similar to 401 but for proxy servers.                                           |
| **419** (non-standard) | **Authentication Timeout**                 | Some frameworks (like Laravel) use this when a session has expired — not an official status code.                                   |
| **498** (non-standard) | **Invalid Token**                          | Used by some APIs (e.g., Google APIs) when a token is expired or invalid.                                                           |
| **499** (non-standard) | **Token Required / Client Closed Request** | Some custom APIs use this when a request lacks a required token. In NGINX, 499 means client closed request prematurely.             |

| Feature                  | Authentication                    | Authorization                          |
| ------------------------ | --------------------------------- | -------------------------------------- |

| **Purpose**              | Confirm user identity (login)     | Control access to resources            |

5. Explain HTTP Session.
    A HTTP session is a way for a web server to remember information about a client across multiple requests, despite the fact that HTTP itself is stateless.
    A HTTP session works like this:
        1. User sends first request(login form)
        2. Server creates a ssion and assigns a session ID
        3. Server stores data on the server, keyed by session ID
        4. Server sends a cookie with session id to the client.
        5. For every future request, the browser sends back the cookie with session id

6. Explain cookie. 
    A cookie is a small piece of data that a server sends to the browser, which the browser stores and sends back with future requests to the same server. Cookies help enable stateful behavior in an otherwise stateless HTTP protocol.
    A cookie is a key-value pair stored in the browser.
    It is sent automatically with every HTTP request to the server that set it.
    used to store information across multiple requests.

11. Explain bearer token and how JWT works.
    A Bearer Token is a security token that a client sends in the Authorization header of an HTTP request to authenticate itself to the server.
    A JWT is a self-contained token that:
    Represents a user's identity and claims
    Is digitally signed
    Can be verified by the server without database lookup
    A JWT has 3 parts, separated by dots:
    Header:
        {
            "alg": "HS256",
            "typ": "JWT"
        }
    Payload:
        {
            "sub": "123456",
            "username": "alice",
            "role": "USER",
            "exp": 1723574732
        }
    Signature:
        Signed using:
        A secret (HMAC)
        Or a private key (RSA/ECDSA)

14. What is the disadvantage of Session? How to overcome the disadvantage.
| Problem                              | Description                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| **1. Server-Side Storage**           | Each session is stored in memory or persistent store on the server → leads to scalability issues             |
| **2. Not Stateless**                 | HTTP is stateless, but sessions make it stateful. Harder to scale horizontally (e.g., across many servers)   |
| **3. Session Hijacking**             | If an attacker steals the session ID (`JSESSIONID` cookie), they can impersonate the user                    |
| **4. Load Balancer Sticky Sessions** | Without sticky sessions or session replication, a user might hit a different server and lose their session   |
| **5. Limited in Mobile/SPA APIs**    | Modern mobile apps and SPAs (React/Vue) use APIs → sessions are not ideal compared to token-based approaches |
How to overcome the disadvantages.
1. Use Token-Based Authentication (e.g., JWT)
    Stateless: Client stores the token and sends it in each request (Authorization: Bearer <token>)
    Scalable: No session data needs to be stored on the server
    Works across domains/microservices
    Scalable: No session data needs to be stored on the server
2. Use Session Replication (if sessions are unavoidable)
    Replicate session data across multiple servers using:
        Hazelcast
        Redis
        Spring Session
| Practice                                  | Reason                          |
| ----------------------------------------- | ------------------------------- |
| Use **HTTPS only**                        | Prevent cookie/session sniffing |
| Use `HttpOnly`, `Secure` flags on cookies | Prevent XSS stealing            |
| Set `SameSite=Strict` or `Lax`            | Prevent CSRF                    |
| Implement **session timeout**             | Force logout after inactivity   |
| Regenerate session ID on login            | Prevent session fixation        |
