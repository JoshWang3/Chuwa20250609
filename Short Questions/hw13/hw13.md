## 2. Explain TLS, PKI, certificate, public key, private key, and signature.

### ✅ TLS/SSL (Transport Layer Security)

**What it is:**  
A cryptographic protocol that secures communication over the internet — for example, HTTPS uses TLS, SSH login to cloud
sever, git setup.

**What it does:**

- Encrypts data between client and server
- Verifies server identity
- Prevents eavesdropping, tampering, and forgery

---

### ✅ PKI (Public Key Infrastructure)

**What it is:**  
A system for managing public-key encryption, including:

- issuing,
- verifying,
- and revoking **digital certificates**

**Components:**

- Certificate Authority (CA)
- Public/private key pairs
- Certificates

**Purpose:**  
Ensures that a public key **really belongs** to the entity it claims to represent.

---

### ✅ Certificate

**What it is:**  
A file (usually `.crt` or `.pem`) that contains:

- A public key
- Information about the owner
- A digital signature from a trusted CA

**Purpose:**  
To prove the identity of a server or user and bind it to a **public key**.

**Example:**  
The certificate used by `https://google.com` proves it is **actually** Google and not an imposter.

---

### ✅ Public Key

**What it is:**  
One half of a key pair used in **asymmetric encryption**.

- Can be **shared freely**
- Used to **encrypt data** or **verify signatures**

---

### ✅ Private Key

**What it is:**  
The **secret** part of a key pair.

- Must be **kept secure**
- Used to **decrypt data** or **create signatures**

**Rule:**  
If your **public key** is like your lock, the **private key** is your key — only you should have it.

---

### ✅ Signature (Digital Signature)

**What it is:**  
A cryptographic proof that:

1. A message or certificate was created by someone with the private key
2. The data hasn’t been tampered with

**How it works:**

- Sender creates a hash of the message
- Signs the hash using their **private key**
- Receiver verifies using sender’s **public key**

---

### 💡 How They Work Together (TLS + PKI)

1. **Browser connects** to a secure server (e.g., `https://example.com`)
2. Server presents its **certificate** (includes public key, signed by CA)
3. Browser **validates certificate** using **PKI** (checks CA, expiration, revocation)
4. Browser uses the **public key** to:
    - Encrypt a session key
    - Start secure TLS communication
5. Only the server can decrypt it using its **private key**

## 4. list all http status codes that related to authentication and authorization failures

🔐 Authentication vs Authorization

- Authentication = Verifying who you are
- Authorization = Verifying what you are allowed to do

✅ Common HTTP Status Codes for Auth Failures

| HTTP Status Code       | Name                          | Category           | Description                                                                                  |
|------------------------|-------------------------------|--------------------|----------------------------------------------------------------------------------------------|
| **400**                | Bad Request                   | General Error      | May occur when authentication data is malformed or missing (e.g., no `Authorization` header) |
| **401**                | Unauthorized                  | **Authentication** | The user is not authenticated. Login is required, or credentials are invalid                 |
| **403**                | Forbidden                     | **Authorization**  | The user is authenticated but does **not** have permission to access the resource            |
| **407**                | Proxy Authentication Required | Authentication     | The client must authenticate with a proxy server first                                       |
| **419** (non-standard) | Session Expired               | Authentication     | Not an official HTTP status code, used by some frameworks to indicate login session timeout  |

✅ In Spring Security context:

| Scenario                                                         | Status Code | Meaning                     |
|------------------------------------------------------------------|-------------|-----------------------------|
| User is **not logged in** and tries to access a secured endpoint | `401`       | Authentication required     |
| User is **logged in** but lacks required role/authority          | `403`       | Access denied               |
| Request is missing `Authorization` header                        | `401`       | Authentication data missing |
| User provides wrong credentials                                  | `401`       | Authentication failed       |

## 5. Compare authentication and authorization? Name and explain important components in Spring security that undertake authentication and authorization

| Concept                | Authentication                             | Authorization                       |
|------------------------|--------------------------------------------|-------------------------------------|
| **Meaning**            | Verifies **who** the user is               | Determines **what** the user can do |

| **Example**            | Login with username/password               | Accessing an admin-only endpoint    |
| **HTTP Code**          | `401 Unauthorized` if authentication fails | `403 Forbidden` if access is denied |

#### Authentication Components

| Component                | Role / Explanation                                                                  |
|--------------------------|-------------------------------------------------------------------------------------|
| `AuthenticationManager`  | Core interface that performs authentication. Delegates to `AuthenticationProvider`  |
| `AuthenticationProvider` | Validates credentials and returns an `Authentication` object                        |
| `UserDetailsService`     | Loads user details from database or memory (`UserDetails`)                          |
| `UserDetails`            | Interface representing the authenticated user (`getUsername()`, `getAuthorities()`) |
| `PasswordEncoder`        | Verifies the password (e.g., `BCryptPasswordEncoder`)                               |
| `SecurityContext`        | Holds current authentication information in thread-local storage                    |
| `SecurityContextHolder`  | Static access to the current `SecurityContext`                                      |

#### Authorization Components

| Component                   | Role / Explanation                                                           |
|-----------------------------|------------------------------------------------------------------------------|
| `AccessDecisionManager`     | Decides whether a user has permission to access a secured resource           |
| `AccessDeniedHandler`       | Handles `403 Forbidden` responses when access is denied                      |

1. **User sends request with credentials**
2. `AuthenticationManager` invokes `AuthenticationProvider`
3. `UserDetailsService` loads the user
4. Credentials are checked (using `PasswordEncoder`)
5. On success:
    - `Authentication` object stored in `SecurityContext`
6. User accesses endpoint:
    - `AccessDecisionManager` checks roles/permissions
    - Access is allowed or denied

## 6. Explain HTTP Session?

An **HTTP Session** is a way to maintain **state** (user data) across multiple HTTP requests from the same client (
typically a browser) to a web server, even though HTTP itself is **stateless**.

---

#### 🔑 Key Concepts

- **HTTP is stateless**: Each request from the client to the server is independent and doesn’t remember previous
  interactions.
- **Session**: A mechanism to store data (like user login info, preferences, cart items) for a particular user across
  multiple requests.

---

#### 🧠 How It Works

1. **Session Creation**:
    - When a user sends their first request (like logging in), the server creates a session and stores a unique *
      *session ID**.
    - This ID is sent to the client via a **cookie** (`Set-Cookie: JSESSIONID=xyz123`).

2. **Session Tracking**:
    - On subsequent requests, the browser sends the cookie (`Cookie: JSESSIONID=xyz123`) back to the server.
    - The server uses this ID to look up the user’s session data.

3. **Session Storage**:
    - On the server side, session data is stored in memory or a database.
    - This data might include:
        - `userId`
        - `shoppingCart`
        - `roles`

---

### 🧰 Common Use Cases

- Login authentication (track logged-in users)
- Shopping cart management
- User preferences/settings
- Form data across multiple steps

---

A **cookie** is a small piece of data(key-value pair) stored on the client-side (in the browser) and sent with every
HTTP request to the
same server. It’s commonly used to maintain **state**, track users, and personalize experiences.

---

#### ✅ Key Characteristics

| Feature    | Description                                                                                    |
|------------|------------------------------------------------------------------------------------------------|
| Storage    | Stored in the **browser** (client-side).                                                       |
| Size Limit | ~4 KB per cookie.                                                                              |
| Lifetime   | Can be **session-based** (deleted on browser close) or **persistent** (expires at a set time). |
| Scope      | Controlled by `domain` and `path` attributes.                                                  |
| Secure     | Can be marked `Secure` (only sent over HTTPS) and `HttpOnly` (not accessible by JS).           |

---

#### 🔄 How Cookies Work

1. **Server sets a cookie**:
   ```http
   Set-Cookie: userId=abc123; Max-Age=3600; Path=/; HttpOnly
   ```
2. **Browser stores it** and sends it with every request to the same domain:

   ```http
   Cookie: userId=abc123
   ```

3. **Server reads cookie** from the request and uses it to identify the user or session.

---

#### 🧠 Common Use Cases

- Session tracking (e.g., `JSESSIONID`)
- Authentication tokens
- User preferences (e.g., theme, language)
- Analytics and tracking

---

#### 🔐 Cookie Attributes

| Attribute             | Purpose                                                |
|-----------------------|--------------------------------------------------------|
| `Name=Value`          | The actual data                                        |
| `Max-Age` / `Expires` | Controls how long the cookie lives                     |
| `Path`                | Limits the cookie to a specific path                   |
| `Domain`              | Limits cookie to specific subdomains                   |
| `Secure`              | Only sent over HTTPS                                   |
| `HttpOnly`            | Prevents JS access (helps prevent XSS)                 |
| `SameSite`            | Controls cross-site behavior (`Lax`, `Strict`, `None`) |

## 8. Compare Session and Cookie?

| Feature                | **Session**                                 | **Cookie**                                   |
|------------------------|---------------------------------------------|----------------------------------------------|
| **Storage Location**   | Server-side (e.g., memory, database)        | Client-side (browser)                        |
| **Data Size Limit**    | Large (server memory limit)                 | Small (\~4 KB per cookie)                    |
| **Security**           | More secure (data is not exposed to client) | Less secure (data stored on client, visible) |
| **Lifetime**           | Expires based on server timeout             | Can be session-based or have explicit expiry |
| **Accessibility**      | Not accessible via client-side JS           | Can be accessed via JS (unless `HttpOnly`)   |
| **Data Type**          | Can store complex objects                   | Only stores string key-value pairs           |
| **Use Case**           | Store login info, cart, user state          | Store preferences, tokens, analytics data    |
| **Sent with request?** | No (only session ID via cookie)             | Yes, sent with every matching HTTP request   |
| **Server Load**        | Higher (stores session data)                | Minimal (stored on client)                   |

#### ✅ Typical Usage

- **Session**:
- Login state (e.g., user info)
- Shopping cart contents
- Multi-step form data

- **Cookie**:
- Remember me tokens
- UI preferences (e.g., dark mode)
- Tracking identifiers (e.g., Google Analytics ID)

---

#### 🧠 How They Work Together

- Sessions often **depend on a cookie** (e.g., `JSESSIONID`) to track the user:
- The cookie holds the **session ID**.
- The server uses that ID to retrieve full session data.

6. SSO Complete
   - User is now logged in, and Medium sets session cookies or JWT in the browser.

## 10. How do we use session and cookie to keep user information across the the application?

1. **User logs in**

- Server authenticates user.
- Server creates a session (e.g., `session.setAttribute("user", userObject)`).
- Server generates a session ID.
- Server sends a `Set-Cookie`

2. **Browser stores the cookie**

- The cookie contains the session ID only (not the actual session data).

3. **User makes subsequent requests**

- Browser sends cookie (`JSESSIONID=abc123xyz`) with each request.
- Server uses that session ID to retrieve the stored session data (like user info).

4. **User stays logged in** as long as:

- The session is valid (not expired).
- The session ID cookie is present in the browser.

---

#### ✅ Example in Java (Spring Boot)

**Set session attributes on login:**

```java

@PostMapping("/login")
public String login(HttpSession session) {
    User user = userService.authenticate(...);
    session.setAttribute("user", user);
    return "redirect:/dashboard";
}
```

**Retrieve session data on another page:**

```java

@GetMapping("/dashboard")
public String dashboard(HttpSession session) {
    User user = (User) session.getAttribute("user");
    if (user == null) {
        return "redirect:/login";
    }
    return "dashboard";
}
```

## 11. What is the spring security filter?

- In **Spring Security**, a **security filter** is a part of the **filter chain** that processes HTTP requests and
  applies **authentication, authorization, CSRF protection**, and other security mechanisms before the request reaches
  the controller.
- Spring Security uses a **`FilterChainProxy`** which delegates to a chain of **Servlet filters**, each handling a
  different security responsibility.

#### 🔄 Common Spring Security Filters (simplified)

| Filter Class                           | Purpose                                                             |
|----------------------------------------|---------------------------------------------------------------------|
| `SecurityContextPersistenceFilter`     | Restores and saves the `SecurityContext` from the session           |
| `UsernamePasswordAuthenticationFilter` | Processes login attempts with username and password                 |
| `BasicAuthenticationFilter`            | Handles HTTP Basic authentication                                   |
| `BearerTokenAuthenticationFilter`      | Handles OAuth2 Bearer tokens (e.g., JWT)                            |
| `ExceptionTranslationFilter`           | Handles security exceptions (e.g., access denied)                   |
| `FilterSecurityInterceptor`            | Performs authorization checks before accessing a protected resource |
| `CsrfFilter`                           | Enforces CSRF protection                                            |
| `LogoutFilter`                         | Handles logout requests                                             |

---

#### 🧠 How It Works

When an HTTP request comes in:

1. It enters the **Spring Security filter chain**.
2. Each filter inspects or modifies the request as needed:

- Is the user authenticated?
- Does the user have the right role?
- Is CSRF token present and valid?

3. If all checks pass, the request proceeds to the controller.

## 12. Explain bearer token and how JWT works.

#### 🔐 What is a **Bearer Token**?

- A **Bearer Token** is a string (usually a long encoded value) that you include in an HTTP request's `Authorization`
  header.
- It tells the server: "**I'm the bearer of this token, so I should be allowed access**."
- Example HTTP request:

```http
GET /api/profile HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

#### 🪙 What is a **JWT (JSON Web Token)?**

JWT is a specific kind of bearer token. It's a compact, self-contained token used to securely transmit information
between parties.

#### 🧱 Structure of JWT

A JWT has 3 parts (Base64-encoded):

```css
header.payload.signature
```

1. **Header**:

Specifies the algorithm and token type.

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

2. **Payload**:

Contains **claims** — data like user ID, roles, expiration.

```json
{
  "sub": "1234567890",
  "name": "Alice",
  "role": "admin",
  "exp": 1712345678
}
```

3. **Signature**: To verify integrity.

---

#### 🔁 How JWT Works (Auth Flow)

1. **User logs in**
    - Server validates credentials.
    - Server generates a **JWT** with user info and expiration.
    - Server returns the JWT to client.

2. **Client stores JWT**
    - Usually in localStorage or a cookie (not HttpOnly unless needed for security).

3. **Client sends JWT with each request**
   ```http
   Authorization: Bearer <JWT>
   ```

4. **Server verifies JWT**
    - Decodes the token.
    - Validates signature and expiration.
    - Grants or denies access.

## 13. Explain how do we store sensitive user information such as password and credit card number in DB?

### 🔐 1. Password Storage

#### ✅ Use **Hashing (with salt)**

- **Never encrypt passwords** (encryption is reversible), always **hash** them.
- A **hash** is a one-way function — it cannot be reversed to get the original password.

#### 🔄 Hashing Process:

```plaintext
user enters password → add salt → hash → store hash in DB
```

#### ✅ Recommended Algorithms:

- `bcrypt` ✅
- `argon2` ✅
- `PBKDF2` ✅

---

### 💳 2. Credit Card Numbers (PII)

#### ❌ Do not store full card numbers unless you are **PCI-DSS compliant**.

#### ✅ If you **must** store:

- **Encrypt** the data using strong encryption (e.g., AES-256).
- **Never store CVV** — even PCI-DSS forbids it.
- **Mask** card number if showing it (e.g., `**** **** **** 1234`).
- Store only what's needed: usually last 4 digits + encrypted token.

#### 🔐 Example: AES Encryption

Use a secure key management system (KMS) — never hardcode keys in code.

```java
Cipher cipher = Cipher.getInstance("AES/CBC/PKCS5Padding");
// initialize with secret key and IV
byte[] encrypted = cipher.doFinal(creditCardNumber.getBytes());
```

#### 🔒 Store:

| Field               | Stored Example                |
|---------------------|-------------------------------|
| `last4Digits`       | `1234`                        |
| `cardEncryptedBlob` | AES-encrypted ciphertext blob |
| `createdAt`         | timestamp                     |

---

### 📜 Summary

| Data Type          | Storage Method                      | Notes                                     |
|--------------------|-------------------------------------|-------------------------------------------|
| Password           | Hash (bcrypt, Argon2)               | Use salt, never decryptable               |
| Credit Card Number | AES encryption (with KMS)           | PCI-DSS required                          |
| CVV                | ❌ Never store                       | Not allowed by PCI-DSS                    |
| Email, Address     | Store plain or encrypted (optional) | Depends on sensitivity and compliance     |
| Token (e.g. JWT)   | Signed + optionally encrypted       | Store securely if refresh tokens are used |

## 14. Compare UserDetailService, AuthenticationProvider, AuthenticationManager, AuthenticationFilter?

### 🔐 1. `UserDetailsService`

-   **Responsibility**: Loads user-specific data from a source (e.g., DB) by username.

-   **Method**: `loadUserByUsername(String username)`

-   **Returns**: `UserDetails`

-   **Typical Usage**: Implemented by a custom class (e.g., `CustomUserDetailsService`) to look up user data.


```java
public interface UserDetailsService {
    UserDetails loadUserByUsername(String username) throws UsernameNotFoundException;
}
```

---

### 🔐 2. `AuthenticationProvider`

-   **Responsibility**: Performs actual authentication.

-   **Method**: `authenticate(Authentication authentication)`

-   **Returns**: `Authentication` (fully populated if successful)

-   **Typical Usage**: Uses `UserDetailsService` and password encoder to verify credentials.


```java
public interface AuthenticationProvider {
    Authentication authenticate(Authentication authentication) throws AuthenticationException;
    boolean supports(Class<?> authentication);
}
```

---

### 🔐 3. `AuthenticationManager`

-   **Responsibility**: Delegates to one or more `AuthenticationProvider`s to authenticate.

-   **Method**: `authenticate(Authentication authentication)`

-   **Common Implementation**: `ProviderManager`

-   **Typical Usage**: Central place that coordinates authentication attempts.


```java
AuthenticationManager authManager = new ProviderManager(List.of(customAuthProvider));
```

---

### 🔐 4. `AuthenticationFilter` (e.g., `UsernamePasswordAuthenticationFilter`)

-   **Responsibility**: Intercepts login requests (usually HTTP POST to `/login`), extracts credentials, and delegates to `AuthenticationManager`.

-   **Typical Flow**:

    -   Parses credentials from HTTP request.

    -   Creates `UsernamePasswordAuthenticationToken`.

    -   Calls `AuthenticationManager.authenticate(...)`.

    -   Sets `SecurityContext` if successful.


```java
public class CustomAuthenticationFilter extends UsernamePasswordAuthenticationFilter {
    // overrides attemptAuthentication(...) and successfulAuthentication(...)
}
```

---

### 🔁 Summary Table

| Component | Role | Depends On | Used In |
| --- | --- | --- | --- |
| `UserDetailsService` | Loads user info from DB | \- | Inside `AuthenticationProvider` |
| `AuthenticationProvider` | Authenticates with credentials | `UserDetailsService` | Used by `AuthenticationManager` |
| `AuthenticationManager` | Delegates to providers | `AuthenticationProvider` | Used by `AuthenticationFilter` |
| `AuthenticationFilter` | Parses requests and starts auth flow | `AuthenticationManager` | Intercepts HTTP login request |

## 15. What is the disadvantage of Session? how to overcome the disadvantage?

| Disadvantage                                | Description                                                                                                                               | Possible Solutions                                                                                                                       |
|---------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------|
| **1. Scalability Issue**                    | Session data is stored in memory (RAM) on the server, so more users = more memory usage. This limits scalability for large-scale systems. | ✅ Use **distributed session storage** (e.g., Redis, Memcached) so sessions can be shared across servers.                                 |
| **2. Server Load**                          | Session storage increases server memory usage, especially for many concurrent users.                                                      | ✅ Offload session state to external store (Redis, DB) to reduce memory pressure.                                                         |
| **3. Sticky Session Requirement**           | In load-balanced environments, the same user must be routed to the same server (sticky session), which reduces flexibility.               | ✅ Use **centralized session store** like Redis; all servers can access the same session data.                                            |
| **4. Stateless Protocol Violation**         | HTTP is stateless, but session adds server-side state, making horizontal scaling and fault tolerance harder.                              | ✅ Design apps to be **stateless when possible**, or minimize session data. Use **JWT tokens** as a stateless alternative if appropriate. |
| **5. Session Expiry Issues**                | If session expires (e.g., timeout), users may lose progress or need to log in again.                                                      | ✅ Use refresh tokens or client-side local storage for persistent login. Also inform users of timeout with countdown timers.              |
| **6. Inconsistency in Distributed Systems** | In multi-server systems, in-memory sessions can become inconsistent or unavailable.                                                       | ✅ Use shared stores (Redis), or stateless tokens like JWT to ensure consistency.                                                         |

### 🛠️ Common Solutions in Practice

1. **Central Session Store**

- Use Redis or Memcached to store session data.
- All application servers access this shared store.

2. **Stateless Authentication with JWT**

- Instead of storing session state on the server, encode user info in a signed token.
- Client sends the token with each request.
- Scales easily and no server-side memory usage.

## 16. how to get value from application.properties in Spring security?

- use the @Value annotation or inject an @ConfigurationProperties bean.

### ✅ 1. Use `@Value`

```properties
# application.properties
jwt.secret=abcd1234
```

```java
@Component
public class JwtConfig {

    @Value("${jwt.secret}")
    private String jwtSecret;

    public String getJwtSecret() {
        return jwtSecret;
    }
}
```

Then use `@Autowired` in the security config or service:

```java
@Configuration
public class SecurityConfig {

    private final JwtConfig jwtConfig;

    @Autowired

        this.jwtConfig = jwtConfig;
    }

    // now can use jwtConfig.getJwtSecret()
```

## 17. What is the role of configure(HttpSecurity http) and configure(AuthenticationManagerBuilder auth)?

### ✅ `configure(HttpSecurity http)`

**Purpose:**  
Defines **which HTTP requests** are secured and how.

**Typical Uses:**
-   Specify which endpoints require authentication.
-   Configure login/logout.
-   Define CSRF, CORS, form login, JWT, OAuth, etc.


**Example:**

```java
@Override
protected void configure(HttpSecurity http) throws Exception {
    http.csrf().disable()
        .authorizeRequests()
        .antMatchers("/public/**").permitAll()
        .anyRequest().authenticated()
        .and()
        .httpBasic();
}

```

___

### ✅ `configure(AuthenticationManagerBuilder auth)`

**Purpose:**  
Defines **how authentication is done** — i.e., where user details come from.

**Typical Uses:**
-   In-memory user details.
-   Database-backed users via `UserDetailsService`.
-   Custom `AuthenticationProvider`.


**Example:**

```java
@Override
protected void configure(AuthenticationManagerBuilder auth) throws Exception {
    auth.inMemoryAuthentication()
        .withUser("user").password("{noop}password").roles("USER");
}

```

Or with custom `UserDetailsService`:

```java
@Override
protected void configure(AuthenticationManagerBuilder auth) throws Exception {
    auth.userDetailsService(customUserDetailsService)
        .passwordEncoder(passwordEncoder());
}

```
___

### Summary Table

| Method | What it Configures | Used For |
| --- | --- | --- |
| `configure(HttpSecurity)` | **Web request security** | URL access rules, login method |
| `configure(AuthenticationManagerBuilder)` | **Authentication source** | Users, passwords, roles |

## 19. Explain best practices to securely store secrets in applications.

#### 🔐 1. **Use a Secrets Management System**

-   **Cloud-native**:
    -   AWS Secrets Manager
    -   Azure Key Vault
    -   Google Secret Manager

-   **Self-hosted**:
    -   HashiCorp Vault
    -   Doppler, SOPS, etc.
➡ These systems provide encryption, access control, auditing, and versioning.


#### 📦 2. **Never Hardcode Secrets**

-   ❌ Don’t put secrets in:
    -   Source code
    -   `.env` files checked into Git
    -   Configuration files under version control

-   ✅ Use environment variables or mounted secrets (e.g., via Kubernetes or Docker).

#### 🛡 3. **Encrypt at Rest and in Transit**

-   Store secrets encrypted on disk (AES-256 recommended).
-   Use TLS/HTTPS when secrets are transmitted (e.g., from app to secret store).


#### 👤 4. **Apply Least Privilege Access**

-   Grant secrets **only to the components that need them**.
-   Use **IAM roles or service principals** with narrow scope.


#### 🕓 5. **Implement Secret Rotation**

-   Rotate secrets periodically or after an incident.
-   Automate rotation if possible (e.g., AWS Secrets Manager auto-rotation).


#### 📜 6. **Audit Access and Usage**

-   Enable logging and auditing:
    -   Who accessed which secret?
    -   When and how?

-   Monitor for unauthorized access patterns.


#### ☁️ 7. **In Cloud Apps, Prefer Instance Metadata or Workload Identity**

-   Example:
    -   Use IAM roles for EC2 or GCP Workload Identity instead of embedding keys.


#### 📁 8. **Separate Secrets by Environment**

-   Keep **dev, test, and prod secrets** isolated.
-   Use different keys or stores per environment.


#### 🧪 9. **Sanitize Logs and Error Messages**

-   Never log secrets.
-   Ensure stack traces or debug logs don’t contain sensitive data.


#### ✅ 10. **Scan Code for Secrets**

-   Use tools like:
    -   [GitLeaks](https://github.com/gitleaks/gitleaks)
    -   [TruffleHog](https://github.com/trufflesecurity/trufflehog)
    -   GitHub secret scanning
