### hw15 Microservices

##### 1. Explain monolithic architecture, service oriented architecture and Microservice architecture.
- Monolithic Architecture:
  Definition: The entire application, UI, business logic, data access, is built, versioned, and deployed as a single unit.  
  Key Characteristics: Single codebase, Single deployment artifact, Tight coupling    
  Pros: 1. Easy to develop, test, and deploy when small. 2. In‑process calls are fast. 3. Unified logging, metrics, and debugging     
  Cons: 1. must scale the whole app even if only one part needs more resources. 2. Any change requires rebuilding and redeploying everything. 3. Hard to adopt new languages or frameworks for parts of the app.  






- Service oriented architecture:  
  Definition: Break the application into coarse‑grained “services” that communicate (often over an Enterprise Service Bus) but still share common infrastructure and governance.    
  Key Characteristics: 1. Each service encapsulates a full business capability. 2. Central middleware for routing, transformation, and orchestration. 3. Shared contracts & governance.  
  Pros: 1. Reusability: Services can be consumed by multiple applications. 2. Moderate decoupling: Teams can work on different services, though still bound by shared bus/config.  
  Cons: 1. Single point of failure, additional latency. 2. Heavyweight integration. 3. Slower agility






- Microservice architecture
  Definition: Decompose functionality into many small, autonomous services that own their own data and can be built, deployed, and scaled independently, communicating via lightweight protocols (e.g., REST/JSON, messaging).  
  Key Characteristics:   
  - Fine‑grained services: Each does one thing well.  
  - Decentralized data: Each service manages its own database/schema.    
  - Lightweight communication: REST, gRPC, or message queues (no central bus).    
  - Independent deployment: Separate CI/CD pipelines, versioning, runtimes.    
  
  Pros: 1. Scale only the services under heavy load. 2. Technology freedom. 3. Teams can deploy their service without touching others. 4. Resilience: Failure isolation, meaning one service going down doesn’t necessarily take the whole system.     
  Cons: 1. Operational complexity: Distributed tracing, monitoring, and debugging across many services. 2. Network overhead: Remote calls add latency and need fault‑tolerance patterns (retries, circuit breakers). 3. Data consistency: Managing transactions across services is harder (often eventual consistency).   


##### 2. Document the microservice architeture and core components

###### API Gateway
- Definition: single entry point between clients and services, handles routing, authentication, rate limiting, and protocol translation
- Tech: AWS API Gateway, Kong, NGINX

###### Service Registry & Discovery
- Definition: maintains a dynamic directory of available service instances, enabling clients or services to locate healthy endpoints
- Tech: Netflix Eureka, Consul, ZooKeeper

###### Configuration Server
- Definition: central store for application settings, supports multiple environments and dynamic refresh
- Tech: Spring Cloud Config, Vault

###### Circuit Breaker & Rate Limiting
- Definition: monitors service call health and “opens” circuits on failures, provides fallbacks to prevent cascading outages
- Tech: Resilience4j, Istio sidecar, Envoy

###### Message Bus / Asynchronous Communication
- Definition: decouples services through event- or message-driven patterns for resilience and eventual consistency
- Tech: Apache Kafka, RabbitMQ, AWS SQS/SNS

###### Database per Service
- Definition: each service owns its own database or schema, preventing direct cross-service data coupling
- Tech: PostgreSQL, MongoDB, MySQL, DynamoDB

###### Logging & Monitoring
- Definition: centralized log aggregation, metrics collection, and distributed tracing for visibility and alerting
- Tech: ELK/EFK (Elasticsearch, Logstash/Fluentd, Kibana), Prometheus, Grafana, Jaeger

###### Security (AuthN/AuthZ)
- Definition: unified authentication and fine-grained authorization, secure service-to-service communication
- Tech: OAuth2/OpenID Connect (Keycloak, Auth0), mTLS via Istio

###### Container Orchestration & Infrastructure
- Definition: automates scheduling, scaling, and self-healing of service containers
- Tech: Kubernetes, Docker Swarm, Nomad

###### CI/CD
- Definition: automated build, test, and deployment pipelines for fast and reliable delivery
- Tech: Jenkins, GitHub Actions, GitLab CI/CD, Argo CD



##### 3. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.  
(1)  In modern distributed systems, transient network errors, latency spikes or overloaded endpoints can cascade into widespread outages.  
Resilience patterns: retries, timeouts, circuit breakers, bulkheads, rate limiters and fallbacks, define structured ways to detect failures early, isolate faulty components and degrade gracefully.  
These are realized by libraries and platforms such as **Resilience4j and Spring Retry (Java), Netflix Hystrix (legacy), Envoy or Istio sidecars** for **circuit breaking** and rate limiting, and **Kubernetes resource quotas** for bulkhead isolation.
(2) Explain circuit breaker: A circuit breaker protects your system from cascading failures by tracking remote call success/failure rates and “opening” (fast‑failing) when errors exceed a threshold, then periodically probing the downstream service in a HALF‑OPEN state and “closing” (normal calls) once health is restored.
States
- CLOSED: calls flow, failures are counted
- OPEN: calls fail immediately without invoking the downstream
- HALF‑OPEN: a limited number of test calls pass through

Hystrix code example:
1. Add the Hystrix starter to your `pom.xml`  
2. Enable circuit breakers in the SpringBootApplication  application: @EnableCircuitBreaker  
3. Define a service with a Hystrix‑protected method and a fallback
```java
@Service
public class PaymentService {

  private final RestTemplate restTemplate;

  public PaymentService(RestTemplate restTemplate) {
    this.restTemplate = restTemplate;
  }

  @HystrixCommand(
    commandKey = "processPayment",
    fallbackMethod = "paymentFallback",
    commandProperties = {
      @HystrixProperty(name = "circuitBreaker.requestVolumeThreshold", value = "10"),
      @HystrixProperty(name = "circuitBreaker.errorThresholdPercentage", value = "50"),
      @HystrixProperty(name = "circuitBreaker.sleepWindowInMilliseconds", value = "5000"),
      @HystrixProperty(name = "execution.isolation.thread.timeoutInMilliseconds", value = "2000")
    }
  )
  public String processPayment(String orderId) {
    String url = "https://payments.example.com/pay?order=" + orderId;
    return restTemplate.getForObject(url, String.class);
  }

  // Must match original signature
  public String paymentFallback(String orderId) {
    return "Payment service unavailable for order " + orderId;
  }
}

```
4. Expose the service via a REST controller  

##### 4. Explain load balancing algorithms.  

###### Round Robin
Distributes requests evenly in turn to each server; simple and fair for homogeneous instances.

###### Weighted Round Robin
Assigns requests based on preset weights; higher‑capacity servers receive more traffic.

###### Least Connections
Routes each request to the server with the fewest active connections; adapts to dynamic load.

###### Weighted Least Connections
Combines weights with connection counts; favors less‑busy, higher‑capacity servers.

###### IP Hash
Uses a hash of the client’s IP to consistently route requests to the same server; provides session affinity.

###### Least Response Time
Sends requests to the server with the lowest average response time; optimizes overall latency but requires real‑time metrics.




##### 5. Explain API Gateway.  

Definition: a single entry point that abstracts microservice topology and handles cross‑cutting concerns.

#### Request routing
forwards incoming client requests to appropriate backend services.

###### Authentication / Authorization
verifies tokens (JWT, OAuth2) and enforces access control policies.

###### Rate limiting / Throttling
controls request throughput per client or API to protect downstream services.

###### Protocol translation
bridges differences between HTTP, gRPC, WebSocket, etc.

###### Request aggregation
combines multiple service responses into a single payload.

###### Caching
stores frequent responses to reduce latency and offload services.

###### Load balancing
distributes traffic across service instances for availability and performance.

###### Monitoring / Logging
collects metrics, traces, and logs for observability and troubleshooting.





##### 6. Explain service discovery and service registry  
###### Service Registry
Definition: a central directory where service instances register themselves, storing metadata such as network locations and health status
- Responsibilities:
  - register/deregister instances at startup/shutdown
  - perform health checks and remove unhealthy instances
  - expose an up‑to‑date list of available services
- Examples: Netflix Eureka, Consul, Apache ZooKeeper

###### Service Discovery
Definition: the mechanism by which clients or routers locate and invoke healthy service instances using the registry
- Patterns:
  - client‑side discovery: client queries registry and load‑balances across returned instances
  - server‑side discovery: a load balancer (e.g., API Gateway or service mesh) queries registry and forwards requests
- Benefits: decouples callers from hard‑coded endpoints, supports dynamic scaling and failover
- Examples: Ribbon (client‑side), Kubernetes DNS (server‑side), AWS Cloud Map
