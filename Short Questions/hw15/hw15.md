1. Explain monolithic architecture, service oriented architecture and Micro service architecture.

   **Monolithic Architecture**:

   - All the components of the application are tightly coupled as **a single unit**.

     ```
     [ UI + Business Logic + Data Access ] --> One deployable unit (e.g., WAR, JAR)
     ```

   - Pros:

     - Simple to develop (at early stage)
     - Easy to test as a whole
     - Less overhead in inter-process communication

   - Cons:

     - Hard to scale individual components
     - A change in one area requires full redeployment
     - Difficult to adopt new technologies, app must be written with 1 tech stack
     - Poor fault isolation: one bug can crash the entire app

   - Example: 

     A single Spring Boot application that includes: User Management, Product Catalog, Order Processing. All in one `myapp.jar`.

   **Service Oriented Architecture**:

   - A **collection of loosely coupled services** that communicate over a network using a common protocol (often **SOAP** or HTTP).

     ```
     [ Service A ] <--> [ ESB(Enterprise Service Bus) ] <--> [ Service B ]
     ```

   - Pros:

     - Better separation of concerns than monoliths
     - Promotes reuse of services across apps
     - Centralized governance and security

   - Cons:

     - ESB can become a **bottleneck or single point of failure**
     - Complex deployment and testing
     - More heavyweight than microservices

   - Example: An e-commerce system where: Inventory service, Payment service, andUser authentication service communicate via an ESB and follow shared contracts (WSDL, XML schemas).

   **MicroService Architecture**:

   - It splits one large application into multiple small and independent service based applications. Each service only does one thing.

   - Each service has its own DB, and communicates via lightweight protocols (REST/HTTP, gRPC, messaging)

     ```
     [ User Service ] --REST--> [ Order Service ] --REST--> [ Payment Service ]
     ```

   - Pros:
     - Independent development, deployment, and scaling
     - Better fault isolation
     - Easier to adopt different technologies per service (polyglot)
     - Faster time to market via parallel teams.
   - Cons:
     - Complex service coordination and debugging
     - Requires robust DevOps, CI/CD, monitoring, and security
     - Network latency and data consistency challenges
   - Example: A Netflix-like system: Auth service in Node.js; Recommendation service in Python; Billing service in Java. All deployed and scaled separately in Docker containers.

   

2. Document the microservice architeture and core components.

   Microservice is an architeture design pattern where an application is composed of **small, independent services**, each responsible for a specific business functionality. 

   **Three main principles:**

   - Single Responsibility Principle: Each service should be responsible for only one thing.
   - Bounded Context: Each service should have its own data model (Entity, DTO). So changes in one service do not affect the others.
   - Domain-Driven Design(DDD): Each service should modeled around a specific business capability.

   **Core Components**:

   | **Component**                    | **Purpose**                                                  | **Example Tools**                                    |
   | -------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
   | **Service**                      | Independent business services, each with own logic and database | Spring Boot, Node.js, Go, .NET Core                  |
   | **API Gateway**                  | Entry point for client requests, routing, authentication, rate limiting | Spring Cloud Gateway, Kong, AWS API Gateway, NGINX   |
   | **Service Registry & Discovery** | Track and locate service instances dynamically               | Eureka, Consul, Zookeeper                            |
   | **Load Balancer**                | Distributes incoming traffic across service instances for better availability and performance | AWS ELB, NGINX, HAProxy, Istio                       |
   | **Circuit Breaker**              | Prevents cascading failures by stopping calls to failing services and offering fallbacks | Hystrix, Resilience4j, Istio                         |
   | **Configuration Management**     | Centralized, dynamic management of service configs           | Spring Cloud Config, Consul K/V, etcd                |
   | **Inter-Service Communication**  | Enables communication between services (**sync/async: message queue**) | **Sync**:REST, gRPC;<br />**Async**: Kafka, RabbitMQ |
   | **Database per Service**         | Each service owns and manages its own data store             | MySQL, PostgreSQL, MongoDB, Cassandra                |
   | **Centralized Logging**          | Aggregate and search logs from multiple services             | ELK Stack, Fluentd + Loki                            |
   | **Monitoring & Tracing**         | Metrics, health checks, and distributed tracing              | Prometheus, Grafana, Jaeger, Zipkin, OpenTelemetry   |
   | **Security**                     | Authentication, authorization, and secure service-to-service communication | OAuth2, Keycloak, mTLS, Istio                        |
   | **CI/CD Pipeline**               | Automates building, testing, and deployment                  | Jenkins, GitHub Actions, GitLab CI, ArgoCD           |

   **Advantages**:

   - Faster, parallel development: Teams can work on different services **independently and simultaneously**
   - Independent scaling: Each service can be scaled **horizontally** based on its specific resource demands
   - Technology flexibility: Teams can choose the most suitable **programming language**, **database**, and **framework** for each service
   - Resilience (isolated failure): Failures are **isolated** to the affected service and don’t crash the whole application

   

3. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.

   Resilience patterns are design stratrgies that help the microservices system withstand failure and maintain functionality.

   **Common Resilience Patterns**

   | **Pattern**         | **Purpose**                                                  |
   | ------------------- | ------------------------------------------------------------ |
   | **Circuit Breaker** | If a service fails repeatedly, the circuit breaker "opens," preventing further calls to the failing service and allowing it to recover. It prevents **cascading failures**, fails fast and provide a **fallback** method to handle failures gracefully. |
   | **Retry**           | Automatically retry failed operations, often with a delay or backoff. |
   | **Fallback**        | Provides a **default** behavior or response when the primary service fails. |
   | **Bulkhead**        | Isolates failures by allocating separate resources for different components. |
   | **Timeout**         | Aborts slow operations that exceed a defined time threshold. |
   | **Rate Limiting**   | Prevents services from being overloaded by l**imiting the number of requests**. |

   Hystrix is a Netflix-developed library that implements the circuit breaker pattern.

   How it works:

   1. Add hystrix dependencies to pom.xml


      ```java
      @SpringBootApplication
      ```

4. Explain load balancing algorithms.

   Load balancing algorithms determine **how incoming requests are distributed** across multiple servers when the traffic load increases.

   **Static load balancing**: follow **predefined rules** and not consider the real-time server load state

   - Round-robin method
     - Each request is assigned to the next server in a cyclic order
     - Use when all servers have roughly the **same capacity** and performance
     - Example:
        If you have 3 servers A, B, and C:
       - Request 1 → A
       - Request 2 → B
       - Request 3 → C
       - Request 4 → A (cycle repeats)

   - Weighted round-robin method
     - Assigns more requests to servers with higher weights (representing more capacity)
     - Use when servers have **unequal capacity**
     - Example:
       - Server A (weight=3), B (weight=1), C (weight=1)
       - Request distribution: A, A, A, B, C, A, A, A, B, C, ...

   - IP hash method
     - The client’s IP address is hashed to select a server
     - Use when need **session stickiness** (e.g., user always routed to same server)
     - Example:
       - Hash(IP address) % total_servers = server_index
       - Client with same IP always routes to same backend

   **Dynamic load balancing**: examine the **real-time state** (e.g., CPU, memory, connections) of the servers before distributing traffic

   - Least connection method
     - Traffic is routed to the server with the fewest active connections
     - Use whenonsystems with **uneven request processing time**
   - Weighted least connection method
     - Within the server with the fewest active connections, a server with more capacity (higher weight) can handle more connections
     - Use on systems with **variable capacity servers**
   - Least response time method
     - Directs requests to the server with the lowest average response time
     - Use when **latency** and **performance** are more important than raw connections
   - Resource-based method
     - Uses real-time server metrics like **CPU usage, memory, I/O**, etc., to route traffic
     - Use on high-performance or cloud-native systems using monitoring agents

   

5. Explain API Gateway.

   API Gateway is **a single entry point** for **routing** client requests to multiple backend services or APIs in a microservices system. It often performs additional responsibilities like authentication, rate limiting, logging, and request transformation. With it, clients can call **a single, unified API** without call each microservice directly.

   

6. Explain service discovery and service registry.

   **Service Discovery**: 

   In microservices, services are usually dynamic(scale up/down, move across hosts), so we can't rely on their static addresses. Service Discovery can help services **find and communicate with each other automatically**, **without hardcoding IP addresses or hostnames**.

   | Type                      | Description                                                  |
   | ------------------------- | ------------------------------------------------------------ |
   | **Client-side Discovery** | The **client queries the service registry** to find the service and makes the request directly. Use on internal microservices communicating with each other. |
   | **Server-side Discovery** | The **API Gateway or load balancer queries the registry**, then forwards the request. Use on external clients accessing services via API Gateway. |

   **Service Registry**: Eureka, Zookeeper

   The core component of the service discovery system: a **central database** that stores the **locations (host + port)** of all available service instances.
