#### 1. Explain `monolithic architecture`, `service-oriented architecture` and `microservice architecture`.

---

|             | **Monolithic Architecture**                              | **Service-Oriented Architecture (SOA)**                     | **Microservice Architecture**                                |
|-------------|-----------------------------------------------------------|------------------------------------------------------------|-------------------------------------------------------------|
| **Definition** | A single, unified software application.                  | A collection of services that communicate over a network.   | Small, independent services that communicate over a network.  |
| **Components** | All components are tightly coupled in a single codebase.  | Components are loosely coupled and share a common platform. | Each service is independent and deployable.                  |
| **Scalability** | Difficult to scale, requires scaling the entire app.     | Scales at the service level but often with complex infrastructure. | Easily scalable by independently scaling services.           |
| **Deployment** | Single unit, all changes are deployed together.          | Services are deployed individually but often on the same platform. | Services are deployed independently, allowing for more flexibility. |
| **Fault Tolerance** | If one part fails, the whole system may fail.             | Failure in one service can affect the whole system.        | Fault isolation: failure in one service does not affect others. |
| **Complexity** | Simple to develop initially but grows complex over time. | More complex due to service coordination and communication. | High complexity, each service requires independent management. |
| **Use Case** | Suitable for small to medium-sized applications.         | Suitable for large applications but with more management overhead. | Ideal for large, distributed applications needing flexibility and scalability. |

#### 2. Document the `microservice architecture` and its core components.

---

Microservice Architecture is a design approach where an application is composed of small, independent services that communicate over a network. 

Each service is focused on a specific business function and can be developed, deployed, and scaled independently.


Microservice Architecture Core Components:

| Component             | Description                                               |
|-----------------------|-----------------------------------------------------------|
| **Service**            | Self-contained unit responsible for a specific business capability. |
| **API Gateway**        | Entry point for clients; handles routing, composition, and protocol translation. |
| **Service Registry**   | Keeps track of available services and their network locations (e.g., Eureka). |
| **Load Balancer**      | Distributes requests across multiple service instances for scalability and reliability. |
| **Configuration Server** | Centralized management of configuration across services (e.g., Spring Cloud Config). |
| **Service Communication** | Usually HTTP/REST or messaging protocols.                 |
| **Database per Service** | Each service has its own database to ensure loose coupling. |
| **Monitoring & Logging** | Tracks service health and logs activity (e.g., Prometheus, ELK Stack). |
| **Security**            | Authentication, authorization, and secure communication (e.g., OAuth2, JWT). |
| **CI/CD Pipeline**      | Automates building, testing, and deployment of services.  |

#### 3. Explain `Resilience patterns`. Explain `circuit breaker` with Spring Cloud `Hystrix` code example.

---

Resilience patterns are strategies used in distributed systems to ensure system stability and availability during failures or latency issues. 

They help prevent cascading failures and improve fault tolerance.


Common Resilience Patterns:

| Pattern            | Description                                                                 |
|--------------------|-----------------------------------------------------------------------------|
| **Circuit Breaker** | Stops calling a failing service temporarily to prevent overload.            |
| **Retry**           | Automatically retries failed requests a fixed number of times.             |
| **Fallback**        | Provides a default response or alternative logic when a service fails.     |
| **Bulkhead**        | Isolates components so failure in one doesn't bring down others.           |
| **Rate Limiter**    | Limits the number of requests a service can handle to prevent overload.    |
| **Timeout**         | Limits the time a service waits for a response from another service.       |

---

`Hystrix` is a `circuit breaker` library in Spring Cloud to handle service failures gracefully.

Code Example:

Maven Dependency:
```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-hystrix</artifactId>
</dependency>
```

Enable Hystrix:
```java
@SpringBootApplication
@EnableCircuitBreaker
public class Application { }

```

Example Service with Circuit Breaker:
```java
@Service
public class UserService {

    @HystrixCommand(fallbackMethod = "getDefaultUser")
    public String getUserDetails() {
        return restTemplate.getForObject("http://user-service/users/1", String.class);
    }

    public String getDefaultUser() {
        return "Default User";
    }
}
```

**Note:** `Hystrix` is in maintenance mode. Use `Resilience4j` for new projects.

#### 4. Explain `load balancing` algorithms.

---

| Algorithm             | Description                                                                 | Use Case                                                  |
|-----------------------|-----------------------------------------------------------------------------|-----------------------------------------------------------|
| **Round Robin**       | Distributes requests evenly in a circular order.                            | Simple, suitable when all servers have similar capacity.  |
| **Weighted Round Robin** | Like Round Robin, but servers with higher weight get more requests.         | Useful when servers have different processing capacities. |
| **Least Connections** | Sends request to the server with the fewest active connections.             | Good when requests have varying processing time.          |
| **IP Hash**           | Hashes client IP to consistently route requests to the same server.         | Sticky sessions, session persistence.                     |
| **Random**            | Chooses a server at random.                                                  | Fast but not optimized for performance.                   |
| **Consistent Hashing**| Minimizes redistribution when servers are added/removed.                    | Distributed caching, session stickiness.                  |
| **Least Response Time** | Chooses server with the lowest average response time.                       | Performance-optimized load balancing.                     |

#### 5. Explain `API Gateway`.

---

An `API Gateway` is a single entry point for all client requests in a microservice architecture.  
It acts as `a reverse proxy` to route requests, enforce policies, and aggregate responses from multiple services.






---
#### 6. Explain `service discovery` and `service registry`.

---

In a microservice architecture, `Service Discovery` and `Service Registry` are used to dynamically locate services without hardcoding their network locations.


A `Service Registry` is a database of available services and their instances (host, port).

`Service Discovery` is the process of finding a service's network location using the registry.


**Summary**: 
- Service Registry keeps track of service instances. 
- Service Discovery finds them.
