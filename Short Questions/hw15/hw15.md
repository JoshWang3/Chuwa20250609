#### 1. Explain monolithic architecture, service oriented architecture and Micro service architecture.  

**1. Monolithic Architecture:**
A monolithic architecture is a unified model where all components of an application—UI, business logic, data access layer—are developed and deployed as a single codebase and unit. It's simple to develop and test initially but becomes difficult to scale and maintain as the application grows, due to tight coupling and low modularity.

**2. Service-Oriented Architecture (SOA):**
SOA structures the application as a collection of services that communicate over a network. Each service is a business function, often exposed over protocols like SOAP. While it promotes reusability and loose coupling, it tends to be heavier due to reliance on enterprise service buses and standardized messaging.

**3. Microservices Architecture:**
Microservices decompose an application into small, independent services that are loosely coupled, independently deployable, and aligned with business capabilities. Each service communicates typically via lightweight protocols like REST or gRPC. This architecture supports better scalability, continuous deployment, and fault isolation, but introduces complexities like distributed data management and service coordination.



#### 2. Document the microservice architecture and core components    
Microservice architecture is a design pattern where an application is structured as a collection of small, loosely coupled, independently deployable services. Each service is responsible for a single business capability and communicates with other services over lightweight protocols, typically HTTP or messaging queues.

**Core Components:**

1. **Service Components** – Independently deployable units, each owning its data and logic, often aligned with specific business domains (bounded contexts).

2. **API Gateway** – Acts as a single entry point for clients. It handles routing, request aggregation, authentication, and rate limiting.

3. **Service Registry & Discovery** – Maintains a dynamic list of service instances. Services register themselves and discover others (e.g., Netflix Eureka, Consul).

4. **Load Balancer** – Distributes traffic evenly across service instances to ensure availability and fault tolerance.

5. **Database per Service** – Each microservice manages its own database to ensure loose coupling and independent scaling.

6. **Inter-Service Communication** – Typically implemented using REST, gRPC, or messaging systems like Kafka or RabbitMQ.

7. **Centralized Configuration** – Shared configuration management (e.g., Spring Cloud Config) allows dynamic updates without redeploying services.

8. **Monitoring and Logging** – Tools like ELK Stack, Prometheus, and Grafana track metrics, logs, and traces to observe system health and debug issues.

9. **Security** – Token-based authentication (OAuth2, JWT), and TLS are commonly used to secure service-to-service and client interactions.

10. **CI/CD Pipeline** – Enables automated testing, building, and deployment of services to support rapid and safe delivery.

This architecture supports scalability, fault isolation, and technology diversity but introduces complexity in terms of orchestration, consistency, and monitoring.




#### 3. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.  
**Resilience Patterns in Microservices**

Resilience patterns are design strategies used to build fault-tolerant systems. Common resilience patterns include:

1. **Circuit Breaker** – Prevents calls to a failing service to avoid cascading failures.
2. **Retry** – Automatically retries a failed operation a predefined number of times.
3. **Timeout** – Fails a call if it takes too long, avoiding resource blocking.
4. **Fallback** – Provides an alternative response when a service fails.
5. **Bulkhead** – Isolates failures to prevent a single failing service from affecting others.
6. **Rate Limiter** – Controls the number of requests to a service to prevent overload.


**Circuit Breaker with Spring Cloud Hystrix – Example**

Using **Spring Cloud Netflix Hystrix**, we can implement a circuit breaker like this:

**1. Add dependencies (Maven):**

```xml
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-netflix-hystrix</artifactId>
</dependency>
```

**2. Enable Hystrix in Spring Boot App:**

```java
@SpringBootApplication
@EnableCircuitBreaker
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

**3. Create a Service with Circuit Breaker:**

```java
@Service
public class UserService {

    @HystrixCommand(fallbackMethod = "getUserFallback")
    public String getUserById(String id) {
        // Simulate external service call
        if (new Random().nextBoolean()) {
            throw new RuntimeException("Service failure");
        }
        return "User-" + id;
    }

    public String getUserFallback(String id) {
        return "Fallback-User";
    }
}
```

**4. REST Controller to Test:**

```java
@RestController
public class UserController {

    @Autowired
    private UserService userService;

    @GetMapping("/user/{id}")
    public String getUser(@PathVariable String id) {
        return userService.getUserById(id);
    }
}
```

**Key Points:**

* `@HystrixCommand` wraps the service call with circuit breaker logic.
* If the call fails or times out, it triggers `getUserFallback`.
* This avoids overloading the failing service and gives the client a graceful fallback.

**Note:** Spring Cloud Netflix is in maintenance mode. For new applications, consider using **Resilience4j**, which is the recommended alternative.




#### 4. Explain load balancing algorithms.  

Load balancing algorithms are essential in microservices architecture to distribute incoming network traffic across multiple service instances efficiently. The primary goal is to ensure high availability, scalability, and optimal resource utilization.

**Common load balancing algorithms include:**

1. **Round Robin**: Distributes requests sequentially across the service instances. It's simple and effective when instances have similar capacity.

2. **Least Connections**: Routes traffic to the instance with the fewest active connections. This is beneficial when request load varies significantly.

3. **IP Hash**: Uses a hash of the client's IP address to determine which instance will handle the request. This provides session stickiness without maintaining server-side state.

4. **Weighted Round Robin**: Similar to Round Robin, but assigns weights to instances based on capacity, so more powerful instances handle more traffic.

5. **Weighted Least Connections**: Combines instance weights with active connection count to route requests more intelligently.

6. **Random**: Selects an instance at random. Simple and sometimes effective when combined with other health check mechanisms.

In microservices, these algorithms are typically implemented at the API gateway, service mesh (like Istio), or within client-side load balancers such as Netflix Ribbon or Spring Cloud LoadBalancer. The choice of algorithm often depends on workload characteristics and service performance profiles.




#### 5. Explain API Gateway.  
An **API Gateway** in a microservices architecture acts as a **single entry point** for all client interactions with backend services. It handles **request routing, composition, and protocol translation**, essentially abstracting the internal microservices from external clients.

Key responsibilities include:

* **Routing**: Directs incoming requests to the appropriate microservice.
* **Load Balancing**: Distributes traffic across multiple service instances.
* **Authentication & Authorization**: Enforces security policies before passing requests downstream.
* **Rate Limiting & Throttling**: Controls API usage to prevent abuse or overload.
* **Aggregation**: Combines responses from multiple services to reduce client-side complexity.
* **Caching**: Improves performance by serving cached responses for frequently requested data.

Common implementations include **Spring Cloud Gateway**, **Kong**, **NGINX**, and **AWS API Gateway**. Proper use of an API Gateway enhances scalability, security, and maintainability in microservices-based systems.





#### 6. Explain service discovery and service registry  

**Service Registry** is a centralized database or repository that keeps track of all available service instances and their network locations (IP addresses, ports). When a service starts, it registers itself with the registry, providing its metadata and endpoint details.

**Service Discovery** is the process by which a microservice client queries the service registry to find the network location of another service it needs to communicate with. This eliminates hardcoding service locations, enabling services to scale dynamically and handle failures gracefully.

In practice, tools like **Eureka**, **Consul**, or **Zookeeper** are often used to implement service registry and discovery. This approach helps achieve loose coupling, better scalability, and fault tolerance in distributed systems.
