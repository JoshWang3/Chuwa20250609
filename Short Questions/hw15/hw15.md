## 1. Explain monolithic architecture, service oriented architecture and Micro service architecture.

### 🧱 1. Monolithic Architecture

**Definition**:  
A single, unified application where all components (UI, business logic, data access) are bundled together and run as one
process.

**Characteristics**:

- Single codebase.

- Tight coupling between components.

- Deployed as one unit.

**Pros**:

- Simple to develop and test initially.

- Easy to deploy.

- Suitable for small applications.

**Cons**:

- Difficult to scale parts independently.

- Any change requires full redeployment.

- Hard to maintain and understand as it grows.

**Example**:  
An e-commerce app with login, product catalog, cart, and payment in a single application.

---

### 🧩 2. Service-Oriented Architecture (SOA)

**Definition**:  
An architecture where functionality is divided into **services** that communicate over a network, usually via XML/SOAP.

**Characteristics**:

- Services are larger, coarse-grained.

- Often relies on **Enterprise Service Bus (ESB)**.

- Shared services and central governance.

**Pros**:

- Reusability of services.

- Better separation of concerns than monolith.

- Centralized governance and integration.

**Cons**:

- Heavyweight communication (e.g., SOAP/XML).

- ESB becomes a single point of failure.

- Less flexible than microservices.

**Example**:  
A banking system where account, loans, and customer management are separate services using a centralized message bus.

---

### 🧬 3. Microservice Architecture

**Definition**:  
An architecture where the application is composed of **small, independent services**, each focused on a single business
capability.

**Characteristics**:

- Services are lightweight and loosely coupled.

- Communicate over HTTP/REST or messaging (e.g., Kafka).

- Each service has its **own database** and is independently deployable.

**Pros**:

- Scalable and flexible.

- Independent development and deployment.

- Technology-agnostic (each service can use different tech stack).

**Cons**:

- Complex to manage (e.g., service discovery, distributed tracing).

- Requires robust DevOps and monitoring.

- Data consistency is a challenge (eventual consistency).

**Example**:  
An e-commerce platform with separate microservices for users, inventory, orders, payments, and reviews.

---

### 🧾 Summary Table

| Aspect        | Monolithic       | SOA                | Microservices             |
|---------------|------------------|--------------------|---------------------------|
| Codebase      | Single           | Multiple services  | Many small services       |
| Deployment    | One unit         | Multiple (via ESB) | Independently             |
| Coupling      | Tightly coupled  | Loosely coupled    | Loosely coupled           |
| Communication | In-process       | XML/SOAP via ESB   | REST, gRPC, messaging     |
| Scalability   | Entire app       | Somewhat modular   | Fine-grained scaling      |
| Best For      | Small teams/apps | Enterprise systems | Cloud-native, agile teams |

## 2. Document the microservice architecture and core components.

### 🧩 Overview

Microservice architecture is an approach where a single application is composed of many loosely coupled and
independently deployable services. Each service focuses on a specific business capability and communicates over
lightweight protocols (typically HTTP/REST, gRPC, or messaging queues).

### 🗂️ Core Components

#### 1\. **API Gateway**

- **Purpose**: Entry point for all client requests.

- **Responsibilities**:

    - Request routing

    - Authentication & Authorization

    - Rate limiting

    - Response aggregation

- **Example Tools**: Kong, NGINX, Spring Cloud Gateway, AWS API Gateway

#### 2\. **Microservices**

- **Definition**: Independent services responsible for a single business functionality.

- **Characteristics**:

    - Own data and business logic

    - Independently deployed

    - Communicate via HTTP/gRPC/message brokers

- **Examples**:

    - User Service

    - Order Service

    - Inventory Service

#### 3\. **Service Registry & Discovery**

- **Purpose**: Keeps track of service instances and their locations.

- **Functionality**:

    - Services register on startup

    - Clients query registry to locate service endpoints

- **Example Tools**: Eureka, Consul, Zookeeper

#### 4\. **Configuration Server**

- **Purpose**: Central management of service configurations.

- **Features**:

    - Version-controlled config files

    - Environment-based configs

- **Example Tools**: Spring Cloud Config, Consul, etcd

#### 5\. **Inter-Service Communication**

- **Approaches**:

    - **Synchronous**: REST, gRPC

    - **Asynchronous**: Message Queues (RabbitMQ, Kafka)

- **Pattern**:

    - API clients or event-based messaging for decoupling

#### 6\. **Database per Service**

- **Design Rule**: Each microservice has its own database.

- **Benefits**:

    - Decoupled schemas

    - No single point of contention

- **Patterns**:

    - Data replication

    - Event sourcing

    - CQRS (Command Query Responsibility Segregation)

#### 7\. **Centralized Logging**

- **Purpose**: Aggregate and analyze logs from all services.

- **Tools**: ELK Stack (Elasticsearch, Logstash, Kibana), Fluentd, Graylog

#### 8\. **Monitoring & Metrics**

- **Purpose**: Track service health and performance.

- **Metrics**:

    - Latency

    - Throughput

    - Error rates

- **Tools**: Prometheus + Grafana, Datadog, New Relic

#### 9\. **Distributed Tracing**

- **Purpose**: Trace requests across microservices.

- **Benefits**:

    - Performance bottleneck identification

    - Root cause analysis

- **Tools**: OpenTelemetry, Jaeger, Zipkin

#### 10\. **Security**

- **Mechanisms**:

    - OAuth2/JWT for authentication

    - Mutual TLS between services

    - API keys for external consumers

- **Best Practices**:

    - Principle of least privilege

    - Secure configuration management

#### 11\. **CI/CD Pipeline**

- **Purpose**: Automate building, testing, and deploying services.

- **Stages**:

    - Code build

    - Unit/integration tests

    - Docker image creation

    - Deployment (Kubernetes, ECS, etc.)

- **Tools**: Jenkins, GitLab CI, GitHub Actions, ArgoCD

#### 12\. **Containerization & Orchestration**

- **Tools**:

    - **Docker**: Container packaging

    - **Kubernetes**: Service orchestration, scaling, and failover

    - **Helm**: Kubernetes package management

## 3. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example.

### ✅ **Resilience Patterns in Microservices**

Resilience patterns help microservices handle **failures gracefully** without cascading issues across the system. They
ensure **fault tolerance**, **availability**, and **stability** under failure conditions.

### 🔑 **Common Resilience Patterns**

1. **Circuit Breaker**

    - Prevents a service from making calls to a failing service repeatedly.

    - Stops cascading failures by "opening" the circuit when error threshold is reached.

2. **Retry Pattern**

    - Retries the request after a temporary failure with exponential backoff.

3. **Timeout**

    - Sets a maximum wait time for a response; prevents thread blocking.

4. **Bulkhead**

    - Isolates failures by partitioning resources (like thread pools).

5. **Fallback**

    - Provides an alternative response when a service call fails.

6. **Rate Limiter**

    - Controls request flow to prevent overload.

---

### ✅ **Circuit Breaker Pattern**

**What is it?**

- It wraps remote calls in a circuit breaker object that monitors failures.

- States:

    - **Closed**: Requests allowed (normal state).

    - **Open**: Requests blocked due to repeated failures.

    - **Half-Open**: Limited test requests allowed; if successful, circuit closes again.

---

### **Spring Cloud + Hystrix Circuit Breaker Example**

#### **Step 1: Add Dependencies**

Add Hystrix to your Spring Boot project in `pom.xml`:

```xml

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-hystrix</artifactId>
</dependency>
```

---

#### **Step 2: Enable Hystrix**

In the main class:

```java

@SpringBootApplication
@EnableCircuitBreaker
public class ResilienceApp {
    public static void main(String[] args) {
        SpringApplication.run(ResilienceApp.class, args);
    }
}
```

---

#### **Step 3: Service with Circuit Breaker**

Example of calling an external service with fallback:

```java

@Service
public class ProductService {

    @HystrixCommand(fallbackMethod = "getDefaultProduct")
    public String getProductDetails() {
        // Simulate call to external API
        if (new Random().nextBoolean()) {
            throw new RuntimeException("External service failed!");
        }
        return "Product details from external service";
    }

    // Fallback method
    public String getDefaultProduct() {
        return "Default Product - Service Unavailable";
    }
}
```

---

#### **Step 4: Controller**

```java

@RestController
@RequestMapping("/products")
public class ProductController {

    @Autowired
    private ProductService productService;

    @GetMapping
    public String fetchProduct() {
        return productService.getProductDetails();
    }
}
```

---

#### **Step 5: Enable Hystrix Metrics Stream**

For monitoring:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: hystrix.stream
```

---

### ✅ **How It Works**

- When `getProductDetails()` fails repeatedly, Hystrix **opens the circuit**, preventing further calls for a period.

- During the open state, all calls are redirected to the fallback method.

- After a timeout, the circuit moves to **Half-Open** to check if the service is healthy.

## 4. Explain load balancing algorithms.

### ✅ **1\. Round Robin**

- **How it works:**  
  Requests are assigned to servers in a fixed circular sequence. After the last server, the process starts again from
  the first.

- **Example:**  
  S1 → S2 → S3 → S1 → S2 → S3

- **Pros:**

    - Very simple and fast.

    - Fair distribution if all servers have equal power.

- **Cons:**

    - Doesn’t account for server load or performance differences.

- **Use case:**  
  Homogeneous servers with similar capacity (e.g., static web servers).

---

### ✅ **2\. Weighted Round Robin**

- **How it works:**  
  Similar to Round Robin, but each server has a **weight** based on capacity. A server with a higher weight gets more
  requests.

- **Example:**  
  S1(weight=3), S2(weight=1) → S1, S1, S1, S2

- **Pros:**

    - Balances load for heterogeneous servers.

- **Cons:**

    - Still ignores real-time load.

- **Use case:**  
  When servers differ in CPU, memory, or network capacity.

---

### ✅ **3\. Geo-Based Load Balancing**

- **How it works:**  
  Routes requests based on the user’s geographic location. Typically implemented in **DNS-based GSLB (Global Server Load
  Balancing)**.

- **Example:**

    - User from USA → US data center

    - User from Asia → Singapore data center

- **Pros:**

    - Reduces latency by serving from the nearest location.

- **Cons:**

    - Requires accurate geo-IP mapping.

    - Not real-time load-aware.

- **Use case:**  
  CDNs, global web services, multi-region deployments.

---

### ✅ **4\. Least Connections**

- **How it works:**  
  Sends a new request to the server with the **fewest active connections**.

- **Pros:**

    - Good for uneven traffic and long-lived connections.

- **Cons:**

    - Requires real-time connection tracking.

- **Use case:**  
  Applications with persistent connections (e.g., database servers, chat apps).

---

### ✅ **5\. Token Bucket (or Ticket Bucket)**

- **How it works:**  
  A **rate-limiting algorithm** that uses tokens to control the rate of requests sent to a server. Each request requires
  a token; tokens are refilled at a fixed rate.

    - If the bucket is empty, requests are delayed or dropped.

- **Purpose:**

    - Primarily used for **rate limiting**, not pure load balancing.

- **Pros:**

    - Prevents overload by limiting request bursts.

- **Cons:**

    - Doesn’t distribute traffic across multiple servers by itself.

- **Use case:**  
  API gateways, microservices rate limiting, DoS attack prevention.

---

### 🔍 **Key Differences**

| Algorithm        | Balancing Type | Real-Time Load Aware? | Use Case                 |
|------------------|----------------|-----------------------|--------------------------|
| Round Robin      | Static         | ❌ No                  | Equal-capacity servers   |
| Weighted RR      | Static         | ❌ No                  | Heterogeneous servers    |
| Geo-Based        | Static (DNS)   | ❌ No                  | Multi-region deployments |
| Least Connection | Dynamic        | ✅ Yes                 | Long-lived connections   |
| Token Bucket     | Rate Control   | ❌ No (Capacity-based) | API rate limiting        |

## 5. Explain API Gateway.

- **What it is:**  
  A **server that sits between clients and backend APIs**, acting as a single entry point.

- **Purpose:**

- Routes client requests to appropriate backend APIs.

- Handles **authentication, rate limiting, caching, load balancing, logging**.

- **Scope:**

- Operates at **system level** to manage **multiple APIs**.

- **Key Responsibilities:**

    - **Routing**: Routes requests to the correct microservice based on path/headers.

    - **Authentication & Authorization**: Validates API keys, OAuth, JWT.

    - **Request/Response Transformation**: Convert JSON ↔ XML, modify headers.

    - **Rate Limiting & Throttling**: Controls traffic to prevent overload.

    - **Caching**: Improves performance by storing responses.

    - **Monitoring & Logging**: Collects metrics for APIs.

- **Popular API Gateway Solutions:**

    - AWS API Gateway
    - Kong
    - NGINX
    - Apigee (Google)
    - Spring Cloud Gateway

## 6. Explain service discovery and service registry

### ✅ **1\. What is Service Discovery?**

**Service Discovery** is the process by which a service (e.g., Service A) locates another service (e.g., Service B) to
make a request.  
Since microservices are usually deployed in **dynamic environments** (containers, Kubernetes, cloud), their IP addresses
and ports can change frequently. Therefore, hardcoding endpoints is impractical.

**Goal of Service Discovery:**

- Dynamically **find the network location (IP + port)** of a service at runtime.

#### **Types of Service Discovery**

1. **Client-Side Discovery**

- The **client** (caller) is responsible for finding the target service.

- Steps:

    -   Client queries a **Service Registry** to get the list of available instances.

    -   Client uses **load balancing** logic to select one instance and makes the request.

- Example: Netflix OSS **Eureka** with **Ribbon** load balancer.

- **Pros:** Simpler server; client knows all instances.

- **Cons:** Each client must implement discovery logic.

2. **Server-Side Discovery**

- The client sends a request to a **load balancer** or **API Gateway**.

- The load balancer queries the **Service Registry** and forwards the request to an available instance.

- Example: AWS **Elastic Load Balancer (ELB)**, Kubernetes **Service**.

- **Pros:** Clients stay simple; discovery logic centralized.

- **Cons:** Extra hop (load balancer adds latency).

---

### ✅ **2\. What is a Service Registry?**

A **Service Registry** is a **database** or **directory** of available services and their network locations.  
Every service **registers itself** (or is registered) when it comes online and **deregisters** when it goes offline.

#### **Key Responsibilities**

- Maintain **health status** of services (via health checks or heartbeats).

- Allow **lookup of services** by name.

- Provide **real-time updates** when services join or leave.

#### **Common Implementations**

- **Eureka** (Netflix OSS)

- **Consul** (by HashiCorp)

- **Zookeeper** (Apache)

- **Etcd** (used in Kubernetes)

---

### ✅ **How They Work Together**

- When **Service A** wants to call **Service B**:

1. Service B registers itself with the **Service Registry** (with its IP and port).

2. Service A queries the registry to find Service B.

3. Depending on discovery type:

    -   **Client-side:** Service A picks an instance and calls it directly.

    -   **Server-side:** A load balancer (or gateway) picks an instance for Service A.

---

#### **Diagram (Client-Side Discovery)**

```css

```

#### **Diagram (Server-Side Discovery)**

```css

```

---

#### ✅ **Why Do We Need This?**

- Microservices run in **dynamic environments** (Docker, Kubernetes).

- IPs are **ephemeral** (change after restart).

- Auto-scaling means **service instances come and go**.

- Avoid **hardcoding endpoints**.
