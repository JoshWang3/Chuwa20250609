Explain following concepts, and how they coordinate with each other:
    1. Topic: A tpoic in Kafka is a logical channel where messages are published by producers. Topices are categorized by name and store streams of data. Messages in a topic are retained for a configurable retention period.
    2. Partition: A partition is a unit of parallelism within a topic. Each topic is divided into multiple partitions, and each partition stores a subset of the topic's message. Partition allow Kafka to scale horizontally by distributing data across multiple brokers. Messages within a partition are ordered, but across partitions, ordering is not guranteed.
    3. Broker: A broker is a Kafka server that stores data and serves client requests(producer and consumers). Kafka brokers collectively form a Kafaka cluster and coordinate to distribute partitions across the brokers. Each broker handles partitions assigned to it and ensures fault tolerance via replication.
    4. Consumer group: A consumer group is a collection of consumers that work together to consume messages from a topic. Each consumer in the group is assigned one or more partitions to read from, ensuring that partitions are distributed among the group members. Consumers in the same group coordinate to avoid reading the same messages.
    5. Producer: A producer publishes messages to Kafka topics. Producers can specify which partition to sned a message to or let Kafka distribute messages automatically using a partition algorithm.
    6. Offset: An offset is a unique identifier for a message within a partition. It represents the position of the message in the partition's log. Consumers use offset to track their progress in reading messages from a partition.
    7. Zookeeper: Zookeeper is a distributed coordination service used by Kafka for managing metadata. It helps Kafka maintain cluster state and ensures fault tolerance.

    How components coordinate:
    * Producers send message to topics, which are divided into partitions. Kafka distributes partitions across brokers for scalability and fault tolerance.
    * Consumers in a consumer group read messages from partitions, ensuring that each partition is consumed by only one consumer in the group
    * Offset track which messages have been read by consumers
    * Zookeeper coordinates metadata management, such as partition leadership and broker health

Answer following questions:
1. Given N (number of partitions) and M (number of consumers,) what will happen when N>=M and N < M respectively?
    N >= M: 
        * Each consumer in the group will be assigned at least one partition
        * Some partitions may be assigned to multiple consumers, depending on the distributed algorithm
        * For example for 4 partitions and 2 consumers, each consuer will handle 2 partitions
    N < M:
        * Some consumers will remain idle because there are not enough partitions to assign to all consumers 
        * For example for 2 aprtitions and 4 consumers, only 2 consumers will be active and the remaining 2 will be idle
  
2. Explain how brokers work with topics?
   * Brokers store partition of topics. Each partition is replicated across multiple brokers for fault tolerance.
   * One broker is designated as the leader for each partition, responsible for handling read and write requests for that partition.
   * Other brokers act as replica and sychronized data with the leader

3. Are messages pushed to consumers or consumers pull messages from topics?
    * Consumers pull message from topics
    * Consumers request message from partitions at their own pace, allowing them to controle the rate of consumption

4. How to avoid duplicate consumption of messages?
    * Kafka avoid duplicate consuption by tracking the offset for each consumer group
    * Consumer commit their offset after processing messages. If a consumer craches, it can resume from the last committed offset
    * Idempotent processing: Ensure that message processing logic is idempotent, such as adding an idempotency key.

5. What will happen if some consumers are down in a consumer group? Will data loss occur? Why?
    * No data loss occurs
    * Kafka retains messages in the topic for a configurable rentention period. When the down consumers recover, they can resume processing from their last committed offset.
    * Other cosumers in the group may take over the partitions of the down consumers temporarily.

6. What will happen if an entire consumer group is down? Will data loss occur? Why?
    * No data loss occuers
    * Kafka retains messages in the topic based on the configured retention period.
    * When the consumer group is restored, its members can resume processing from the last committed offset

7. Explain consumer lag and how to resolve it?
    * Consumer lag is the difference between the latest offset in the partition and the last committed offset by a consumer group.
    * Causes:
      * Slow consumer processing
      * High message production rate
      * Network or resource constraints
    * Resolution:
      * Scale the number of consumers in the group
      * Optimize consumer processing logic
      * Allocate more resources to consumers

8. Explain how Kafka tracks message delivery?
    * Kafka tracks message delivery using offset
    * Consumers commit offsets after processing messages. These committed offsets are stored in Kafka itself
    * If a consumer craches, it can resume from the last committed offset

9.  Compare Kafka vs RabbitMQ, compare messageing frameworks vs MySql (Why Kafka)?

    **Kafka vs RabbitMQ**
    | Feature       | Kafka                                    | RabbitMQ                                             |
    | ------------- | ---------------------------------------- | ---------------------------------------------------- |
    | Message Model | Log-based(presistent message storage)    | Queue-based (messages are removed after consumption) |
    | Scalability   | Highly scalable (partitioning)           | Limited scalability                                  |
    | Throughput    | High throughput for large-sclae system   | Suitable for moderate worklaods                      |
    | Retention     | Stores messages for a configuable period | Messages are removed after acknowledgment            |
    | Use Case      | Event streaming, real-time analytics     | Task queues, short-lived messaging                   |

    **Messaging Framework vs. MySQL
    | Feature          | Messaging Frameworks                        | MySQL                            |
    | ---------------- | ------------------------------------------- | -------------------------------- |
    | Message Delivery | Asychronous, real-time delivery             | Not designed for messaging       |
    | Scalability      | Horizontal scalability(brokers, partitions) | Limited scalability              |
    | Retention        | Configurable message retention              | Data is stored indefinitely      |
    | Performance      | Optimized for high throughput messaging     | Optimized for transactional data |

    **Why Kafka?**
    * Kafka is designed for high-throughput, scalable, and fault tolerant messaging
    * Enable real-time data streaming and event-driven architectures
    * Provides durable storage for messsages, unlike traidtional messaging systems
    * Supports distributed systems with partitioning and replication.

Change the configuration in producer config
```java
package com.chuwa.demo.config;

import com.chuwa.demo.partitioner.CustomPartitioner;
import org.apache.kafka.clients.admin.NewTopic;
import org.apache.kafka.clients.producer.ProducerConfig;
import org.apache.kafka.common.serialization.StringSerializer;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.core.DefaultKafkaProducerFactory;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.core.ProducerFactory;
import java.util.HashMap;
import java.util.Map;

@Configuration
public class KafkaProducerConfig {

    @Value("${spring.kafka.bootstrap-servers}")
    public String bootstrapServers;


    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> configProps = new HashMap<>();
        configProps.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, bootstrapServers);
        configProps.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        configProps.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
       // Add custom Partitioner
        configProps.put(ProducerConfig.PARTITIONER_CLASS_CONFIG, CustomPartitioner.class);

        return new DefaultKafkaProducerFactory<>(configProps);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate() {
        return new KafkaTemplate<>(producerFactory());
    }

    @Bean
    public NewTopic createTopic() {
        return new NewTopic(
                "${kafka.topic.name}",
                3,
                (short) 2);
    }
}
```
