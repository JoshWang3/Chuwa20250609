<p> Explain following concepts, and how they coordinate with each other: </p>

<p> Topic: a particular stream of data </p>

<p> Partition: data is randomly assigned to a partition </p>

<p> Broker: contains certain topic partitions </p>

<p> Consumer group: Consumer reads data in consumer groups </p>

<p> Producer: writes data to topics </p>

<p> Offset: each message within a partition gets an incremental id </p>

<p> Zookeeper: manage brokers </p>

<p> Answer following questions: </p>
<p> 1. Given N (number of partitions) and M (number of consumers) what will happen when N >= M and N < M respectively? </p>

When N >= M, consumers will automatically use a GroupCoordinator and a ConsumerCoordinate to assign a consumer to a partition.
When N < M, some consumers will be inactive. 

<p> 2. Explain how brokers work with topics? </p>

Each broker contains certain topic partitions

<p> 3. Are messages pushed to consumers or consumers pull messages from topics? </p>

Consumers pull messages from topics. Kafka is a pull-based messaging system,

<p> 4. How to avoid duplicate consumption of messages? </p>

Introduce idempotency key with each message. (Idempotency ensures that multiple same operation won't affect data)

<p> 5. What will happen if some consumers are down in a consumer group? Will data loss occur? Why? </p>

No, data loss will not occur because some consumers in a Kafka consumer group go down 
as long as offsets are managed properly and retention settings are respected.

<p> 6. What will happen if an entire consumer group is down? Will data loss occur? Why? </p>

No data loss will occur by default, as long as Kafka's retention policy is respected.

<p> 7. Explain consumer lag and how to resolve it? </p>

<p> Difference between the latest message on the topic and the last committed offset by the consumer group. </p>

`
1). Scale Out the Consumer Group: Add more consumer instances
2). Optimize Consumer Logic: Avoid slow operations (e.g., synchronous DB writes)
3). Tune Consumer Configurations
4). Monitor and Alert: Set alerts on lag thresholds
5). Rebalance or Reassign Partitions: If one consumer is overloaded, consider custom partition assignment or scaling up.
`

<p> 8. Explain how Kafka tracks message delivery? </p>

Producer can wait for acknowledge to track message delivery

<p> 9. Compare Kafka vs RabbitMQ, compare messaging frameworks vs MySql (Why Kafka)? </p>

`
Kafka: Distributed, durable event log system
Best for event-driven architecture, analytics, and microservice decoupling
RabbitMQ: flexible, transactional message queue
Best for job queues, task processing, and request/response patterns
MySQL: Use for data, not messages
Good for storage and queries, but not scalable messaging
`
