## Explain following concepts, and how they coordinate with each other:
### Topic
A topic is a category or feed name to which records are sent by producers. It’s the logical channel where Kafka messages are published and read.

* Think of it as a table in a database.



### Partition


Each topic is split into partitions for scalability and parallelism.

* Data is assigned randomly to a partition unless a key is provided
* Each partition is ordered and Order is guaranteed only within a partition(not across partitions)

### Broker
A broker is a Kafka server that stores topic data (partitions).

* each broker contains certain topic partitions

* A Kafka cluster typically has multiple brokers.

* Each broker can manage multiple partitions.

* Brokers handle receiving messages from producers and serving them to consumers.

### Consumer group

A consumer is a client application that reads data (messages) from Kafka topics.

A consumer group is a group of consumer instances that work together to consume data from a topic.

* Allows load balancing: if there are 3 partitions and 3 consumers, each consumer gets 1 partition.



### Producer

* producers write data to topics (which is made of partitions)
  
* producers automatically know to which broker and partition to write to

* in case of broker failures, producers will automatically recover


### Offset

An offset is a unique identifier for each record within a partition.

* It acts like a bookmark.

* Consumers track offsets to know which message to read next.

* Offsets can be committed manually or automatically by consumers.

### Zookeeper
Apache Kafka uses Zookeeper to manage metadata and cluster coordination.


## Answer following questions:
### 1. Given N (number of partitions) and M (number of consumers,) what will happen when N >= M and N < M respectively?

* N ≥ M (partitions ≥ consumers)
    * Each consumer gets at least one partition

    * Some consumers may get more than one

    * Efficient parallel consumption

* N < M (partitions < consumers)
    * Some consumers will be inactive

    * Kafka assigns only one consumer per partition, so extra consumers do nothing

### 2. Explain how brokers work with topics?

* A broker stores partitions of topics.

* When a topic is created, its partitions are distributed across brokers.

* Each partition has:

    * A leader broker (handles reads/writes)

    * Follower brokers (replicas for fault tolerance)

* Brokers also:

    * Handle producer and consumer requests

    * Communicate with Zookeeper
### 3. Are messages pushed to consumers or consumers pull messages from topics?

Using pull-based model

* Consumers request (pull) data from Kafka brokers at their own pace.

* This gives consumers control over:

    * How much data they read

    * When they read it

    * How often they commit offsets

### 4. How to avoid duplicate consumption of messages?

* Use Kafka’s offset management carefully:

    * Commit offsets only after processing is complete

* Use idempotent operations in consumers (e.g., deduplication keys in DB)

### 5. What will happen if some consumers are down in a consumer group? Will data loss occur? Why?

No, data will not be lost. 

* Kafka handles this situation automatically:
    * Kafka detects that a consumer in the group is down (via heartbeat timeout).

    * It triggers a rebalance — the partitions assigned to the failed consumer are reassigned to the remaining active consumers in the group.

    * The new consumer(s) continue consuming from the last committed offset, so no data is lost.


### 6. What will happen if an entire consumer group is down? Will data loss occur? Why?

* Still no data loss, as long as:

    * Kafka’s retention policy has not expired (default: 7 days)

* When the group comes back, it resumes from last committed offset

* If offsets are not committed, consumers may reprocess old data (duplicate possible)


### 7. Explain consumer lag and how to resolve it?

* Consumer Lag = (Latest offset in partition) - (Last committed offset by consumer)

* High lag = consumers are falling behind


How to reduce lag:
* Add more consumers (if more partitions exist)

* Optimize consumer logic (e.g., faster processing, batching)

* Ensure efficient offset commits

* Scale hardware/resources



### 8. Explain how Kafka tracks message delivery?

* Kafka uses offsets to track message delivery.
* Offsets are per-partition, per-consumer group bookmarks.


### 9. Compare Kafka vs RabbitMQ, compare messageing frameworks vs MySql (Why Kafka)?

Kafka vs RabbitMQ:
* Both are messaging systems, but they’re built for different purposes and have key differences.

Kafka:
* Pull-based
* Event streaming, big data pipelines, log ingestion

RabbitMQ:
* Push-based
* Task queues, short-lived jobs, RPC-like messaging

frameworks vs MySql:
* Using MySQL as a message queue is possible (e.g., a messages table), but it's not ideal

MySQL:
* Slower due to transactional overhead
* Tight coupling between producers and consumers

Kafka:
* High throughput, optimized for logs
* Excellent for microservice decoupling

Why Kafka? (vs RabbitMQ or MySQL)
* Extremely fast & scalable

* Can replay messages from any point in time

* Built for big data, stream processing (e.g., with Kafka Streams or Flink)

* Decouples producers and consumers

* Ideal for real-time analytics & pipelines


When not to use Kafka?
* For simple task queues (use RabbitMQ or Redis)

* For small apps that don’t need stream processing or event replay

* For low-latency RPC-style communication
