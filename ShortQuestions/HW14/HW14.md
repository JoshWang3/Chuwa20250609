## 1. Explain monolithic architecture, service oriented architecture and Micro service architecture

### ✨ Monolithic Architecture
Definition: A single, unified application where all functionalities (UI, business logic, database) are part of one codebase and deployed together.

Characteristics:
- All features are tightly coupled.
- Easy to develop and test initially.
- Simple to deploy (single WAR/JAR).

Problems:
  - Difficult to scale individual features.	
  - A single bug can crash the whole system.
  - Hard to maintain as the codebase grows. 
  - All components are tightly coupled, leading to tight dependency and deployment issues.

### ✨ Service-Oriented Architecture (SOA)
Definition: An architecture where the application is composed of services that communicate over a network, typically using XML-based protocols like SOAP.

Characteristics:
- Services are reused and shared across the enterprise.
- Uses Enterprise Service Bus (ESB) for communication.
- Emphasis on business service interfaces and contracts.

Problems:
- Heavier communication protocols (SOAP). 
- ESB can become a bottleneck or single point of failure.

Microservice is presented as an evolution of SOA with more granularity, independence, and looser coupling. 

Key differences implied include:
- ESB-based centralized communication vs. decentralized communication in microservices.
- Larger services with potentially shared models across services (contrary to DDD in Microservices).

### ✨ Microservice Architecture

Definition: A design pattern where a large system is broken into small, independent, and loosely coupled services, each focused on a single business capability

Characteristics:
- Independently Deployable: Each service can be deployed on its own.
- Loosely Coupled: Communicate through APIs, not shared memory.
- Domain Driven Design (DDD): Each service owns its data and business logic

Advantages:
- Better scalability and fault isolation.
- Flexibility in tech stack (e.g., one service in Java, another in Node.js).
- Faster development by different teams.

Problems:
- Complex inter-service communication.
- Requires DevOps maturity (CI/CD, monitoring, logging).
- Data consistency and security are harder to manage.

## 2. Document the microservice architecture and core components


### Microservice Architecture

Key Properties:
* Independently Deployable
* Loosely Coupled
* Focused on Single Responsibility
* Bounded Context
* Uses Domain-Driven Design (DDD)

### Core Components of Microservice Architecture

#### 1. API Gateway
- Acts as the single entry point for all clients.
- Routes requests to the appropriate backend services.
- Common tools:
  - Zuul, Zuul2 (legacy)
  - Spring Cloud Gateway (recommended)
- Handles:
  - Authentication 
  - Logging
  - Response transformation
- Example mapping:
```http request
POST http://xhs.com/deals  -->  Service 1: http://deals.xhs.com/api/v1/deals
POST http://xhs.com/users  -->  Service 2: http://users.xhs.com/api/v1/users
```


#### 2. Service Discovery (Eureka)
- Keeps track of all running services and their instances.
- Allows dynamic lookup of service locations (IP + Port).
- Supports health monitoring and auto-registration.
- Tools:
  - Spring Cloud Eureka Server (`@EnableEurekaServer`)
  - Spring Cloud Eureka Client (`@EnableEurekaClient`)

#### 3. Load Balancer
- Distributes incoming requests among service instances.
- Ensures fault tolerance and scalability.
- Types:
  - Client-side Load Balancer (e.g., Ribbon)
  - Server-side Load Balancer (e.g., Nginx)
- Performs health checks to remove failed instances from routing.

#### 4. Circuit Breaker (Resilience)
- Prevents cascading failures when a dependent service fails.
- If errors exceed threshold, the circuit opens and triggers fallback logic.
- Tool: Hystrix (Spring Cloud Netflix)
```java
@GetMapping("/id/{id}")
@HystrixCommand(fallbackMethod = "handleFallback")
```

#### 5. Distributed Configuration Server
- Centralizes configuration across all services.
- Externalizes environment-specific properties.
- Tool: Spring Cloud Config Server


#### 6. Messaging (Asynchronous Communication)
- Used for decoupled, event-driven communication.
- Tool: Kafka
  - Topics, Partitions, Brokers, Producers, Consumers
  - Guarantees high-throughput and fault-tolerant messaging.
       ￼
#### 7. Database per Service
- Each service owns and manages its own database.
- Promotes data encapsulation and avoids coupling.
- Example: Product Service uses product_db, Order Service uses order_db

#### 8. (Monitoring & Logging)

- Used to track metrics, logs, traces.
- Tools often used: ELK Stack, Prometheus, Grafana, Zipkin

## 3. Explain Resilience patterns? Explain circuit breaker with Spring Cloud Hystrix code example
### Resilience Patterns in Microservice Architecture

#### Why Resilience?

> In a distributed microservices system, services depend on each other. If one service fails or slows down, it may cause a cascading failure across the system. 
Resilience patterns prevent this by adding fault-tolerance mechanisms.

| Pattern          | Description                                                                 |
|------------------|-----------------------------------------------------------------------------|
| Circuit Breaker  | Opens the circuit to stop calls to a failed service, preventing overload.   |
| Fallback         | Provides a default response when the primary service fails.                 |
| Timeouts         | Fails a request if it takes too long, avoiding thread exhaustion.           |
| Retry            | Retries a failed request a limited number of times.                         |
| Bulkhead         | Isolates failures to specific components, like compartments on a ship.      |
| Rate Limiting    | Controls the rate of incoming requests to protect the service.              |

### Circuit Breaker with Spring Cloud Hystrix

Concept:
- If a service call fails repeatedly, the circuit opens.
- No further calls are made until a cooldown period elapses.
- During this time, the app calls a fallback method.
- Once the system recovers, the circuit closes automatically.


Code Example:
```java
@GetMapping("/city/{city}")
@HystrixCommand(fallbackMethod = "handleWeatherServiceDown")
public ResponseEntity<WeatherResponse> getWeatherByCity(@PathVariable String city) {
    WeatherResponse response = new WeatherResponse();

    // Call to another microservice
    LocationInfo location = locationRepository.findByCity(city);
    response.setLocation(location);

    // This external call might fail
    Forecast forecast = restTemplate.getForObject(
            "http://WEATHER-SERVICE/forecast/" + city, Forecast.class
    );
    response.setForecast(forecast);

    return new ResponseEntity<>(response, HttpStatus.OK);
}

public ResponseEntity<WeatherResponse> handleWeatherServiceDown(String city) {
    WeatherResponse response = new WeatherResponse();

    // Provide only location info if weather service fails
    LocationInfo location = locationRepository.findByCity(city);
    response.setLocation(location);
    response.setForecast(null); // null forecast as fallback

    return new ResponseEntity<>(response, HttpStatus.SERVICE_UNAVAILABLE);
}
```

## 4. Explain load balancing algorithms.
### ⚖️ Load Balancing Algorithms in Microservices

In microservices architecture, load balancing distributes incoming traffic across multiple service instances to enhance scalability, reliability, and system performance.

### Types of Load Balancing

#### 1. **Client-Side Load Balancing**
- Logic for selecting the service instance resides on the client (e.g. a microservice).
- The client fetches a list of available instances (typically from a registry like Eureka).
- Tools: **Spring Cloud Ribbon**
- Pros: No extra network hop; faster routing decisions.

#### 2. **Server-Side Load Balancing**
- A centralized server (like a proxy or gateway) forwards requests to available backend instances.
- Clients are unaware of backend details.
- Tools: **Nginx**, **HAProxy**
- Pros: Centralized management; useful for external traffic.

### Common Load Balancing Algorithms

| Algorithm                 | Description                                                                 |
|---------------------------|-----------------------------------------------------------------------------|
| **Round Robin**           | Rotates requests evenly among all servers in order.                         |
| **Least Connections**     | Sends traffic to the server handling the fewest active connections.         |
| **Random**                | Selects a target server at random.                                          |
| **IP Hash**               | Routes clients to a server based on their IP address, ensuring stickiness.  |
| **Weighted Round Robin**  | Prioritizes servers based on assigned weights (e.g., CPU capacity).         |
| **Consistent Hashing**    | Minimizes disruptions when nodes are added/removed, often used in caching.  |

### Tools That Support Load Balancing

- **Ribbon**: Client-side balancer used in Spring Cloud environments.
- **Nginx**: Popular server-side balancer for HTTP traffic.
- **Eureka**: Often paired with Ribbon for dynamic instance discovery.

## 5. Explain API Gateway
### What is an API Gateway?

> An API Gateway is a single entry point that sits between clients (e.g., frontend, mobile apps) and the backend microservices. It acts as a traffic manager, directing incoming API requests to the appropriate microservice.
>
> Instead of the client calling multiple microservices directly, the client makes a single request to the API Gateway, which handles routing, transformation, and additional cross-cutting concerns.


### Key Responsibilities

- **Routing**: Directs client requests to the correct microservice endpoint.
- **Load Balancing**: Distributes traffic across service instances.
- **Authentication and Authorization**: Enforces security policies centrally.
- **Request Transformation**: Modifies request formats, headers, or payloads before forwarding.
- **Response Aggregation**: Combines results from multiple services into one response.
- **Monitoring and Logging**: Captures request logs, response times, and metrics for observability.
- **Rate Limiting**: Controls how many requests each client can make over time.


### Common Tools

| Tool                     | Description                                                                    |
|--------------------------|--------------------------------------------------------------------------------|
| **Zuul**                 | Netflix’s original gateway library (now deprecated).                           |
| **Zuul2**                | Improved version with non-blocking I/O, but not supported by Spring.           |
| **Spring Cloud Gateway** | Modern reactive gateway built on Spring WebFlux, preferred in Spring projects. |

---

### Example Flow

1. A user sends a `POST` request to `http://example.com/orders`.
2. The API Gateway intercepts the request.
3. Based on routing rules, the Gateway forwards it to `http://order-service/api/v1/orders`.
4. The response from the service is returned to the user via the Gateway.

This allows clients to only interact with one domain (`example.com`) while backend services remain hidden and modular.


### 🔐 Security Note

Because the API Gateway is exposed to the public, it often handles:
- Token verification (e.g., JWT)
- Adding user context to requests
- Centralized logging and auditing

## 6. Explain service discovery and service registry


### Service Discovery?

> Service Discovery is the mechanism that allows microservices to locate each other dynamically within a distributed system. 
>
>Instead of hardcoding hostnames and ports, services can register themselves and discover others using a central registry.

---

### What is a Service Registry?

> A **Service Registry** is a centralized database that stores the locations (IP and port) of all registered microservice instances. It maintains a real-time directory of healthy services that are available for communication.

One popular tool for this in the Spring ecosystem is **Spring Cloud Eureka**.

---

### How Them Works

1. **Registration**:
    - When a microservice starts, it automatically registers itself with the registry (e.g., Eureka Server) by providing its service name and address.

2. **Discovery**:
    - Other services query the registry to discover the location of the service they need to call.

3. **Health Checks**:
    - Registered services send periodic heartbeats to inform the registry that they're alive.
    - If a service stops sending heartbeats, it's removed from the registry.
---

### Tools & Annotations (Spring Cloud Eureka)

- `@EnableEurekaServer`: Declares a Spring Boot application as a Eureka server.
- `@EnableEurekaClient`: Used on client microservices to enable auto-registration.
- `spring.application.name`: The logical name by which a service is registered.
- `eureka.client.service-url.defaultZone`: Configures the Eureka server address in `application.properties`.
---
### Diagram
```markdown
+----------------+         +----------------+         +------------------+
| Order Service  | <---->  |  Eureka Server | <---->  | Payment Service  |
+----------------+         +----------------+         +------------------+
       ↑                          ↑                          ↑
       |                    Heartbeat & Status         Heartbeat & Status
       +-----------------------------------------------------+
```

---

### Benefits of Service Discovery

- **Dynamic Routing**: No need to hardcode service URLs.
- **Improved Resilience**: Only healthy instances are returned.
- **Scalability**: Easily supports horizontal scaling (add/remove instances at runtime).
- **Load Balancing Friendly**: Works with tools like Ribbon or Spring Cloud Gateway for routing.

---

### Notes

- Without service discovery, you’d need to manage IP addresses and port configurations manually, which doesn’t scale well.
- In large systems, it's essential for microservices to interact without tight coupling.
