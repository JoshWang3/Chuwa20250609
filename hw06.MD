1. Explain the concept of API(Application Programming Interface), why do we need APIs?
    API stands fro Application Programming Interface. It is a set of rules and protocols that allows different software applications to communicate with each other.
    We need APIs because they are essential for enabling communication and integration between different software systems.
    - Separation of Concerns
      APIs abstract away complexity. You don't need to know how a system works internally -- just how to use its interface.
    - System Integration
      APIs allow different systems, apps, or services to work together, even if they are built with different technologies.
    - Reusability
      APIs allow developers to reuse functionality without rebuilding it from scratch.
    - Faster Development
      Using APIs saves time and effort by letting developers leverage existing tools, services, or platforms.
    - Security and controlled access
      APIs allow secure, controlled access to systems. They expose only what is needed and keep the rest hidden.
    - Support for multiple platforms
      APIs enable your backend system to support multiple client platforms like web, mobile and loT devices.
    - Scalability and Microservices
      APIs are the backbone of microservices architecture, where different parts of a system are separate and communicate via APIs. This helps in scaling and maintaining large systems.
    - Ecosystem and Innovation
      Public APIs allow other developers to build on top of your system, leading to ecosystem growth and innovation.
2. Compare developer API vs application API
   A developer API generally refers to an API that is made specifically for developers to use when building applications.
   it usually is:
        - Well-documented
        - Publicly available or accessible via registration
        - Designed to help developers integrate with a service/platform
   An application API is an interface provided by an application or system that allows other software components, apps, or developers to interact with that application's features or data.

4. Compare path variables vs request parameters in REST API.
   In a REST API, path variables and request parameters are both used to pass data from the client to the server, but they serve different purposes and are used in different parts of the URL.
   Path Variables are for identifying resources.
   Request Parameters are for passing options or controls for the request.
5. Explain the different components that make up a RESTful API and what does each part do?
   - Base URL:
        The root address of your API.
   - Endpoints:
        Each endpoint represents a resource. The resource is identified by a path in the URL.
        Resources are usually nouns, not actions.
   - HTTP Methods:
        Define the action to be performed on a resource:
        GET, POST, PUT, DELETE
   - Request Headers:
        Used to send metadata along with request.
   - Request Body:
        Used with POST, PUT or PATCH, to send data from client to server.
   - Response Body:
        Data returned from the server to the client, usually in JSON or XML.
   - Response Status Codes:
        200 OK
        201 Created
        400 Bad Request
        401 Unauthorized
        404 Not Found
        500 Internal Server Error
   - Query Parameters:
        Optional parameters to filter or customize the request
   - Path Variables
        Used to identify specific resources in the URL.
   - Authentication/Authorization
        APIs often require security measures to control access.
   - Documentation
        Good Restful APIs come with clear documentation.

8. List HTTP methods and their meanings, and their expected HTTP status codes.
   | **Method**  | **Meaning**           | **Used For**                                   | **Typical Success Codes**                                                     | **Typical Error Codes**             |
   | ----------- | --------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------- |
   | **GET**     | Retrieve data         | Fetch a resource or list of resources          | `200 OK` (success), `206 Partial Content` (for partial responses)             | `404 Not Found`, `401 Unauthorized` |
   | **POST**    | Create data           | Submit new data to a resource                  | `201 Created`, `200 OK` (if returning a response), `202 Accepted` (async)     | `400 Bad Request`, `409 Conflict`   |
   | **PUT**     | Replace data          | Fully update or create a resource (idempotent) | `200 OK`, `204 No Content`, `201 Created` (if new)                            | `400 Bad Request`, `404 Not Found`  |
   | **PATCH**   | Modify data           | Partially update a resource                    | `200 OK`, `204 No Content`                                                    | `400 Bad Request`, `404 Not Found`  |
   | **DELETE**  | Remove data           | Delete a resource                              | `204 No Content`, `200 OK` (if returning data), `202 Accepted` (async delete) | `400 Bad Request`, `404 Not Found`  |
   | **HEAD**    | Retrieve headers only | Same as GET, but no response body              | `200 OK`                                                                      | `404 Not Found`                     |
   | **OPTIONS** | Describe options      | Get supported HTTP methods or CORS preflight   | `204 No Content`, `200 OK`                                                    | `405 Method Not Allowed`            |
9. Explain why rest API is stateless.
   Statelessness is one of the core principles of REST.
    - No session information is stored on the server between requests.
    - The server does not remember anything about previous client interactions.
   That also means a REST request usually includes:
      - Authentication info.
      - All necessary data.

10. Discuss about best practices for REST API design, from performance perspective.
    - Use JSON instead of XML.
    - Let clients specify fields using a fields query param
    - Use Nouns, Not verbs
    - Avoid Deep Nesting
    - If use method like getAll(), Pagination is a must.
    - Use Filtering
    - Sorting
    - Use HTTP Cache headers
    - Use Asynchronous Processing For Heavy tasks
    - Error Handling and Rate Limiting
    - Connection and request Optimization
11. Explain the concept of XSS(Cross-Site Scripting) and CSRF(Cross Site Request Forgery) and how to avoid them.
    Cross-Site Scripting is a type of security vulnerability found in web applications. It allows attackers to inject malicious scripts into webpages that are viewed by other users.
        These scripts can:
            - Steal cookies, tokens or session data
            - Deface websites
            - Redirect users to malicious sites
            - Perform actions on behalf of the victim
   To prevent XSS
        - Escape user input
        - Validate and Sanitize input
        - Use a Template Engine
        - Set Security Headers
        - Avoid inline javascript
   Cross-Site Request Forgery is a type of web security vulnerability where and attacker tricks a user's browser into making unwanted requests to a different site where the user is already authenticated
   To prevent CSRF:
        - Use CSRF Tokens
        - SameSite Cookie Attribute
        - Use Custom Headers
        - Check Referer Or origin Headers
        - Use the POST Method with State-Changing Actions
        - User Interaction


API Practices:
    1. OpenWeatherMap - a RESTful Weather API
    Endpoint to get current weather:
      - GET https://api.openweathermap.org/data/2.5/weather?lat={lat}&lon={lon}&appid={API key}
      - Returns weather info in JSON, XML or HTML
      - Query params used to pass lat, lon and API key - a classic RESTful requestpattern
      -
| REST Constraint               | How OpenWeatherMap Demonstrates It                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Client–Server**             | Mobile/web apps (clients) request weather data; OpenWeatherMap (server) stores & processes it — **clear separation** ([webscrapingapi.com][1])                      |
| **Stateless**                 | Each request includes **all needed info**, including location and credentials (`appid`) — server holds no session *state*                                           |
| **Cacheable**                 | Responses can use `Cache-Control`, `ETag`, or `Last-Modified` headers (common in REST APIs) to **reduce repeated calls**                                            |
| **Uniform Interface**         | Uses standard HTTP methods (`GET`), consistent resource URIs (`/weather`), and well-known representations (JSON/XML) — **self-descriptive** and client-independent  |
| **Layered System**            | Calls can be routed through proxies, CDNs, load balancers — clients don’t need to know intermediate layers                                                          |
| **Code on Demand (Optional)** | The API doesn’t deliver executable code — this optional REST constraint is **not used**, which is fine                                                              |
       - Technical Breakdown of the API Call
            GET /data/2.5/weather?lat=35&lon=139&appid=YOUR_KEY HTTP/1.1
            Host: api.openweathermap.org
            Accept: application/json
         HTTP Method: GET safe/idompotent
         Resouce URI:/weather
         Query Parameters: State passed in URL(lat, lon, appid)
         Headers: Use Accept(client-driven content negotiation)
         Response Format: JSON
            {
                "weather":[ {"id":500,"main":"Rain",…} ],
                "main": { "temp":289.92, "humidity":93 },
                …
            }
